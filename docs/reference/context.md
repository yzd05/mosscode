# 上下文管理

长任务中，对话历史会逐渐接近模型的上下文窗口。MossCode 分两层控制历史的大小：第一层在工具结果写入历史前，把过大的结果存到磁盘；第二层在请求前估算上下文，达到阈值时用一次模型请求把较早的消息压缩成摘要，近期消息保留原文。设计取舍见 [第八章规格](../specs/chapter-08-context/spec.md)。

## 配置

| 位置 | 选项 | 默认 | 说明 |
| --- | --- | --- | --- |
| 每个 Provider | `context_window` | 未配置时按 128,000 估算 | 模型的上下文窗口（Token）。程序不维护模型窗口表，以这里的配置为准，`/model` 切换后按新提供商的值重新计算。未配置时启动区提示一次 |
| 每个 Provider | `compact_threshold` | 不设置 | 提前自动压缩的 Token 数，用于大窗口模型。取值需在 16,000 与自动阈值之间 |
| 顶层 | `auto_compact` | `true` | 设为 `false` 时不自动压缩，也不在超限时自救；仍可 `/compact` |

```yaml
providers:
  - name: deepseek
    protocol: openai-chat-completions
    model: replace-with-deepseek-model
    base_url: https://api.deepseek.com
    api_key_env: DEEPSEEK_API_KEY
    max_output_tokens: 16384
    context_window: 1000000      # 以服务文档为准
    # compact_threshold: 200000  # 可选：约 20 万 Token 时就压缩，降低成本和延迟
```

阈值由配置计算：

| 名称 | 计算 | 1M 窗口、输出 16,384 时 |
| --- | --- | --- |
| 输出预留 | `max(max_output_tokens, 20,000)` | 20,000 |
| 有效窗口 | `context_window − 输出预留` | 980,000 |
| 自动阈值 | `有效窗口 − 13,000`；配置了 `compact_threshold` 时取较小值 | 967,000 |
| 手动压缩的摘要请求上限 | `有效窗口 − 3,000` | 977,000 |

自动阈值小于 16,000（窗口太小或 `max_output_tokens` 太大），或 `compact_threshold` 超出范围时，启动时报配置错误。

## 估算

不使用分词器。每次回复完成后，以服务返回的 `input_tokens + output_tokens` 为锚点；下一次请求前的估算值等于锚点加上之后新增消息的估算值。新增部分按字符估算：ASCII 字符每 4 个算 1 Token，其他字符（中文等）每个算 1 Token，每条消息另加 4 Token。中文按 1 字 1 Token 偏保守，避免低估。

服务没有返回输入用量（例如 Chat 协议未开启 `stream_usage`），或刚完成压缩、`/clear`、切换模型时，没有可用的锚点，就按同样的规则估算系统提示、工具定义和全部历史。

## 第一层：大结果存盘

| 情况 | 处理 |
| --- | --- |
| 单个工具结果估算超过 12,500 Token（约 5 万个 ASCII 字符） | 完整原文写入会话目录 `tool-results/<调用 ID>.txt`；历史中保留预览：原始大小、文件路径、前 2,000 字符和后 1,000 字符 |
| 同一批并行调用的结果合计超过 50,000 Token | 在尚未存盘的结果中从大到小依次存盘，直到合计不超限 |
| `read_file` | 不存盘。它已经分页，读的又是磁盘上的文件 |
| 会话目录无法写入 | 只保留预览，并注明未能保存完整内容 |

存盘决定在结果写入历史前做出，之后不再改写，已发送的历史前缀保持不变，不影响 Prompt Cache。模型需要完整内容时用 `read_file` 分页读取存盘文件；读取本会话目录不需要审批，计划模式中也可以读。工具行在结果摘要下注明“完整结果已存盘：路径”。

命令输出的内部上限是 2 MiB，只用于防止内存失控；正常大小的输出都交给第一层处理，不再在 32 KiB 处截断。

## 第二层：压缩

### 何时压缩

- **自动**：每次请求模型前估算，达到自动阈值就先压缩再请求。任务进行中的每一轮都会检查。对话中记一行“✓ 已压缩上下文 · N 条消息 → 摘要 · 约 X Token · 用时”，任务继续，不需要确认。
- **超限自救**：估算偏低、服务仍返回上下文超限错误时，立即压缩并重试一次原请求。重试仍超限就停止任务并报错。每一轮只自救一次。
- **手动**：空闲时输入 `/compact [说明]`，不看阈值。说明会附加到摘要提示中，用来指定摘要的侧重点，例如 `/compact 只保留与 notes.txt 相关的内容`。没有可压缩的内容时给出提示。压缩期间状态栏显示“压缩上下文中”和计时，按 Esc 取消，历史不变。

### 保留哪些消息

从历史末尾往回数，直到保留部分不少于 10,000 Token 且不少于 5 条消息；保留部分不超过自动阈值的 40%，超过时少留几条，但至少保留最后一组完整消息。保留部分不以工具结果开头，对应的工具调用和结果总是一起保留。

### 摘要请求

较早的消息序列化成一条带角色标记的纯文本（`[用户]`、`[助手]`、`[工具调用]`、`[工具结果 · 名称]`），作为一条用户消息发送，不带工具定义。提示的开头和结尾都写明禁止调用工具。模型先在 `<analysis>` 中梳理，再在 `<summary>` 中按 9 部分写摘要：主要请求和意图、关键技术概念、文件和代码段、错误和修复、问题解决过程、用户的偏好与约束、待办任务、当前工作、下一步。程序只取 `<summary>`，草稿丢弃。

摘要请求超过上限时，先把每个工具结果缩短到前 2,000 字符；仍然超限，就丢掉最早 20% 的消息再试，最多缩减 3 次。服务返回上下文超限错误时按同样的方式缩减。

以下情况算失败，历史保持不变：服务报错、回复中没有 `<summary>` 或摘要为空、回复包含工具调用、因输出上限被截断。

### 压缩后的历史

历史变为 `[边界消息, 近期原文…]`。边界消息是一条用户消息，依次包含：

1. 压缩说明和摘要；
2. 被压缩部分的用户原话，按时间顺序由程序原样附上，不经过模型改写。预算 8,000 Token，超出时优先保留较新的消息，较早的只留前 200 字符并注明“原文见记录文件”。多次压缩时，上一次附上的原话继续带入；
3. 记录文件的路径，以及提示：需要具体代码、报错或输出时读取记录文件，文件可能已变化，修改前必须重新读取。

被压缩的原始消息完整写入会话目录的 `compact-<n>.md`。压缩后，所有文件都要重新读取才能修改；下一次请求重新发送模式提醒（与 `/clear` 相同）。

### 熔断

自动压缩（包括超限自救）连续失败 3 次后，本会话暂停自动压缩，并提示“自动压缩已暂停，可以 /compact 手动重试或 /clear”。手动压缩成功、`/clear` 或切换模型后恢复。

## 会话目录

每次启动对应一个会话目录 `~/.mosscode/sessions/<启动时间>-<4 位随机串>/`，第一次存盘或压缩时才创建，其中有 `tool-results/` 和 `compact-<n>.md`。目录中的标记文件 `.mosscode-session` 说明它由 MossCode 创建。启动时删除 30 天前的会话目录，只删除带标记文件的目录。会话目录不是对话记录，不支持恢复会话。

## 界面与无界面输出

| 位置 | 显示 |
| --- | --- |
| 状态栏 | 收到第一次用量后显示“上下文 约 N%”（估算值 ÷ 有效窗口），达到自动阈值的 80% 时用琥珀色 |
| 对话 | 自动压缩的结果显示在本轮回复之前；失败和熔断用琥珀色 `!` 加原因 |
| 工具行 | “完整结果已存盘：路径” |
| `-p` text | 压缩进度和结果输出到 stderr |
| `-p` json / stream-json | result 增加 `compactions`（成功压缩次数）；stream-json 增加 `{"type": "compact", "subtype": "started" / "finished" / "failed", …}` 事件 |
