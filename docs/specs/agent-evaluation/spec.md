# MossCode 评测设计：DeepSeek、版本对照与公开基准

日期：2026-11-13。状态：设计完成，尚未实现。

本规格只规划评测接入与对照方式，尚未安装 Harbor、下载任务或镜像、调用付费模型。实现与首次运行另行推进。

## 目标与边界

评测分别回答三个问题：MossCode 是否仍能完成原本会做的事；一次改动带来了什么收益或退步；在同一模型条件下与公开参考 Agent 相差多少。三个问题分别报告，不合成一个质量总分。

以公开 Terminal-Bench 为能力评测主体，自定义任务补充 Windows、审批、恢复、回退和上下文等产品回归。主模型使用 DeepSeek 官方 API 的 `deepseek-flash`。先接一个模型、一个外部参考和少量配置，不建设评测平台、数据库、网页看板或自动优化系统。

## 已核实的现状

- `evals/tasks/` 已有 13 个受控任务；`scripts/run_evals.py` 支持真实模型、重复运行、隐藏测试、成本与 Markdown 报告。已有一次 DeepSeek 13/13 的结果，适合基础回归与成本参照。
- 当前脚本通过 `Conversation` 调用生产运行时，接入压缩与自动后台设置；尚未接入新加的共享调用预算与 `pre_finish`，也不保存跨提交比较所需的完整实验标识。
- 当前 `check()` 只选择隐藏测试文件，不能由此声称所有原有测试均通过。
- `moss -p --output-format stream-json` 已能输出工具、停止原因、压缩事件、请求与用量。当前费用字段来自模型目录的价格估计，不能直接等同于账单金额。
- 本规格选定的产品代码锚点为 `fccece23950c1db4438a310ecb23bb282dac8288`。工作区另有研究草稿，不作为评测输入。
- Harbor 已提供任务隔离、任务版本配置、重复运行、结果目录和自定义安装式 Agent 接口；这些能力应直接复用。

## 对比对象

| 对比 | 基线 | 运行时机 | 能支持的结论 |
| --- | --- | --- | --- |
| 直接版本对照，主要用途 | 重要改动开始前的 MossCode 提交 | 影响模型行为的一批改动完成后 | 这批改动在相同任务和条件下的收益与退步 |
| 长期锚点 | 固定 MossCode `fccece2` 与冻结的评测配置 | 首次建立；之后在阶段性报告中复用 | 相对最初基线的累计变化 |
| 外部对照 | 固定 Harbor/Terminus 2 版本，同一个 DeepSeek 服务 | 首次建立，重要里程碑或条件变化后复核 | 两套 Agent 配置在该模型和任务集上的差异 |
| 公开成绩 | 官方排行榜、作者公开运行和模型发布报告 | 对外解释结果时引用 | 提供背景；条件不一致时不能作直接实验对照 |

长期锚点不随候选版本变好而覆盖。另记录最近一次接受的稳定版本，用于下一批改动的直接对照。旧基线结果保留；更换模型、任务、判定器或关键资源配置时建立新的实验系列，不把新旧系列连接成单一进步曲线。

公开数据集、参考 Agent 和公开运行结果是不同概念。Terminus 2 是可复跑的参考实现，不是某个固定的分数。本轮未核实到与计划使用的 DeepSeek 后端、任务版本和预算完全匹配的公开结果，初始按自行建立 Terminus 2 对照设计；若后来获得完整、相容的公开结果和运行产物，可导入为历史参照并标注来源。

MossCode 与 Terminus 2 的差异包含提示词、工具和上下文策略及其与模型的配合，不解释成独立于模型的“框架净贡献”。若要判断某项功能的作用，使用同一 MossCode 提交上的功能开关对照；没有干净开关时比较两次提交，并说明其中的其他改动。

## 数据集与运行分档

初始建议冻结 Terminal-Bench 2.1：官方已修正 2.0 中部分任务的问题。要复现 2.0 榜单时使用独立配置，结果不混合。下载后记录精确修订、任务清单、镜像和判定器信息；不使用滚动的 `latest` 作为长期基线。

| 档位 | 任务与次数 | 默认对比对象 | 用途 |
| --- | --- | --- | --- |
| 离线回归 | 直接相关 pytest、模拟模型与必要的受控任务 | 当前代码 | 普通修复与界面调整，无真实模型费用 |
| 接入试跑 | 公开集选 3–5 题，各 1 次 | MossCode 与 Terminus 2 | 验证接入、模型兼容性、环境和费用，不宣布能力提升 |
| 开发抽检 | 从冻结的开发清单选择 3–5 个相关任务，各 1 次 | 候选与改动前版本；相容的旧结果可复用 | 调查一次改动是否值得扩大验证 |
| 阶段评测 | 固定开发子集 12 题，先各 1 次 | 候选与稳定版本，必要时加入外部参考 | 比较一批行为改动；结果不清楚时只对相关任务追加到 3 次 |
| 完整报告 | 官方完整任务清单，先各 1 次，再按预算与报告要求增加重复 | 候选、稳定版；外部参考优先复用相容结果 | 大版本、面试展示、公开能力报告 |

正式提交排行榜时遵守当时的官方协议；项目内部的单次筛查不冒充官方认可的成绩。补跑选中的变化任务用于诊断，不把这种自适应补跑直接并入全体任务的无偏能力分数；正式重复比较使用两边相同、预先声明的完整运行计划。

开发子集在看到 MossCode 成绩前，按任务类别与环境需求抽取并保存清单及选择方法，不只保留有利题目。完整报告使用官方全部任务；本机无法支持的任务要列出，不能静默删去后仍称全量。反复用于调参的开发子集与阶段性完整报告分别标注。

自定义用例保留两个层次：现有 13 题继续作为基础回归；新增产品场景只补真实缺口，不为凑数量扩建 10–20 道大题。取消、预算、权限、验收次数等优先用模拟模型验证；需要模型理解和长期遵循的场景再按需抽检。自定义结果不计入公开基准得分。

## 一致性与配置

- 两边使用同一个模型服务端点、账号层级、传输协议口径和显式采样/思考设置；不把 NVIDIA 托管服务、第三方中转与官方 API 当成相同条件。
- 记录请求的模型 ID、服务报告的 ID、核查到的后端版本信息及核查日期。`deepseek-flash` 是滚动别名；无法锁定实际版本时注明限制，尽量在同一时间段交错运行基线与候选。后端发生变化或无法确认历史条件时，重新跑少量旧版本任务校准，必要时重建基线。
- 固定任务和判定器、镜像、硬件资源、网络规则、时限、并发、模型上下文与单次输出上限；尽可能同一时段运行，记录缓存命中与价格口径。
- 任务时限与资源以冻结版本的官方配置为起点。预算受限时可以另建受限配置，但报告必须明确是受限实验。
- 初版共同约束为任务时限、环境资源和模型单次输出上限。Agent 内部迭代策略各自保留并记录；在两边都能实施相同累计额度前，不仅给 MossCode 设较紧 `run_budget` 再称“同预算比较”。
- 默认单主 Agent、无用户记忆、无用户全局指令、无第三方 MCP/插件、自定义 Skill 和用户 Hook。保留任务本身的文档与约定。MossCode 使用 `bypassPermissions`，权限能力另做产品回归。
- `pre_finish` 默认关闭，单独设功能对照配置；只有任务合法提供的可见检查才能作为完成前命令，最终隐藏判定内容不得提前送入模型。
- 保留各 Agent 的原生工具和提示词，因为它们正是比较对象；安装与评测适配层不额外增加解题提示，不把参考答案、隐藏测试或历史成功轨迹放进任务环境。
- 遵循任务网络策略，并记录能否联网。发现通过公开网络获取参考解或判定答案的轨迹时，单列完整性问题，不当作能力提升证据。
- 不读取当前工作区的实际凭据文件；运行时通过环境变量提供密钥。产物不包含密钥或原始认证配置。

## 最小实现结构

继续使用两条现有或成熟执行路径，不建立第三套调度器：

```text
现有 13 题/产品回归 → scripts/run_evals.py 或相关 pytest
公开能力评测       → Harbor 原生任务配置 → MossCode 适配器 / Terminus 2
两条路径的结果     → 小型比较脚本 → JSON + Markdown
```

拟新增 `evals/harbor/mosscode_agent.py`：继承锁定 Harbor 版本的 `BaseInstalledAgent`，在任务容器内安装指定提交构建的 MossCode wheel，使用独立的 Agent 环境运行 `moss -p --output-format stream-json`。安装不替换任务项目依赖，也不让 Agent 代码进入被评测项目的源码树。解析停止原因、用量和压缩等事件，填充 Harbor 的 `AgentContext`；具体接口签名在实施时按锁定版本复核。

使用 Harbor 原生 JSON/YAML 配置管理模型、Agent、数据集、任务、重复数和容器。开发任务清单保存为单独的显式列表；解析后的配置与运行结果一并归档。外部参考固定为该 Harbor 版本自带的 Terminus 2，不自行修改其算法。若需要修复适配器或基础设施，记录补丁，并对受影响基线重新验证。

拟新增 `scripts/compare_evals.py`，只读取归一化后的 JSON 和原始结果引用，不启动模型。先检查实验条件是否相容，再生成逐任务对照与成本表。旧提交即使没有某个新事件，也应能正常收集结果，并把该事件指标标为未报告而不是 0。

结果默认存入已经忽略的 `.test-artifacts/evals/<实验系列>/<运行标识>/`。保留 Harbor 原生结果、任务日志和 Agent 输出作为可定位证据，原始用量只在一层计数；归一化报告引用它们，不重复创建一套完整会话存储。脱敏后的汇总可供用户选择公开，完整轨迹不自动发布。

Harbor 只作为评测环境依赖，锁定经过验证的版本；不加入 MossCode 运行时依赖。第一版不改 Agent Loop、权限判断或生产模型协议。

## 最小结果记录与指标

| 范围 | 必须记录 |
| --- | --- |
| 实验标识 | 实验系列、运行标识、任务清单及摘要、任务集/判定器/镜像版本、Harbor 与适配器版本 |
| Agent 与模型 | Agent 类型与代码 SHA/wheel 摘要、配置摘要、请求及报告的模型 ID、后端版本可知性、服务提供方、采样与思考设置 |
| 执行条件 | 时间、平台、时限与资源、并发、重试策略、功能开关 |
| 单次结果 | 任务 ID、重复编号、官方 reward/通过判定、运行停止原因、错误类别、原始产物路径 |
| 消耗 | 总请求、输入/输出/缓存 Token、辅助调用用量、任务耗时、费用估计及其价格快照、未知用量标记 |
| 诊断 | 能获得时记录工具错误、压缩次数、后台化、重复调用停止、完成前验收及失败次数；未报告为缺失值 |

主指标为官方定义的任务结果和完整覆盖率。多次运行报告每题成功次数及按任务等权汇总的单次成功率；不把“试三次有一次通过”冒充单次通过率。开发小样本优先看逐题胜负与轨迹，不凭几个百分点判断显著提升。

配套报告总费用、全体任务耗时中位数/P90，以及两版本都成功的任务上的成本/耗时变化。总支出除以成功数可作为批次效率指标，但必须同时展示失败任务开销，零成功时不可计算；不只统计成功样本来隐藏失败成本。

停止原因与任务结果分开：`completed` 只表示 Agent 正常结束，不能证明解题正确；反过来，也不把所有正常结束但判定失败都命名为“谎报完成”，因为模型可能明确报告无法解决。初版记录“正常结束但未通过判定”的数量，真实完成声称由失败轨迹人工抽查。

模型服务、环境、Agent 和判定器错误分别列出。保留原始 reward 和 Harbor 错误语义，另报告包含服务失败的端到端完成情况；不通过删除失败样本抬高分数。取消、缺失、未执行的计划项标记不完整；部分覆盖不得称为全量成绩。重试与新增独立尝试要区分，所有已产生费用均计入。

CLI 当前可能在部分请求缺价格时仍返回已知请求费用的小计；评测必须根据逐次用量及完整性核算，或将总费用标为未知，不能把这个字段无条件当作完整账单。报表区分 Token 原始量、统一价格快照重算的估计费用和有来源的实际账单。不同计费时段会影响费用比较，不把价格波动误判为框架优化。

## 基线复用与成本控制

- 第一次只运行接入试跑，随后保存固定开发子集上的 MossCode 锚点和 Terminus 2 参考。当前 `fccece2` 只是候选锚点提交，尚没有该公开任务集上的实测成绩。
- 以后优先只跑候选版本，读取条件相容的历史基线；对变化任务与少量未变化任务补跑旧版本，用于调查随机波动或模型漂移。需要对外声称提升时，使用预先确定的完整配对计划，并在必要时于同期重跑旧版本。
- 外部参考不随每个功能反复重跑；模型实际版本、任务版本、Harbor/Terminus 2、判定器、资源或关键设置变更时再重建或复核。
- 默认不在普通 PR 和每次发版中自动启动付费完整评测。先提供显式选择运行范围的入口；后续是否接入标签/发布工作流再单独决定。
- 付费运行前展示 Agent 数、任务数、重复数、计划总次数及基于试跑的费用估计。总次数为 `Agent 数 × 任务数 × 重复数`，另显示可能的重试，不能漏算外部参考和旧版本。
- 每次运行显式声明预算、并发和时限。初始并发建议为 1；完成试跑后再按实际费用分布决定完整运行预算，不把此前的假设 Token 数当作 Terminal-Bench 实测。
- 在尝试之间检查已用额度与下一次预计开销，额度不足时停止新派发并保留结果。模型请求与在途任务仍可能继续产生费用；请求/Token 阈值、超时和估算美元预算都不承诺精确账单硬封顶。未知用量时停止自动追加，要求先核对。
- 恢复评测复用已结束的尝试；重新运行失败项生成新记录，不覆盖旧失败。完成任务不能因重启而重复计费。

## 实施顺序与验收

1. 锁定 Harbor 与任务版本，写 MossCode 安装式适配器；通过模拟 CLI 结果验证退出状态、逐次用量、缺失数据和错误映射，不请求模型。
2. 保存共同配置及任务清单；比较脚本能拒绝混淆不同数据集、模型条件和资源的报告，能够明确展示不完整运行。手工检查报告足以覆盖纯展示变化，不添加格式快照测试。
3. 在后续明确启动评测时，先用一个任务验证容器安装及判定路径，再执行 3–5 题双 Agent 试跑；核对工具调用、流式输出、思考设置、时限、费用和判定内容隔离。这里没有预先认定某个 API/模型配置已经兼容。
4. 冻结 12 题开发清单，建立 MossCode 锚点和 Terminus 2 参考；保存可复核的原始结果，再开始版本比较。
5. 有明确的大版本或对外报告需求、且预算经过试跑估算后，再扩展完整任务集和重复次数。

必要验收包括：旧版与新版运行同一任务后分别保留结果；不同配置不被错误比较；服务错误/超时/缺失用量不被当作通过或零成本；恢复不重跑已经完成的尝试；隐藏判定未提前暴露；无配置凭据进入日志或汇总。后续只为新增行为增加直接相关测试，不重复实现 Harbor 已有的调度与容器测试。

本规格不把本机支持所有任务、API 兼容性、模型效果、真实费用或远程 CI 标为已验证。设计交付后尚需实现与受控试跑。
