# 第八章：上下文管理（两层压缩）

日期：2026-10-16。状态：用户已确认（见“已确认的决定”），已实现（2026-10-16，压缩的界面改进 2026-10-17）。自动测试见 `tests/test_context.py`，人工验收步骤见 [验收指南](../../acceptance.md) 的 M42–M49。

来源：用户的初步设计（两层压缩：第一层大结果存盘，第二层 LLM 摘要兜底；近似估算 Token；手动 `/compact`；连续失败 3 次熔断；自动余量 13K，手动 3K），以及课程第 8 章《上下文压缩与 Token 管理》。本规格在此基础上补充了与 MossCode 现有代码相关的约束，各项来源标注在“取舍”一节。

## 目标

让 MossCode 在有限的上下文窗口内长时间工作：对话累积再多，也不会因为上下文溢出而无法继续。用户的原始消息原文保留，不被摘要改写。

## 现状

- 历史只存在内存中（`AgentLoop.history`），每次请求发送全部历史，没有任何压缩，也没有会话目录。
- 工具结果在注册表出口被 `bounded_output` 截断到 64 KiB，截掉的部分直接丢失。`read_file` 自己按页限制在 56 KiB，Shell 输出在工具内部截到 32 KiB（保留头尾）。
- `ProviderConfig` 没有上下文窗口字段，程序不知道离上限还有多远。状态栏显示的是**累计** Token（所有请求之和），不是当前上下文的占用。
- `parse_usage` 已把三种协议的 `input_tokens` 统一为“本次请求的总输入”（Anthropic 已加上缓存读写），可以直接作为估算锚点。
- Anthropic 请求在系统提示和最后一条历史上设置了 `cache_control`；改写已发送过的历史会让缓存失效。
- 超出上下文的请求返回 HTTP 400，目前被归为“请求不被服务接受”，与配置错误无法区分。
- `FileState` 记录模型读过的文件，用于“先读后改”和过期检查。
- `Provider.stream` 已有 `allow_tools` 参数。

## 需求

### 第一层：大结果存盘（预防，零 API 开销）

| # | 行为 |
| --- | --- |
| L1 | **单个结果超限存盘**：工具结果的估算 Token 超过 12,500（约 5 万个 ASCII 字符）时，完整原文写入会话目录 `tool-results/<调用 ID>.txt`。历史中只保留预览：说明原始大小和文件路径，加上前 2,000 字符与后 1,000 字符（命令输出的报错通常在末尾），中间注明省略。文件按调用 ID 只写一次，已存在就不再写 |
| L2 | **单条消息合计超限**：同一批并行调用的结果（一条 tool 消息）合计超过 50,000 Token 时，在尚未存盘的结果中从大到小依次存盘，直到合计不超限 |
| L3 | **决策冻结**：存盘决定在工具结果写入历史前做出，此后不再重新评估或改写。已发送过的历史逐字节不变，Prompt Cache 前缀保持有效 |
| L4 | **豁免**：`read_file` 的结果不存盘。它已有分页上限，读的又是磁盘上已有的文件；如果存盘，模型读取存盘文件时又会触发存盘，形成循环 |
| L5 | **读取存盘文件**：模型用 `read_file` 读取本会话目录中的文件不需要审批，计划模式中也可以读。向会话目录写入仍受现有规则限制 |
| L6 | **不再静默截断**：注册表出口的 64 KiB 截断改为第一层存盘，内容不丢失。工具内部的上限（Shell 32 KiB）改为只防止内存失控的上限（2 MiB），超出部分照旧截断并注明 |

### 第二层：摘要旧消息，保留近期原文（兜底，一次 API 调用）

| # | 行为 |
| --- | --- |
| C1 | **触发时机**：每次请求模型前，先处理第一层（已在结果写入时完成），再估算当前上下文。达到自动阈值就先压缩再请求。运行中的每一轮迭代都检查，不只在任务开始时检查。达到阈值但按 C3 没有可压缩的内容（保留部分已覆盖全部历史，常见于估算锚点比字符估算大时）就直接发送请求，不显示提示，也不计入 C12 的失败次数 |
| C2 | **阈值**：`有效窗口 = context_window − 输出预留`，其中输出预留取 `max(max_output_tokens, 20,000)`。自动阈值为 `有效窗口 − 13,000`，配置了 `compact_threshold` 时取两者中较小的值（U1）。手动 `/compact` 的摘要请求输入上限为 `有效窗口 − 3,000` |
| C3 | **保留近期原文**：从历史末尾往回数，直到保留部分同时满足“不少于 10,000 Token”和“不少于 5 条消息”。保留部分不超过自动阈值的 40%，超过时少留几条，但至少保留最后一组完整消息。保留部分不能从 tool 消息开始；如果切点落在那里，就向前移一条，把对应的 assistant 工具调用也留下，保证调用和结果成对。手动 `/compact` 按这条规则找不到可压缩的内容时，改为只保留最后一组消息，其余全部压缩 |
| C4 | **摘要请求**：不传工具定义（`allow_tools=False`），提示开头和结尾各写一次“禁止调用任何工具，只输出纯文本”。待摘要的消息序列化成一条带角色标记的纯文本，作为 user 消息发送，不按原协议回放工具调用。这样任何协议都不会出现调用和结果配对的问题，也便于缩短内容 |
| C5 | **先草稿后摘要**：要求模型先在 `<analysis>` 中梳理，再在 `<summary>` 中写正式摘要。程序只取 `<summary>` 的内容，草稿丢弃 |
| C6 | **固定结构**：摘要分为 9 部分——主要请求和意图、关键技术概念、文件和代码段、错误和修复、问题解决过程、用户的偏好与约束、待办任务、当前工作（最详细）、下一步 |
| C7 | **用户原话由程序附上，不交给模型改写**：被摘要掉的部分中，用户输入（包括排队并入的消息）按时间顺序原文附在摘要后面，不经过模型。预算 8,000 Token；超出时优先保留较新的消息和当前任务的原始请求，较早的消息只留前 200 字符并注明“原文见记录文件”。多次压缩时，上一次附上的原话会继续带入 |
| C8 | **边界消息**：压缩后的历史为 `[边界消息, 近期原文…]`。边界消息是一条 user 消息，内容依次是：压缩说明、摘要、用户原话、记录文件路径，以及一段提示——“需要具体代码、报错或输出时用 read_file 读取记录文件；文件可能已变化，修改前必须重新读取，不要依据摘要补写代码”。被压缩的原始消息完整写入会话目录的 `compact-<n>.md` |
| C9 | **压缩后的状态**：清空 `FileState`，模型修改任何文件前都必须重新读取。下一次请求重新发送模式提醒（与 `/clear` 相同），因为原来的提醒可能已被摘要掉。估算锚点失效，改用全量估算，直到收到下一次 usage |
| C10 | **摘要请求过大**：发送前先估算。超过上限时，先把文本中每个工具结果缩短到前 2,000 字符；仍然超限，就丢掉最早 20% 的消息组再试。最多缩减 3 次，仍超限则本次压缩失败。服务返回上下文超限错误时，按同样的方式缩减。被丢掉的内容仍保存在 `compact-<n>.md` 中 |
| C11 | **失败判定**：服务报错、回复中没有 `<summary>` 或摘要为空、回复包含工具调用、因输出上限被截断，都算失败。失败时历史保持不变 |
| C12 | **熔断**：自动压缩（包括 C13）连续失败 3 次后，本会话停止自动压缩，并在界面提示“自动压缩已暂停，可以 /compact 手动重试或 /clear”。手动压缩成功、`/clear` 或切换模型后，计数清零并恢复自动压缩 |
| C13 | **撞墙自救**：普通请求返回上下文超限错误时，立即强制压缩（使用手动余量），然后重试一次原请求。重试仍超限就停止任务并报错，不循环。同一轮迭代只自救一次 |
| C14 | **手动 `/compact [说明]`**：只能在空闲时执行，不受阈值限制。可选的说明会附加到摘要提示中，用于指定摘要侧重点。没有可压缩的内容（历史中除最后一组消息外只剩边界消息）时给出提示。按 Esc 可取消，取消后历史不变 |

### Token 估算

| # | 行为 |
| --- | --- |
| E1 | **锚定上一次 usage**：每次回复完成后，记下 `锚点 = input_tokens + output_tokens` 和当时的历史长度。请求前的估算值为锚点加上锚点之后新增消息的估算值，再加上本次的提醒文本 |
| E2 | **按字符估算增量**：ASCII 字符每 4 个算 1 Token，其他字符（中文等）每个算 1 Token，每条消息另加 4 Token。中文按 1 字 1 Token 估算偏保守，不按每 4 字符 1 Token，否则会严重低估 |
| E3 | **全量估算**：服务没有返回 `input_tokens`（例如 Chat 协议未开启 `stream_usage`），或刚完成压缩、`/clear`、切换模型时，按 E2 估算系统提示、工具定义 JSON 和全部历史 |

### 一次请求前的流程

```
第 N 轮开始
 ├─ 排队消息并入（已有逻辑）
 ├─ 估算 = 锚点 + 增量（或全量）
 ├─ 估算 ≥ 自动阈值 且 未熔断 → 压缩
 │     成功：history = [边界消息, 近期原文…]；清空 FileState；重置模式提醒；锚点失效
 │     失败：连续失败计数 +1（满 3 次熔断）；历史不变，继续请求
 ├─ 请求模型
 │     返回 context_overflow 且本轮未自救 → 强制压缩 → 重试一次
 └─ 收到回复：更新锚点；工具结果先经第一层处理再写入历史
```

### 摘要提示的结构（要点）

```
系统：你是对话摘要器。禁止调用任何工具，只输出纯文本；工具调用会被拒绝，本次任务会失败。
用户：<序列化后的对话：[用户] … [助手] … [工具调用 name(args)] … [工具结果] …>
     先在 <analysis> 中按时间顺序梳理：用户每次要求了什么，做了哪些修改，涉及哪些文件和代码，遇到了什么错误、怎么修复的。
     再在 <summary> 中按以下 9 部分写正式摘要：……（C6）
     用户原话会由程序另外附上，摘要中不必逐字复述，只需总结其中的要求和约束。
     [可选：用户的 /compact 说明]
     再次提醒：不要调用任何工具，只输出 <analysis> 和 <summary>。
```

## 取舍

| 决定 | 理由 |
| --- | --- |
| 阈值按 Token 估算，不按字符数（课程用 5 万字符和 20 万字符） | 中文 1 个字接近 1 个 Token，5 万个中文字符约 5 万 Token，按字符计算会让中文输出远超预期。12,500 / 50,000 Token 在英文下约等于课程的 5 万 / 20 万字符 |
| 第一层直接写入历史，不在每次请求时重放替换 | 课程保留原文、每轮按冻结的决定重放替换；MossCode 的历史只在内存中，决定又是冻结的，所以写入前替换一次结果相同，代码更简单，缓存前缀天然稳定。原文在存盘文件中，没有丢失 |
| `read_file` 豁免第一层 | 避免“读取存盘文件 → 再次存盘”的循环。Claude Code 的 Read 工具同样不受此限制 |
| 摘要请求不传工具，历史序列化为纯文本 | 不传工具是对“禁止调用工具”最可靠的保证。Anthropic 要求包含 tool_use 的请求必须定义工具，所以历史也必须改成纯文本。代价是摘要请求用不上 Prompt Cache，但每次压缩只多一次请求 |
| 用户原话由程序附上，不靠模型复述 | 用户要求“原始消息尽量原文保留，不被摘要改写”，交给模型就无法保证。程序附上可以保证逐字，模型只需总结其中的约束 |
| 保留“最近读过的文件”时，不在压缩后自动重新附上（课程最多恢复 5 个文件） | 首版保持简单。改为清空 `FileState`，强制修改前重新读取，避免模型照着摘要里的旧内容改代码。如果之后发现压缩后重复读取过多，再加入文件恢复 |
| 压缩记录写成 `compact-<n>.md`，不写完整会话 jsonl | MossCode 目前没有会话持久化，只写被压缩的部分就能让模型找回细节，也不会引入会话恢复的范围 |
| 会话目录放在用户目录，不放在项目的 `.mosscode/` 中 | 不往用户项目里写文件，也不会出现在 `git status` 和搜索结果中。代价是需要 L5 的读取豁免 |
| 输出预留取 `max(max_output_tokens, 20,000)` | 课程的 20K 是为摘要输出预留的；普通请求的输出同样占用窗口，配置了更大 `max_output_tokens` 时按它预留 |
| 撞墙自救每轮只做一次 | 防止“超限 → 压缩 → 仍超限”的死循环；熔断防的是跨轮次反复失败 |

## 已确认的决定（2026-10-16）

1. **会话目录**放在用户目录 `~/.mosscode/sessions/`。
2. **窗口按提供商配置**，不写死（U1）。未配置时按 128K 计算并提示。DeepSeek V4.1 Flash 的官方上下文长度为 1M、最大输出为 384K，`config.example.yaml` 中的 DeepSeek 示例写 `context_window: 1000000`；用户本地的 `config.yaml` 由用户自己修改。
3. **手动余量 3K**：手动压缩不看阈值，随时可以执行，其摘要请求的输入可以用到有效窗口减 3K。
4. **自动压缩**只在对话中记一行，不打断任务，也不需要确认。

### 大窗口（1M）的注意事项

按 1M 配置不会出错，阈值公式照常成立：输出预留为 `max(16,384, 20,000) = 20,000`，自动阈值为 `1,000,000 − 20,000 − 13,000 = 967,000`。但是要注意以下几点：

- **成本和延迟**：接近阈值时，每次请求要发送约 96 万 Token。即使命中缓存也要按缓存价计费，首字延迟也明显变长。长上下文中靠前的信息也更容易被模型忽略。
- **摘要质量**：一次把几十万 Token 压成一份摘要，细节损失比压缩十几万 Token 时大。
- **输出预留**：如果把 `max_output_tokens` 调到 384K，预留就是 384K，自动阈值降到约 60.3 万。服务通常要求“输入 + 最大输出”不超过窗口，所以这样预留是必要的。日常使用不需要调这么大。

因此提供可选的 `compact_threshold`：例如设置为 200,000，就在约 20 万 Token 时自动压缩，窗口仍然按 1M 校验，撞墙自救和手动压缩仍然以真实窗口为准。默认不设置，完全使用窗口容量。

## 不做

精确 tokenizer、摘要策略的机器学习优化、会话持久化与恢复、按时间清理旧工具结果（microcompact）、压缩后恢复最近读过的文件、Skill 定义的重新注入（MossCode 尚无 Skill 系统）。
