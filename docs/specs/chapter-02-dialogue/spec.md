# 第二章：对话模块

## 范围

用 Python 实现终端交互式流式对话，支持 Anthropic Claude 与 OpenAI 两种后端、YAML 配置、多轮历史和选定 Claude 模型的 thinking。

本章每次用户发送只发起一次模型请求。正常的用户输入交互可以持续进行，但不包含模型自行调用工具并继续请求的 Agent Loop。

工具注册、工具 schema、工具调用事件、文件操作工具和执行器属于第三章；自主反馈循环属于第四章。本章不提前实现这些模块或为它们建立空框架。

## 功能与验收

| 功能 | 可观察的验收结果 |
|------|------------------|
| 配置选择 | --provider 优先，其次显式 default_provider，均直接进入；未指定时单项直进、多项用方向键列表选择，Enter 确认；配置错误在请求前提示 |
| 实时输出 | 第一段正文到达即显示，随后逐段更新，不等待完整响应 |
| 多轮对话 | 第二次请求包含此前已完成的 user/assistant 消息 |
| thinking | 服务提供思考片段时展示过程与实时计时；正文开始输出后收起过程，只留思考用时；取消后也收起；不虚构没有收到的思考，协议内容和签名仍保留在完成的模型历史中 |
| 取消 | Esc 或 Ctrl+C 取消正在生成的回复；资源关闭后可再次输入 |
| 失败处理 | 认证、网络、限流和不完整响应有明确提示；不污染已完成历史 |
| 状态展示 | 生成时显示当前阶段与耗时，完成后底部恢复就绪，耗时保留在消息下方，避免重复状态和未知用量挤占界面；配置名称只在启动区显示一次，显示 name 而不显示 API model |
| 回复渲染 | 生成时显示纯文本增量，完成后以 Markdown 展示正文 |
| 对话记录 | 按用户提供的 Claude Code 截图排版，❯ 与问题同行、● 与回复同行，不重复角色标题；每轮保留耗时。真实内联界面将稳定的启动信息、用户消息、完成回复、工具结果和本地命令结果按顺序写入终端原生滚动历史，实时区仅保留未完成内容和输入控制。关闭鼠标报告，滚轮由终端处理，可查看同一终端此前的启动记录；移除应用内部历史跳转。模型消息仍完整保存在内存，不压缩、不做会话持久化 |
| 简洁界面 | 用户提供的机器人 SVG 适配为单色字符图标，左侧图标、右侧版本 / name / 工作目录三行信息；上下横线输入区、纯文本状态；不挂载 Header / Footer，不提供默认命令面板或可点击退出入口 |
| 内联显示 | 在原终端内容下方显示，Windows 不切换备用屏幕、不清空启动前内容；退出后保留当前可见输出，恢复控制台输入与输出模式 |
| 终端背景 | 所有主题始终使用终端默认背景，主题仅改变文字、图标和高亮颜色；Markdown、菜单和输入区不铺独立底色，字体和字号由终端决定 |
| 本地界面命令 | /help 展示命令与按键，/theme 用方向键与 Enter 选择主题，/exit 退出；命令及结果显示在界面记录中，不调用模型、不进入模型对话历史 |
| 命令提示与补全 | 输入 / 展示命令及右侧中文解释，按前缀筛选；选中命令和说明用蓝色加粗文字显示；↑ / ↓ 选择，Tab 补全命令或主题参数，Esc 收起并保留输入，编辑后可恢复，包括重输相同的 /；Enter 先补全不完整命令，再执行完整命令；窄屏候选可滚动且输入区可见 |

首版会话只保存在内存；退出后不恢复。Provider 在启动时选择，更换 Provider 开启新会话。

启动选择列表仅展示 name，仅在没有显式 Provider 和默认配置、且有多项配置时显示，初始选中第一项。确认前不创建客户端、不发请求，退出列表直接结束程序。无界面 `--prompt` 模式使用显式 Provider、默认配置或第一项，不显示选择界面。

这与 MewCode 第二章 Python 规格的 F2（多配置启动选择）一致；该规格在排除项中明确将会话内切换 Provider / model 和 `/model` 等可扩展命令系统留到后续。这里将课程内容作为范围参考，不引入完整产品的登录、在线注册、模型发现或热切换功能。

本次用户明确要求参考 Claude Code 的终端布局，并通过斜杠命令提供帮助和主题查看，因此增加固定的本地界面命令。它们不包含可扩展注册、插件命令或模型切换；第十章的完整命令框架仍留待后续。当前仅保留一种正常亮度的文字主题，辅助信息不淡化，Logo 为浅绿色；主题面板显示在输入框下方，保留原界面和对话。

取消或失败的部分回复保留在界面并注明状态；该轮 user 和未完成 assistant 不作为完成对话提交到下一轮上下文。用户可修改或重新发送本轮问题。

## 最小实现划分

- 配置：解析 YAML，验证协议与必要参数；`api_key_env` 填环境变量名称，`api_key` 填直接使用的密钥，二选一。误把密钥填入环境变量名称时提示两种字段的区别，不回显误填值。
- 消息与事件：规范消息表达正文和必要 thinking 数据，流事件限于正文、thinking、用量及结束信息；Provider 专属数据留在适配边界。
- Provider：协议序列化、单次流式请求与流资源关闭；底层使用官方异步 SDK，上层使用项目定义的消息和事件。
- 对话服务：维护唯一的已完成历史；一轮请求成功后提交一对消息，失败或取消时回退本轮，拒绝同时发起多个会话请求。
- TUI：采用 Textual 的局部刷新机制，包含品牌启动信息、自适应对话区、状态行和横线输入区；消费流事件、发送取消及处理固定本地界面命令，不构建厂商请求。

本章不需要 Agent Core、会话树、上下文压缩、事件持久化、插件系统或额外 Agent 框架。对话服务可被无界面脚本调用，便于测试。

## 协议与端点：通过配置选择

支持官方 API 与第三方中转／兼容服务，不设置供应商或模型白名单。`protocol` 决定适配器，`base_url` 决定请求端点，`model` 使用服务实际接受的名称。

本章实现 Anthropic Messages、OpenAI Responses 与 OpenAI Chat Completions 三种协议。兼容端点按实际支持的协议选择；不要求用户在开发前选定具体服务。

thinking 通过可选配置表达关闭、自适应或手动预算，不按模型名称推断能力；服务不支持该组合时明确提示请求失败。自定义认证支持 API key 与 Anthropic bearer token。

## 实现与验证顺序

1. 建立包、配置与消息结构。
2. 实现三种协议的单次流式适配。
3. 实现对话历史提交、取消与失败处理。
4. 接入 TUI，共用对话服务。
5. 用模拟流验证多轮、分块、取消、断流与失败回退，用 Textual 无界面测试验证发送和取消交互。
6. 用户配置凭据后对两个实际服务运行小型真实对话验收；记录模型与接口。未运行的真实 API 验收标记未验证。

本章默认不自动重试请求，避免流式输出后重复发送；错误发生后由用户重新发送。后续有需要再加入明确、有界的重试策略。
