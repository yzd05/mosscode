# 投影式折叠：只在发给模型的版本中把最早的一段对话换成摘要

日期：2026-11-12。状态：**已实现**，“待定问题”均按建议确定（见该节）；用户文档见[上下文管理](../../reference/context.md#再折叠最早的一段对话)。相关文档：[上下文管理](../../reference/context.md)、[压缩到期时先清理较早的工具结果](../tool-result-clearing/spec.md)。

## 结论

- 建议做，但**不照搬 MiniCode 的独立阈值**。折叠只在自动压缩本来就到期的那一刻尝试，排在“只清理工具结果”之后、“全量摘要”之前（Q2）。
- 折叠和现在的摘要的区别有两点：
  - **只折最早的一段，够用就停**。中间较早的对话保留原文，摘要请求的输入也更小。
  - **原始历史不动**。只在发给模型的版本（投影）中把这一段换成一条摘要，`/rewind`、会话记录和恢复都还能看到原文。
- 代价也要说清：折叠释放的空间比全量摘要少，下一次到期来得更早。按下文的估算，长会话中摘要请求的总输入差不多，但缓存整段失效的次数多约一半（见“和现在的摘要比较”）。
- 本机的会话还没有一个接近过自动阈值（见[清理规格](../tool-result-clearing/spec.md)的 F8），所以收益目前没有本机数据证明。

## 已确认的事实

| # | 事实 | 来源 |
|---|------|------|
| F1 | MiniCode 在占用 75% 时折叠：找一段可以折叠的连续历史，不拆开未闭合的工具调用组，让模型写成摘要，只在发给模型的版本中替换；每次最多折叠 2 段，连续失败 3 次后关闭。它在 85% 时另有全量摘要 | `context-collapse.ts`、`constants.ts`；整理在 `docs/research/minicode-comparison.md`（本地笔记，未提交） |
| F2 | MiniCode 不用提示缓存，随时改历史中段都没有代价；MossCode 的三种协议都按前缀缓存，第一个被改动的位置之后全部不命中 | [清理规格](../tool-result-clearing/spec.md) F7 |
| F3 | 每次请求的消息由 `deepcopy(self.history) + fresh` 构成，投影可以只在这里生效，不改 `self.history` | `agent.py` `run`（约 566 行） |
| F4 | 现在的自动压缩只在请求前估算达到自动阈值时触发，先试“只清理工具结果”（降到阈值 50% 以下才算够），不够再摘要；摘要直接替换 `self.history` 为“边界消息 + 近期原文” | `agent.py` `_compact`、`_clear` |
| F5 | 摘要保留的近期部分由 `cut_point` 决定：不少于 10,000 Token 且不少于 5 条消息，不超过自动阈值的 40%，不以工具结果开头 | `compaction.py` `cut_point` |
| F6 | 摘要之后 `/rewind` 列不出被压缩的消息，恢复会话也从边界消息开始 | [会话存档与恢复](../../reference/sessions.md) |
| F7 | 每条消息有 `id`；会话记录是只追加的 JSONL，已有 `message`、`compact`、`clear`、`rewind` 等记录类型，不认识的类型恢复时跳过 | `messages.py`、`session.py` `load_session` |
| F8 | 用量锚点按消息条数记录（`meter.record(usage, len(self.history))`），压缩和清理之后 `meter.invalidate()` | `agent.py`、`context.py` `ContextMeter` |

## 为什么不用独立的 75% 阈值

在压缩到期之前单独折叠一次，相当于多一次“改写前缀”：折叠那一刻缓存整段失效，之后到 85% 摘要时又失效一次。这和[清理规格](../tool-result-clearing/spec.md)中不做“常驻清理”的理由相同。所以折叠和清理一样，只在本来就要改写前缀的时刻尝试。

## 和现在的摘要比较

以 128K 窗口、自动阈值 T ≈ 95,000 为例，假设历史均匀增长：

| | 现在：全量摘要 | 折叠 |
|---|---|---|
| 这一次处理多少 | `cut_point` 之前的全部，约 0.6T | 从最早的未折叠消息开始，折到估算降到 0.6T 为止，约 0.4T |
| 之后的上下文 | 摘要加近期原文，约 0.4T | 已有的折叠摘要、中间的原文、近期原文，约 0.6T |
| 多久再到期 | 再增长约 0.6T | 再增长约 0.4T，频率约 1.5 倍 |
| 缓存 | 下一次请求全部不命中 | 从这一段的开头起不命中；第二次折叠时，第一段的摘要和它之前的部分仍然命中 |
| 原文 | 较早的部分都只剩摘要 | 只有被折叠的那段只剩摘要；原始历史仍在，`/rewind` 可以回到其中 |

长会话中两者摘要请求的总输入大致相当（次数多、每次小）；折叠多出来的是失效次数，换来的是更多原文留在上下文中，以及可回退的完整历史。

## 设计要点

- `compaction.py` 增加 `collapse_range(history, collapses, cut, estimate, target)`，返回要折叠的 `[start, end)` 或 `None`；`project(history, collapses)` 返回投影；`collapse_segment(...)` 发摘要请求并写记录文件，复用 `compact_history` 的序列化、缩减和 `<summary>` 解析。
- `agent.py`：`self.collapses` 保存 `(首条 id, 末条 id, 摘要消息)`；`_compact` 在 `_clear` 之后、`compact_history` 之前尝试折叠。构造请求、`estimate()` 和全量摘要改用 `project(self.history, self.collapses)`。
- 投影按消息 `id` 定位，而不是下标：清理工具结果会替换消息对象，`/rewind` 会截短历史，用 `id` 不受这两者影响。
- 用量锚点记录投影的长度；折叠、撤销折叠都让锚点失效。

## 待定问题（已确定）

六个问题均按“建议”一列确定。实现时补充的一点：选择范围时，摘要正文按 2,000 Token 估计，附上的用户原话按实际大小计入，否则用户消息很长时折叠后会超出 60%。范围只在用户输入的消息之前结束，所以整段历史只有一轮时不折叠。

| # | 问题 | 选项 | 建议 |
|---|------|------|------|
| Q1 | 现在做，还是等有长会话的数据再做？ | 现在做 / 先加统计（记录每次压缩前后的大小和间隔），有数据再决定 | 现在做。“原始历史不动、`/rewind` 能回到被折叠的消息”不依赖数据就有价值 |
| Q2 | 什么时候触发？ | 和自动压缩同一时刻 / 像 MiniCode 一样单独一个更低的阈值 | 同一时刻。单独的阈值每次多一次整段缓存失效 |
| Q3 | 折叠到多少为止？ | 自动阈值的 60% / 50%（与清理相同）/ 可配置 | 60%。折得越多越接近全量摘要；比清理的 50% 高，因为折叠要发请求，留出的原文更值 |
| Q4 | 投影中最多保留几段折叠摘要？ | 2 段（MiniCode）/ 不限，每次把旧摘要和新的一段一起重新摘要 | 2 段，第三次直接全量摘要。重新摘要旧摘要会层层失真 |
| Q5 | 现在的全量摘要要不要也改成投影（原始历史不动、`/rewind` 能回到摘要之前）？ | 这次只做折叠 / 一起改 | 这次只做折叠。全量摘要改投影会让内存中的历史无限增长，需要另外设计上限 |
| Q6 | 折叠是否默认开启？ | 默认开启 / 默认关闭，先作为可选项 | 默认开启，`context_collapse: false` 关闭；失败时自动退回全量摘要，最坏情况与现在相同 |

## 测试计划

- `tests/test_context.py`：范围选择（组边界、不越过 `cut_point`、已有 2 段时不折叠）、投影的逐字节前缀、三条路径的先后、失败退回与熔断。
- `tests/test_sessions.py`：`collapse` 记录的写入与恢复；旧记录被跳过时的恢复。
- `tests/test_checkpoints.py`：回退到被折叠范围之内和之后。
- `tests/test_tui.py`、`tests/test_cli_product.py`：对话中的结果行、`-p` 的 stderr 与 stream-json 事件。

## 不做的

- 不单独设更低的触发阈值（Q2）。
- 不在折叠时清理工具结果以外的内容，也不做 MiniCode 的确定性裁剪（不调用模型、直接删中段）：删掉的内容模型无从得知，`/rewind` 之外也找不回来。
