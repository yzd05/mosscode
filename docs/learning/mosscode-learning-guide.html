MOSSCODE · LEARNING GUIDE

从一次请求，到上下文压缩

MossCode 是一个参考 Claude Code 与 Pi 的轻量终端编程 Agent。本页按“数据怎么流动”的顺序讲解每个子系统的具体实现，引用的代码均为当前源码的节选（标注“简化”的去掉了与主题无关的分支）。最后一大节专门讲第八章的两层上下文管理，以及人工验收中发现并修复的问题。

01

全局地图

先记住分层：界面只消费事件，Agent Loop 只做决策，工具层只负责执行和边界检查。

cli.py命令行入口：加载配置、选择 Provider、清理过期会话目录；进入 TUI，或以 -p 运行一个任务（text / json / stream-json 输出）。
tui.pyTextual 界面（内联模式）：输入、排队、审批面板、状态栏、工具行、压缩进度；把完成的内容写入终端原生滚动历史。
conversation.py对外接口：启动时加载 AGENTS.md、git 快照和 MCP；提供 reply()、ask()、compact()、clear()、set_provider()。TUI 与 -p 共用。
agent.pyAgent Loop：组装请求、流式收集、执行工具、排队消息并入、停止条件、压缩时机与超限自救。
providers.py三种协议适配（Anthropic Messages / OpenAI Responses / Chat Completions）、首事件前重试、缓存断点、用量归一。
prompts.py七个固定模块的稳定提示、工具清单、<environment> 与 <system-reminder> 补充、项目指令。
tools/注册表与执行边界（base.py）、分批并发（execution.py）、文件 / 搜索 / 命令 / 计划工具。
permissions.py · security.py四档权限、分层规则、审批请求、只读命令白名单、危险命令分级、项目路径检查。
context · compaction · tool_budget · session第八章：上下文估算与阈值、摘要压缩、大结果存盘、会话目录。

一次任务的完整路径

TUI 输入 Enter→ Conversation.reply(prompt)→ AgentLoop.run：每轮估算 → 可能压缩→ provider.stream：Delta… Completed→ 有工具调用？execute_batch→ registry.execute：校验 → 授权 → 执行 → 存盘判断→ 结果写回历史，下一轮

循环直到模型的完整回复不再请求工具，或遇到停止条件（取消、达到轮数上限、连续未知工具、输出截断、错误）。每一步都向上产出事件（StreamEvent），界面据此绘制；Agent Loop 本身不 import 任何界面代码。

02

数据模型与事件流

所有模块之间只传递 messages.py 中的不可变 dataclass。

类型关键字段要点
Messagerole（user / assistant / tool）、content、tool_calls、tool_results、protocol、native、synthetic通用格式，三种协议各自转换。native 保存只对原模型有效的数据（thinking 签名、加密推理），切换模型时清除。synthetic="compact" 标记压缩产生的边界消息。
ToolCallid、name、arguments（JSON 字符串）参数保持原始字符串，执行时才解析，便于报告 invalid_json。
ToolResultoutput、is_error、code、detailsoutput 发给模型（失败时 model_text() 为“错误 [code]：…”）；details（diff、耗时、退出码、存盘路径）只留在本地给界面和测试。
Usageinput_tokens、output_tokens、缓存读写服务没给的字段是 None，不伪造为 0；界面显示“—”或“≥”。

事件：运行时与界面之间的契约

事件何时产生界面用途
IterationProgress每轮开始状态栏“N/200 轮”
Delta(kind, text)流式片段（正文或 thinking）实时显示，思考计时
Retrying首事件前的临时故障重试状态栏显示原因和等待秒数
ResponseBoundary含工具调用的完整回复已记录封存本段回复，开始工具行
ToolProgress工具 parsing / running / finished工具行、diff、存盘提示
ApprovalRequest需要用户确认输入区下方的审批面板
UserInput排队消息在迭代边界并入在对话中逐条显示
UsageUpdate每次回复完成Token 累计、上下文比例
CompactStarted / Finished / Failed压缩开始、成功、失败进度行原地变为结果；stream-json 的 compact 事件
Completed最终文本回复渲染 Markdown
RunStopped(reason)任务结束completed / max_iterations / max_tokens / unknown_tools / cancelled / error
为什么用事件流而不是回调？

AgentLoop.run() 是一个异步生成器。TUI 和 -p 都只是 async for event in conversation.reply(...)，各自决定怎么显示；测试可以直接收集事件列表断言顺序。取消也自然：界面取消任务，生成器在当前 await 处收到 CancelledError，finally 负责清理。

03

Agent Loop

src/mosscode/agent.py 的 AgentLoop.run() 是整个项目的核心，约 120 行。

agent.py · run()（简化）
for iteration in range(1, self.max_iterations + 1):        # 默认 200
    env = environment(root, permission_mode=..., git=self.git, shell=...)   # 每轮重建：批准计划会改变档位

    if committed and self.pending:                     # 运行中排队的消息，在迭代边界并入

    fresh = [] if committed else [user]                 # 用户消息尚未进入历史

    self.meter.record(final.usage, len(self.history))   # 上下文估算的锚点
    if not calls: yield final; yield RunStopped("completed"); return
    if truncated: 每个调用配一条 output_truncated 结果，continue   # 参数可能被截断，不执行
    async for event in execute_batch(final.message, self.registry, self.history): yield event

几个容易忽略的设计点

用户消息“晚提交”

第一次请求时用户消息放在 fresh 里临时拼接，收到完整回复后才写入历史（committed）。如果第一次请求就失败或被取消，历史里不会留下一条没有回答的用户消息。

工具结果“先占位”

execute_batch 先追加一条空的 tool 消息，每完成一个调用就 save() 一次。取消时 finally 给未执行的调用补上 not_executed，保证每个调用都有结果，协议不会因为调用和结果不成对而拒绝请求。

输出截断的两种处理

纯文本被截断：保留正文，以 max_tokens 停止，提示“继续”。工具调用被截断：JSON 参数可能不完整，一律不执行，以 output_truncated 回传，让模型拆小后重试。

排队消息（steering）

运行中按 Enter 的内容进入 pending，在下一次请求前合并为一条 user 消息。若模型已经给出最终回复，排队内容在任务结束后作为下一个任务发送。

模型协议层

providers.py：一个基类负责重试，三个子类负责协议转换。

protocol工具结果怎么发系统提示与补充输出上限的停止原因
anthropic-messagesuser 消息中的 tool_result 块，失败时 is_error稳定 system 块 + 环境块；模式提醒附在最后一条 user 消息末尾max_tokens
openai-responsesfunction_call_output 项；store=false，回传加密推理instructions + developer 消息incomplete: max_output_tokens
openai-chat-completionsrole: tool 消息system 消息length

三者都被归一为同一个 Completed(message, stop_reason, usage)，stop_reason == "max_tokens" 表示截断。Agent Loop 完全不知道底层是哪种协议。

providers.py · SDKProvider.stream()
async def stream(self, messages, system, tools=(), *, allow_tools=True):
    attempt = 0
    while True:
        produced = False
        try:
            async with aclosing(self._stream(...)) as events:
                async for event in events:
                    produced = True
                    yield event
            return
        except Exception as exc:
            # Only a request that produced nothing is safe to repeat: no text
            # was shown and no tool call can have been executed.
            retry = None if produced or attempt >= self.config.max_retries else _retry_reason(exc)
            if retry is None: raise _safe_error(exc) from None
            delay = _retry_delay(exc, attempt, self.retry_base_delay)
        attempt += 1
        yield Retrying(attempt, self.config.max_retries, delay, retry)
        await asyncio.sleep(delay)

只在首事件前重试

429、529、5xx、超时、断连按 1、2、4、8 秒加抖动退避（遵守 retry-after，最长 60 秒），默认 4 次。已经产生事件后断流不重试：正文可能已显示，重放会重复。SDK 自身重试设为 0，避免叠加。

安全的错误信息

_safe_error 把 SDK 异常转成中文 ProviderError，不回显凭据和请求体。HTTP 400/413 且提到 prompt is too long 等特征时标记 code="context_overflow"，供第八章自救使用。

用量归一

usage.py：Anthropic 的总输入 = 普通输入 + 缓存读 + 缓存写；其他协议直接给总数。DeepSeek 的 prompt_cache_hit_tokens 也能识别。

切换模型

/model 后 set_provider() 去掉历史中的 native 和 protocol，各协议从通用字段重建工具调用；Anthropic 还会合并相邻同角色消息。因此可以在三种协议之间来回切换。

05

系统提示与缓存

prompts.py：把“每次都一样的”和“每次不同的”严格分开，才能命中 Prompt Cache。

稳定前缀（缓存）七个模块：identity 身份 · constraints 系统约束 · mode 任务模式 · execution 动作执行 · tools 工具使用 · tone 语气 · output 文本输出；加“当前可用工具”清单；末尾追加 AGENTS.md（用户级 → 根目录 → 当前目录）。
工具定义（缓存）每个工具的 description 末尾追加 prompt_guidelines。用法规则只出现在这里，不在系统提示中重复（完善阶段 6）。
历史（缓存断点）Anthropic 在最后一个历史块上打断点，多轮工具循环复用已发送的前缀。
本次补充（不缓存）<environment>：日期、系统、shell、工作目录、权限档位、启动时的 git 快照。<system-reminder>：只在模式变化后的第一次请求出现（进入或退出计划模式、压缩后）。
为什么第八章要“冻结”存盘决定？

缓存要求前缀逐字节一致。如果某个工具结果先完整发送、后来又被替换成预览，之后所有请求的前缀都会变，缓存全部失效。所以大结果在写入历史之前就决定是否存盘，之后不再改写（details["budgeted"]）。压缩是唯一会改写前缀的操作，它发生得很少。

06

工具系统

tools/base.py 的 ToolRegistry.execute() 是唯一的执行入口，所有检查都在这里按固定顺序发生。

  1. 查找工具：不存在返回 unknown_tool（Agent Loop 统计连续未知工具的轮数）。
  2. 解析 JSON：失败返回 invalid_json；拒绝 NaN 等非标准常量。
  3. Pydantic 校验：失败时逐条列出字段问题（invalid_arguments），模型能据此修正。
  4. 授权：permissions.authorize()，可能挂起等待用户审批（见第 7 节）。
  5. 执行并限时：asyncio.wait_for(shield(task))；超时或取消时等待任务真正结束，命令会清理整个进程树。
  6. 大小判断：_bound() 调用第八章的 bound_result，过大的结果存盘、只留预览。
  7. 异常归类：FileNotFoundError → not_found、UnicodeError → encoding_error 等，模型收到的始终是中文说明，不是堆栈。
工具只读要点
read_file是“右对齐行号 + Tab + 原文”，默认 2000 行，超长行截断，翻页提示下一个 offset。第八章存盘的豁免对象。
write_file否创建或覆盖；覆盖已有文件须先读。
edit_file否精确替换，默认要求唯一匹配，replace_all 替换全部；CRLF 文件可用 LF 原文匹配。成功只回传摘要，diff 留在 details。
execute_command否*Git Bash / PowerShell / bash；默认超时 120 秒、最大 600 秒；输出在 2 MiB 处保留头尾。*白名单中的只读命令免审批。
glob是遵守 .gitignore，按修改时间倒序，最多 200 项。
grep是优先 ripgrep，没有时用独立 Python 进程；三种输出模式。

先读后改：FileState

tools/files.py · FileState.check()
def check(self, path):
    seen = self._seen.get(self._key(path))         # 读取或自身写入时记录的 (mtime_ns, size)
    if seen is None:
        raise ToolFailure("not_read", "修改已有文件前需要先用 read_file 读取它；文件未修改。")
    if self.stamp(path) != seen:
        raise ToolFailure("stale_read", "文件在上次读取后被修改…请重新读取后再修改。文件未修改。")

这条规则由程序强制，不靠提示词。第八章压缩后会调用 registry.forget_reads() 清空记录：摘要里只有概述，模型手里没有文件原文，必须重新读取才能修改（人工验收 M46 验证的就是这一点）。

相邻只读调用并发

tools/execution.py · partition_calls()
def partition_calls(calls, registry, concurrency=4):
    batch = []
    for index, call in enumerate(calls):
        if registry.is_read_only(call.name):
            batch.append(index)
            if len(batch) == concurrency: yield batch; batch = []
        else:                                    # 有副作用的调用是屏障：单独一批
            if batch: yield batch; batch = []
            yield [index]
    if batch: yield batch

例如 [read, read, edit, grep] 分成 [0,1]、[2]、[3]：写入之后的读取不会被提前。界面可以先显示较快的结果，但写回历史的顺序始终是模型给出的原始顺序。系统提示（阶段 6）明确鼓励模型把互不依赖的只读调用放在同一次回复中。

权限与计划模式

permissions.py 与 security.py。先过硬检查，再按优先级决定 allow / ask / deny。

permissions.py · PermissionPolicy.decide()
def decide(self, operation, *, read_only):
    matched = 最高一层中命中的规则                       # 会话 > 本地 > 项目 > 用户
    if any(rule.action == "deny" for rule in matched): return deny   # 任何档位都生效
    if operation.risk: return ask                       # 高风险命令：每次确认，bypass 也不放行
    if matched: return allow
    if 读取的是本会话目录（存盘结果、压缩记录）: return allow   # 第八章新增
    if operation.outside: return allow if bypass else ask     # 项目外读取
    if bypass or 只读工具 or 只读命令: return allow
    if acceptEdits and 写入/编辑: return allow
    return ask

硬检查（在 decide 之前）

operation() 解析路径：写入和编辑限于项目根目录（解析符号链接和 junction 后按路径段比较）；灾难级命令（删根目录、格式化、fork 炸弹、关机）抛出 SecurityError，任何授权都解除不了；计划模式中非只读工具返回 plan_blocked。

只读命令

read_only_command()：单条简单命令（无管道、串联、重定向、变量、命令替换），在白名单中（git status/diff/log、ls、cat、rg…），不含危险选项，路径参数都在项目内。满足就免审批，计划模式也能运行。

审批与规则

本次 / 本会话 / 永久（写入 .mosscode/permissions.local.yaml）。命令可选“永久允许以 X 开头”，保存为 Bash(X:*) 前缀规则。deny 前缀规则检查复合命令的每一段。无界面模式不等待，返回 approval_required。

计划模式

只提供只读工具、只读命令和 exit_plan_mode。模型提交 Markdown 计划后，用户选择“批准并执行 / 批准并自动接受编辑 / 继续规划”。批准后同一任务的下一轮就能使用全部工具。

边界要说清楚

路径检查是应用层限制，不是系统沙箱：用户批准的命令以当前用户权限运行，正则也无法识别所有混淆写法。MCP Server 也不受本地路径检查约束。

MCP 外部工具

mcp_config.py（配置）与 mcp_client.py（连接、发现、适配）。

配置

用户级 ~/.mosscode/mcp.yaml < .mcp.json（需 import_mcp_json: true）< 项目级 mcp.yaml，同名整项覆盖。env / headers 支持 ${VAR:-默认值}。

09

终端界面

tui.py 是最大的文件（约 1,500 行），核心难点是“内联模式 + 原生滚动历史”。

完成的内容交给终端

界面以内联方式画在命令行下方。_commit_ready_transcript() 从对话区顶部依次检查组件：用户消息、完成的回复、结束的工具行、本地提示都是“就绪”的，写入终端原生滚动历史后从实时界面移除；遇到第一个未完成的组件（正在生成的回复、执行中的工具、压缩进度行）就停止，保证顺序。

宽度变化重绘

终端改变宽度会重新折行旧内容，实时界面的行数随之失效。宽度稳定约 0.2 秒后清屏并按新宽度重新输出全部记录（与 Pi 相同）。

Windows 的 Shift+Enter

开启 VT 输入后 Enter 记录不带修饰键。windows_inline.py 用自己的输入线程读取记录和键盘 Shift 状态，转成 kitty 协议的 \x1b[13;2u 交给 Textual。

状态栏

权限档位标记 · 模型 · 运行阶段/轮次/耗时 · 排队数 · “上下文 约 N%”（达到自动阈值 80% 变琥珀色）· Token 累计 · 缓存读写。压缩期间显示“压缩上下文中 · Ns · Esc 取消”。

实现中踩过的坑：不要覆盖框架的私有名字

第八章最初在 App 上加了属性 self._context 保存上下文比例，结果所有 TUI 测试挂起。原因是 Textual 的 App._context 本身是一个上下文管理器方法，被属性覆盖后事件循环卡死。改名为 _context_share 解决。排查方法：对比基线版本的 tui.py，再在 Textual 源码中搜索同名标识符。

上下文管理（第八章）

规格 chapter-08-context/spec.md，行为说明 reference/context.md。

11.1 要解决的问题

每次请求都包含完整历史。长任务里，读文件、跑测试产生的大段输出会让历史持续增长，最终超出模型的上下文窗口，服务直接返回 400。第八章之前 MossCode 没有任何应对，只能 /clear 重来。

第一层 · 预防

大结果存盘

单个工具结果太大时，完整内容写到会话目录，历史中只放开头和结尾的预览。模型需要细节时用 read_file 分页读取存盘文件。成本为零，不调用模型。

第二层 · 兜底

摘要压缩

估算接近阈值时，用一次不带工具的模型请求把较早的消息压缩成结构化摘要，近期消息保留原文，用户原话由程序原样附上。

11.2 配置与阈值

程序不维护“模型 → 窗口”对照表，窗口由每个 Provider 的 context_window 配置（未配置按 128K 并提示一次）。阈值全部由配置算出：

context.py · ContextBudget
SUMMARY_RESERVE = 20_000   # 给结构化摘要留的输出空间
AUTO_MARGIN = 13_000       # 吸收两次检查之间一轮的增长和估算误差
MANUAL_MARGIN = 3_000
MIN_THRESHOLD = 16_000

effective        = window - max(max_output_tokens, SUMMARY_RESERVE)   # 输入 + 最大输出须放进窗口
window_threshold = effective - AUTO_MARGIN
auto_threshold   = min(window_threshold, compact_threshold) if compact_threshold else window_threshold
manual_limit     = effective - MANUAL_MARGIN                         # 摘要请求本身的输入上限

阈值计算器

验收时用 context_window: 50000 而不是 40000：40000 算出的自动阈值是 40000 − 20000 − 13000 = 7000，小于 16000 的下限，启动时报配置错误。

11.3 估算：不用分词器

context.py · estimate_text() 与 ContextMeter.estimate()
def estimate_text(text):
    """ASCII at 4 characters per token, every other character (CJK etc.) as one token: errs high."""
    ascii_count = len(text.encode("ascii", "ignore"))
    return math.ceil(ascii_count / 4) + len(text) - ascii_count     # 每条消息另加 4

def estimate(self, history, extra="", fixed=...):
    if self.anchor is not None and self.anchor_length <= len(history):
        # 锚点 = 上次服务返回的 input + output；只估算之后新增的消息
        return self.anchor + estimate_messages(history[self.anchor_length:]) + estimate_text(extra)
    # No usable anchor: count the whole request, including system prompt and tool definitions.
    return estimate_text(fixed()) + estimate_messages(history) + estimate_text(extra)

有锚点时，大部分数字来自服务的真实计数，只有增量是估算，误差小；刚压缩完、/clear、切换模型、或服务不返回输入用量（Chat 协议未开 stream_usage）时，没有锚点，就全量估算系统提示、工具定义和历史。中文按 1 字 1 Token 偏保守，宁可早压缩也不要撞墙。

两套口径并存

“是否触发”用锚点（真实计数），“切在哪里”用字符估算（split_point 只能估算单条消息）。真实分词器对数字等内容可能比估算多很多，所以会出现“总量已超阈值，但按估算近期消息覆盖了全部历史”的情况。验收中正是这个现象导致了“没有可压缩的内容”的误报，见 11.8。

11.4 第一层：大结果存盘

tool_budget.py（简化）
RESULT_TOKENS = 12_500       # 单个结果上限，约 5 万个 ASCII 字符
MESSAGE_TOKENS = 50_000      # 同一批并行调用的合计上限
HEAD, TAIL = 2_000, 1_000
EXEMPT = frozenset({"read_file"})   # 已分页、读的又是磁盘文件；存盘会在副本上循环

    if name in EXEMPT or estimate_text(text) <= RESULT_TOKENS: return text, details
    return store(text, details, session, call_id)       # 写 tool-results/<id>.txt，返回预览

def bound_message(message, session):                 # 一批结果：在 execute_batch 的 finally 中调用
    超过 50,000 时，在尚未存盘的结果中从大到小依次存盘，直到合计不超限

预览长什么样

“输出过大（约 N Token，M 字符），完整内容已保存到：路径。需要完整内容时用 read_file 读取这个文件（可用 offset 和 limit 分页）。”然后是前 2,000 字符、省略字节数、后 1,000 字符。测试失败摘要通常在末尾，所以保留尾部。

会话目录

session.py：~/.mosscode/sessions/<时间>-<4 位随机>/，第一次写入时才创建（lazy=True），含标记文件 .mosscode-session。启动时只删除 30 天前且带标记的目录。persist_result 用 "x" 模式写，同一调用 ID 只写一次。

读取不需要审批

存盘文件在项目外。registry.use_session() 把会话目录告诉权限策略，decide() 对该目录内的 read_file 直接放行，包括计划模式。否则模型每次查看存盘内容都要弹审批。

决定只做一次

store() 在 details 中写入 budgeted=True；bound_message 跳过已标记的结果。结果一旦进入历史就不再改写，保证缓存前缀不变（测试 AC1 验证了相邻两次请求的前缀逐项相同）。

同一章还把命令输出的内部上限从“每个流保留 8 KiB 头 + 22 KiB 尾”改为 1 MiB 头 + 1 MiB 尾：截断改由第一层统一负责，那个上限只用来防止内存失控。

11.5 第二层：摘要压缩

估算 ≥ 自动阈值→ cut_point：切在哪里→ summary_request：不带工具的请求→ parse_summary：取 <summary>→ boundary：边界消息 + 原话→ write_record：compact-n.md→ 重置状态

compaction.py 对 Agent 是纯函数：输入历史，返回新历史或抛出 CompactionError，从不修改传入的列表。失败时历史保持原样。

① 保留哪些消息：split_point 与 cut_point

compaction.py
KEEP_TOKENS, KEEP_MESSAGES, KEEP_SHARE = 10_000, 5, 0.4

def _group_start(history, index):
    # Never start on tool results: keep the assistant call that produced them.
    while index > 0 and history[index].role == "tool": index -= 1
    return index

def split_point(history, threshold):
    start = _group_start(history, len(history) - 1)        # 至少保留最后一组
    tokens = estimate_messages(history[start:])
    cap = int(threshold * KEEP_SHARE)                      # 保留部分不超过阈值的 40%
    while start > 0 and (tokens < KEEP_TOKENS or len(history) - start < KEEP_MESSAGES):
        earlier = _group_start(history, start - 1)
        extra = estimate_messages(history[earlier:start])
        if tokens + extra > cap: break
        start, tokens = earlier, tokens + extra
    return 0 if _only_boundary(history[:start]) else start   # 只剩上次的摘要：没有可压缩的

def cut_point(history, threshold, *, manual=False):
    """split_point; a manual /compact on a short history keeps only the last group instead."""
    cut = split_point(history, threshold)
    if cut or not manual or not history: return cut
    start = _group_start(history, len(history) - 1)
    return 0 if _only_boundary(history[:start]) else start

模拟器：保留哪些消息

按上面的算法逐步计算。数字是每条消息的估算 Token，绿色保留原文，灰色被压缩。

② 摘要请求

  • 不带工具：provider.stream(..., tools=(), allow_tools=False)，提示的开头和结尾都写明禁止调用工具。
  • 序列化为纯文本：被压缩的消息渲染成 [用户]、[助手]、[工具调用] 名称 参数、[工具结果 · 名称]，作为一条 user 消息发送。这样任何协议都不会遇到“工具调用和结果不成对”的问题。
  • 先草稿后摘要：要求先在 <analysis> 中按时间梳理，再在 <summary> 中按 9 部分写：主要请求和意图、关键技术概念、文件和代码段、错误和修复、问题解决过程、用户的偏好与约束、待办任务、当前工作（最详细）、下一步。程序只取 summary。
  • 手动说明：/compact 只保留与 notes.txt 相关的内容 的说明附加在提示中。
compaction.py · compact_history() 中的缩减循环（简化）
for step in range(SHRINK_STEPS + 1):                 # 最多缩减 3 次

失败判定（parse_summary）：服务报错、回复包含工具调用、因输出上限截断、没有 <summary> 或内容为空。任何一种都抛出 CompactionError，历史不变。

原话不交给模型改写

摘要可能遗漏或改写用户的要求。collect_quotes 收集被压缩部分的用户输入，原样附上，预算 8,000 Token。fit_quotes 从新到旧装入：放得下就完整保留，放不下就只留前 200 字符加“原文见记录文件”。人工验收 M45 就是检查压缩后模型还能复述最早那句“以‘收到’开头”。

多次压缩时原话继续带入

每条原话是边界消息中一个以 "\n\n▸ " 开头的独立内容块。下一次压缩时，carried_quotes() 从旧边界消息中取回这些块，和新的用户输入一起重新排预算，所以第一句要求不会在第二次压缩时丢失。

④ 压缩成功后的状态

async def _compact(self, instructions="", *, manual=False):
    if not cut_point(self.history, self.budget.auto_threshold, manual=manual):
        # Nothing older than the kept tail: automatic attempts skip silently and never trip the breaker.
        if manual: yield CompactFailed(NOTHING, ..., "nothing", True)
        return
    yield CompactStarted(manual)
    try:
        done = await compact_history(self.provider, self.history, self.budget, session=self.session,
                                     instructions=instructions, manual=manual)
    except CompactionError as exc:
        if not manual and exc.code != "nothing": self.compact_failures += 1
        yield CompactFailed(...); return
    self.history = done.history
    self.registry.forget_reads()                          # 先读后改：所有文件都要重新读取
    self._announced, self._reannounce = "normal", True  # 模式提醒可能被摘要掉了，下一次请求重发
    self.meter.invalidate()                               # 锚点失效，改为全量估算

    yield CompactFinished(done.removed, done.summary_tokens, elapsed, record)

11.6 压缩时机与熔断

入口触发保留规则失败计入熔断
自动每次请求模型前（含任务中的每一轮），估算 ≥ 自动阈值split_point；没有可压缩的就静默跳过是
超限自救服务返回 context_overflow：压缩一次，重试一次原请求；仍超限就报错停止同自动是
手动 /compact空闲时，不看阈值；Esc 取消，历史不变cut_point(manual=True)：短历史只保留最后一组否；成功后清零并恢复自动压缩

熔断：自动压缩连续失败 3 次（BREAKER = 3）后暂停，提示“自动压缩已暂停，可以 /compact 手动重试或 /clear”。手动压缩成功、/clear 或切换模型后恢复。这样可以避免每一轮都发出一个注定失败的摘要请求。auto_compact: false 则完全关闭自动压缩和自救，只保留手动。

11.7 界面与无界面输出

进度行原地变为结果

收到 CompactStarted 时挂载一个 CompactRow（自动：“✻ 上下文接近上限，正在压缩 · Ns”；手动：“✻ 正在压缩上下文 · Ns”），每 0.2 秒由 _tick 刷新计时。完成、失败或取消时调用 finish()，同一行变成“✓ 已压缩上下文 · N 条消息 → 摘要 · 约 X Token · 用时”。行未完成前 transcript 为 None，滚动历史的提交在这里停住，保证顺序。

显示位置

本轮回复尚未开始时，进度行插在回复之前（mount(row, before=reply)），读起来是“先压缩、后回答”；任务中途压缩时追加在工具行之后。

状态栏比例

“上下文 约 N%” = 估算值 ÷ 有效窗口，收到第一次用量后显示，达到自动阈值的 80% 时变琥珀色。_refresh_context() 只在历史变化时重算并缓存。

-p 无界面

text 格式把进度和结果写到 stderr；stream-json 输出 {"type":"compact","subtype":"started|finished|failed"}；最终 result 增加 compactions。

11.8 人工验收中发现的问题与修复

自动测试全部通过后，用真实模型（DeepSeek，窗口配置为 50,000）做验收，又发现了四个问题。这一段最值得学习：单元测试证明了算法正确，但没有覆盖“真实 Token 计数与估算不一致”和“用户的感受”。

现象原因修复
M44 读完 3000 行也没有压缩验收配置的副本里漏加了 context_window，按 128K 计算，自动阈值约 95K补上配置；验收指南写明“启动区不应再出现未配置提示”，作为自检
一轮开始时出现“没有可压缩的内容”锚点（真实计数）已超阈值，但按字符估算，近期消息覆盖了全部历史；这次空尝试还被当成失败计入熔断自动压缩先算 cut_point，为 0 时不发事件、不计失败，直接发送请求（超限还有自救兜底）
手动 /compact 说没有可压缩的内容手动与自动共用“至少 1 万 Token、5 条”的保留规则；小窗口压缩一次后，剩余历史全落在保留范围内新增 cut_point(manual=True)：常规规则为 0 时只保留最后一组，与 Claude Code 的 /compact 一致
编辑失败后十几秒没有反应自动压缩期间只有底部状态栏在计时，对话区没有任何变化新增 CompactRow 实时进度行，完成后原地变为结果；取消时变为“已取消压缩”

修复后新增 4 个测试：手动切点、阈值已到但无可压缩时静默跳过、进度行原地变为结果、取消时进度行收尾。第八章测试从 43 个增加到 47 个，全量 591 passed。

11.9 已知限制

  • 估算没有分词器，与服务计费数字有差异；压缩时机以估算为准，超限时由自救兜底。
  • 摘要质量依赖模型；关键细节靠记录文件和“修改前必须重新读取”的约束兜底。
  • 会话目录不是对话记录，不支持退出后恢复会话。

自测题

先自己回答，再展开核对。

1. 第一次请求就被取消，历史里会留下那条用户消息吗？

不会。用户消息在收到第一个完整回复后才写入历史（committed），之前只作为 fresh 临时拼进请求。

2. 为什么首事件之后断流不重试？

正文可能已经显示给用户，重放会重复显示；更重要的是，只有“什么都没产生”的请求才能保证没有任何工具调用被执行，重试才安全。

3. 模型一次回复了 read、read、edit、read，执行顺序是怎样的？

分成三批：[0,1] 并发，[2] 单独，[3] 单独。写入之后的读取不会被提前；历史中的结果顺序始终是原始顺序。

4. bypassPermissions 能放行 git push --force 吗？能放行 rm -rf / 吗？

前者是高风险级，任何档位都要求每次确认，只提供“本次允许”和“拒绝”；后者是灾难级，在 operation() 中直接以 dangerous_command 拒绝，任何授权都解除不了。

5. 为什么 read_file 不参与第一层存盘？

它已经分页，而且读的就是磁盘上的文件。如果把它的结果也存盘，模型为了看完整内容又会去 read_file 存盘文件，形成循环。

6. 为什么存盘决定必须在结果写入历史之前做，而且之后不再改？

为了 Prompt Cache。已经发送过的历史前缀必须逐字节不变，否则之后每次请求都无法复用缓存。budgeted 标记保证同一结果不会被处理两次。

7. 窗口 50,000、输出上限 4,096 时，自动阈值是多少？保留部分最多多少？

输出预留取 max(4096, 20000) = 20000，有效窗口 30000，自动阈值 30000 − 13000 = 17000；保留部分上限是 17000 × 0.4 = 6800（但至少保留最后一组）。

8. 压缩成功后，模型直接 edit 一个之前读过的文件会怎样？

返回 not_read。压缩时 forget_reads() 清空了 FileState，因为模型手里已经没有文件原文。重新 read_file 后才能修改（验收 M46）。

9. 用户最早的一句要求，经过两次压缩后还在吗？

在。原话是边界消息中独立的 ▸ 内容块，第二次压缩时 carried_quotes() 取回它们重新排预算；预算不够时较早的会被缩短到 200 字符并注明见记录文件。

10. 为什么“阈值已到但没有可压缩的内容”时，自动压缩要静默跳过而不是报失败？

这不是摘要失败，而是估算口径差异造成的空操作。报出来会让用户困惑，计入熔断还会在几轮后错误地暂停自动压缩。请求照常发送，真超限时还有自救兜底。

11. 手动 /compact 和自动压缩的保留规则有什么不同？为什么？

自动压缩要保证压缩后仍有足够的近期原文继续工作（至少 1 万 Token、5 条）。手动是用户明确要求，常规规则找不到可压缩内容时改为只保留最后一组，否则小窗口下手动压缩几乎总是“没有可压缩的内容”。

12. 进度行为什么要等完成后才进入终端滚动历史？

写入滚动历史后就不能再改了。_commit_ready_transcript() 遇到 transcript is None 的 CompactRow 就停止提交，等它 finish() 后再连同后面的内容一起按顺序写入。
