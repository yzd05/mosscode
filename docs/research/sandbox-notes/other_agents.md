## Q1. OpenHands: Docker sandbox, agent server, process/local and remote providers

### Takeaway
OpenHands' isolation boundary is a whole-agent container. The agent's tools run inside a Docker container that hosts the "Agent Server" (V1; in V0 this was the "action execution server"), and the host talks to it over HTTP/WebSocket with a session API key. There is no per-command OS sandbox. The "process" provider runs everything with the user's rights, and the project's own docs call it unsafe.

### Cited Findings
- V1 uses the term "sandbox" (not "runtime"). There are three providers: **Docker sandbox (recommended)**, which "Runs the agent server inside a Docker container"; **Process sandbox (unsafe, but fast)**, which "Runs the agent server as a regular process on your machine. No container isolation"; and **Remote sandbox**, used by managed/hosted setups. Selection still goes through the legacy `RUNTIME=docker|process|remote` variable, where `process` is "aka legacy `RUNTIME=local`". — [OpenHands docs: Sandbox overview](https://docs.openhands.dev/usage/runtimes/overview.md)
- Mounts: the user's repo is mounted explicitly, either with `openhands serve --mount-cwd` (legacy) or `SANDBOX_VOLUMES=host_path:container_path[:mode]`, e.g. `$PWD:/workspace:rw`. The docs warn: "Anything mounted read-write into `/workspace` can be modified by the agent." The legacy CLI launcher "is no longer actively maintained". — [OpenHands docs: Docker Sandbox](https://docs.openhands.dev/usage/runtimes/docker.md)
- Networking: each Docker sandbox exposes its agent-server, VS Code and worker ports on **randomly assigned host ports**, and the frontend reaches them through `container_url_pattern` (default `http://localhost:{port}`). `AGENT_SERVER_USE_HOST_NETWORK=true` switches to Docker host-network mode on fixed ports 8000/8001/8011/8012, which allows only one sandbox at a time. The docs describe no egress allowlist. — [OpenHands docs: Docker Sandbox](https://docs.openhands.dev/usage/runtimes/docker.md)
- Communication: `RemoteWorkspace` runs commands by `POST /command` over HTTP and moves files with `POST /file/upload` and `GET /file/download`. `LocalWorkspace` uses `subprocess.run()` directly. The docs' comparison: Local = "Process-level" isolation, "Host system access"; Remote = "Container/VM-level", "Sandboxed". — [OpenHands SDK: Workspace architecture](https://docs.openhands.dev/sdk/arch/workspace.md)
- `DockerWorkspace` pulls the image (e.g. `ghcr.io/openhands/agent-server:latest-python`), starts the container with the agent server, waits for readiness, and removes the container on context exit. The conversation then automatically becomes a `RemoteConversation` that streams events over WebSocket. Images are `linux/amd64` or `linux/arm64`. — [OpenHands SDK: Docker Sandbox guide](https://docs.openhands.dev/sdk/guides/agent-server/docker-sandbox.md)
- The Agent Server "starts without API authentication" by default. To expose it, set `OH_SESSION_API_KEYS_0` (clients send it as `X-Session-API-Key`) and `OH_SECRET_KEY`, and bind to `127.0.0.1` for local use. — [OpenHands SDK: Agent Server package](https://docs.openhands.dev/sdk/arch/agent-server.md)
- Execution boundary table: on a **host process** "Agent Server and tools run directly on the backend host without container isolation". With **Docker/Kubernetes**, tools "run inside the configured container or pod with its mounts and network policy". With **Cloud/Enterprise**, the platform creates a per-conversation sandbox hosting Agent Server. — [OpenHands: Agent Canvas Architecture](https://docs.openhands.dev/openhands/usage/agent-canvas/architecture.md)
- The install docs warn: "Agent Canvas is the client and does not provide isolation. If the backend runs directly on your machine, the agent can act with your user account's permissions. Use a container, sandbox, or VM". The desktop preview ships for macOS and x64 Windows/Linux, and its default local backend "runs directly on your machine". The Docker install method "Runs inside a container and can access mounted project directories". — [OpenHands: Install Agent Canvas](https://docs.openhands.dev/openhands/usage/agent-canvas/setup.md)
- Secrets: the SDK's Secret Registry "automatically detects secret references in bash commands, injects them as environment variables when needed, and masks secret values in command outputs". `conversation.update_secrets({...})` accepts static strings or callable `SecretSource`s. — [OpenHands SDK: Secret Registry](https://docs.openhands.dev/sdk/guides/secrets.md)
- Approvals are separate from the sandbox. A `security_risk` parameter (LOW/MEDIUM/HIGH/UNKNOWN) is added to every tool schema, the LLM fills it in, and a `ConfirmationPolicy` maps risk to a confirmation requirement. `LLMSecurityAnalyzer` makes no extra LLM calls. — [OpenHands SDK: Security architecture](https://docs.openhands.dev/sdk/arch/security.md)
- Other sandbox backends documented in the SDK: Apptainer and an API-based (remote) sandbox. — [OpenHands docs index](https://docs.openhands.dev/llms.txt)
- License: MIT for both `OpenHands/OpenHands` and `OpenHands/software-agent-sdk` (GitHub API `license.spdx_id`). — [GitHub OpenHands/OpenHands](https://github.com/OpenHands/OpenHands), [GitHub OpenHands/software-agent-sdk](https://github.com/OpenHands/software-agent-sdk)

### Inferences
- The OpenHands model ("move the whole agent into a container and RPC into it") gives strong isolation but needs Docker. On Windows that means Docker Desktop/WSL2, and the agent operates on Linux paths over a bind mount. That is a heavy dependency for a Windows-first TUI like MossCode. It is better suited as an optional "container mode" than as the default.
- The risk-labelled tool schema and the Secret Registry's output masking can be reused independently of any sandbox. The Secret Registry injects secrets as env vars only when they are referenced and masks them in output.

### Gaps
- I did not re-read the V0 `action_execution_server.py` source; the old runtime README URL returned 404. V0 details (runtime image build, `/execute_action` endpoint) are therefore not re-verified here.
- No primary doc found stating default egress restrictions for the Docker sandbox. Inference: none beyond Docker's default bridge network.
- The Windows prerequisites for the Docker sandbox (Docker Desktop + WSL2) were not explicitly confirmed on a current page.

## Q2. Cursor: sandboxed agent terminal

### Takeaway
Cursor has the most mature local design among the agents researched here. Its local sandbox is uniform across platforms (Seatbelt on macOS, Landlock+seccomp on Linux, the Linux sandbox inside WSL2 on Windows). By default it gives the workspace read/write access and denies network access except through a domain allowlist, and it hard-protects config and git paths. It is integrated with "Auto-review": sandboxable commands run without prompts, and failed or unsandboxable ones go to a classifier or to the user. Cursor has no native Windows sandbox; it uses WSL2.

### Cited Findings
- Engineering blog (Feb 18, 2026): sandboxing was rolled out "on macOS, Linux, and Windows", and "Sandboxed agents stop 40% less often than unsandboxed ones". Cursor exposes "a uniform sandbox API, implemented differently on each platform". — [Cursor blog: Implementing a secure sandbox for local agents](https://cursor.com/blog/agent-sandboxing)
- On macOS, Cursor rejected App Sandbox (it would require signing every binary), containers (Linux binaries only) and VMs (latency and memory). It chose Seatbelt via `sandbox-exec`, "deprecated in 2016, but is still used by... Chrome". The profile is generated dynamically from workspace and admin settings plus `.cursorignore`. The blog shows the profile's write-deny rules for `.vscode`, `.cursor` (except `rules|commands|worktrees|skills|agents`), `.code-workspace`, `.cursorignore`, `.git/config` and `.git/hooks`. — [Cursor blog](https://cursor.com/blog/agent-sandboxing)
- On Linux, Cursor uses Landlock and seccomp directly, because existing open-source wrappers don't support `.cursorignore`: "We map user workspaces into an overlay filesystem and overwrite ignored files with Landlocked copies that can't be read or modified". — [Cursor blog](https://cursor.com/blog/agent-sandboxing)
- On Windows: "we run our Linux sandbox inside WSL2. Building an equivalent native Windows sandbox is significantly harder because most existing sandboxing primitives are tailored to browsers and do not support general-purpose developer tools. We're working with Microsoft to ensure the necessary primitives become available." — [Cursor blog](https://cursor.com/blog/agent-sandboxing)
- Making the agent sandbox-aware: the Shell tool description explains the sandbox constraints and how to request elevation. Tool results now "explicitly surfac[e] the sandbox constraint responsible for a failure and, in certain cases, recommend[] that the agent escalate permissions". Before this change, agents kept retrying the same command. "a third of requests on supported platforms" run sandboxed. — [Cursor blog](https://cursor.com/blog/agent-sandboxing)
- Run Modes: **Auto-review** runs allowlisted calls immediately, runs other shell commands "in the sandbox when possible", and sends anything else to the classifier. **Allowlist** runs the allowlist without approval and can optionally sandbox supported commands. **Run Everything** has no sandbox. "If a sandboxed command fails on a sandbox restriction... the agent can rerun it outside the sandbox. The classifier reviews that rerun." The docs also state: "Auto-review is not a security boundary". The classifier runs on the Cursor backend using Gemini 3.5 Flash Lite with a Haiku fallback. — [Cursor docs: Run Modes](https://cursor.com/docs/agent/security/run-modes)
- Changelog: 3.5 (May 22, 2026) deprecated "Ask Every Time" and folded "Run in Sandbox" into Allowlist with sandboxing enabled. 3.6 (May 29, 2026) made Auto-review the default. 3.23 (Oct 1, 2026) added the Workspace read boundary. — [Cursor docs: Run Modes](https://cursor.com/docs/agent/security/run-modes)
- Defaults: the workspace is read/write; protected paths are not writable; network is "Blocked by default, then opened by your network mode and sandbox.json"; `/tmp` and platform temp directories are writable. "Some commands need full system access and bypass the sandbox. Cursor will indicate when a command runs outside the sandbox and ask for your approval." — [Cursor docs: Run Modes](https://cursor.com/docs/agent/security/run-modes)
- Read boundary (3.23+): `readBoundary: "system"` is the default. `"workspace"` means sandboxed commands on macOS/Linux can read only the workspace, the Read Allowlist and system paths (libraries, toolchains, cert stores), and they get a private per-project temp directory. — [Cursor docs: Run Modes](https://cursor.com/docs/agent/security/run-modes)
- On Linux, the kernel must be ≥6.2 with Landlock v3 and unprivileged user namespaces enabled, "If your kernel does not meet these requirements, Cursor falls back to asking for approval". An AppArmor profile package is needed for the CLI and remote environments. The sandbox remaps the process to UID 0 in a user namespace, so `CURSOR_ORIG_UID`/`GID` are provided. `CURSOR_SANDBOX_LANDLOCK_STATUS` is `fully_enforced` or `bubblewrap` (fallback). — [Cursor docs: Run Modes](https://cursor.com/docs/agent/security/run-modes)
- Network modes: "sandbox.json Only", "sandbox.json + Defaults" (the default, adding about 100 package-registry domains such as pypi.org, registry.npmjs.org, github.com and crates.io) and "Allow All". — [Cursor docs: Run Modes](https://cursor.com/docs/agent/security/run-modes)
- The `sandbox.json` schema lives in `~/.cursor/sandbox.json` and `<workspace>/.cursor/sandbox.json`. `type` is `workspace_readwrite` (default), `workspace_readonly` or `insecure_none`. Other fields: `additionalReadwritePaths`, `additionalReadonlyPaths`, `readBoundary`, `additionalReadPaths`, `disableTmpWrite`, `enableSharedBuildCache` (redirects npm/cargo/pip caches to a shared tmpdir), and `networkPolicy {default: deny, allow[], deny[]}` with exact/wildcard/CIDR patterns. "Deny always beats allow". RFC1918, loopback, `169.254.169.254` and IPv6 private ranges are blocked by default ("to prevent SSRF"). Matching is by domain/IP only, so paths are ignored. — [Cursor docs: sandbox.json reference](https://cursor.com/docs/reference/sandbox)
- Merge order is per-user < per-repo < team-admin < hardcoded. Network allow lists are unioned unless an admin allowlist replaces them, deny lists are always unioned, and `default: "deny"` wins. Always write-protected: `.cursor/*.json`, `.claude/*.json`, `.vscode/**`, `.code-workspace`, `.git/hooks/**`, `.git/config`, `.git/info/attributes`, `.cursorignore`. With `readBoundary: "workspace"`, only `~/.ssh/known_hosts` is readable from `~/.ssh`. — [Cursor docs: sandbox.json reference](https://cursor.com/docs/reference/sandbox)
- Third-party (forum bug report, search snippet only): on Windows the sandbox logged "direct egress blocking is best-effort on Windows". — [Cursor forum: allowlist ignored with Auto-Run in Sandbox](https://forum.cursor.com/t/command-allowlist-is-silently-ignored-when-auto-run-in-sandbox-is-enabled/152136) (not opened first-hand)
- License: proprietary; no source available.

### Inferences
- Cursor's key UX insight for MossCode is that a sandbox only reduces prompts if the agent knows about it. The tool description has to state the constraints, failures need a structured "blocked by sandbox: <constraint>" message, and there must be an explicit escalation path. Otherwise models retry blindly.
- Note that per-repo `sandbox.json` can *add* paths and domains (paths are unioned). That is weaker than Junie and Kilo, which refuse to let project config widen the sandbox.
- Even Cursor, with Microsoft engagement, did not ship a native Windows sandbox as of the Feb 2026 blog post, and the Oct 2026 docs list macOS and Linux requirements only. That is a strong signal of how hard native Windows is. (The Codex CLI native Windows sandbox is covered by another researcher.)

### Gaps
- The current docs' platform section lists only macOS and Linux. It is unclear whether the WSL2-based Windows sandbox is still offered, and under what conditions (e.g. only when the workspace is opened in WSL).
- I found no details on how the network allowlist is enforced on macOS/Linux (proxy vs. socket filtering).

## Q3. Other agents with real OS-level sandboxes: Zed, Kilo Code, Devin Local (Windsurf), JetBrains Junie

### Takeaway
By late 2026, three more agents ship OS sandboxes that share a pattern: Seatbelt on macOS, bubblewrap/namespaces (+seccomp) on Linux, a write-confined workspace with read-only `.git`, network denied by default or limited to an allowlist via a loopback HTTP(S) proxy, and approval prompts that widen the sandbox on demand. Zed is on by default; Kilo, Devin and Junie are opt-in. None of them sandboxes native Windows processes. Zed uses WSL with documented weaknesses on NTFS; Kilo, Devin and Junie don't support Windows at all, and Devin hard-fails.

### Cited Findings

**Zed Agent** (sandbox on by default since v1.14, Aug 2026)
- "Sandboxing instead uses OS features to forcibly restrict which resources a tool call has access to." It applies only to the Zed Agent **terminal** and **fetch** tools. It does not cover Zed itself, language servers, extensions, tasks, normal terminals, External Agents or Terminal Threads. — [Zed docs: Sandboxing](https://zed.dev/docs/ai/sandboxing)
- Defaults: reads are allowed for "most of the filesystem". Writes are allowed only in open project directories, and `.git` and linked-worktree metadata are not writable. A per-thread temp directory is provided. Other writes are blocked unless approved. Outbound network is blocked unless approved per host or entirely. Sandboxed commands cannot open Unix-domain sockets, e.g. the session bus or a container daemon, "which could otherwise be used to run commands outside the sandbox". — [Zed docs](https://zed.dev/docs/ai/sandboxing)
- Approvals: a prompt asks for specific hosts, any host, specific write paths, unrestricted writes, or running unsandboxed. Each grant can be "one tool action / rest of thread / always", and "always" grants persist in `settings.json` under `agent.sandbox_permissions` (`network_hosts`, `allow_all_hosts`, `write_paths`, `allow_fs_write_all`, `allow_unsandboxed`). "When requesting elevated privileges, agents must provide a reason". Git metadata writes are never grantable while a command is sandboxed. — [Zed docs](https://zed.dev/docs/ai/sandboxing)
- macOS uses Seatbelt via `sandbox-exec` with a Mach-service allowlist that blocks LaunchServices/launchd, the pasteboard and audio. Approved network access goes through an HTTP/HTTPS proxy for host filtering, so SSH and raw sockets may not work. On Linux, Zed uses a **non-setuid** `bwrap` only and refuses setuid bwrap because it would run "root-privileged setup with arguments partly derived from model-influenced input". `/tmp` is a fresh tmpfs per call. "If Bubblewrap is unavailable... Zed may run the command without the OS sandbox and show a warning". Filesystem restrictions are fixed at sandbox creation time. — [Zed docs](https://zed.dev/docs/ai/sandboxing)
- Windows: "Zed Agent sandboxing is supported only when the agent action runs inside WSL". Writes may escape grants on NTFS-backed paths (`/mnt/c/...`) because inode pinning does not pin the underlying Windows object, and Zed shows a warning when this applies. "Native Windows processes do not currently have the same sandbox integration". Network inside WSL is all-or-nothing, and host-specific filtering is not available. Without WSL, or when running unsandboxed, Zed falls back to the native shell in this order: Git Bash/scoop bash, then PowerShell, then cmd.exe. — [Zed docs](https://zed.dev/docs/ai/sandboxing)
- Threat model: Zed documents sandbox side channels. These include Rust proc-macros executed by rust-analyzer outside the sandbox, Makefile poisoning, and a submodule with an attacker-controlled `core.fsmonitor` that runs when the user later uses git. The docs call the sandbox "one layer in a defense-in-depth strategy". — [Zed docs](https://zed.dev/docs/ai/sandboxing)
- Release: Zed 1.14.2 (Aug 5, 2026) shipped default sandboxing for the terminal and fetch tools (third-party news). — [alternativeto news](https://alternativeto.net/news/2026/8/zed-enables-default-sandboxing-for-agent-panel-tools-in-version-1-14/). Design blog: [Zed blog: Sandboxing](https://zed.dev/blog/sandboxing) (not opened first-hand). Microvm backend proposal (Oct 2026): [GitHub discussion #40482](https://github.com/zed-industries/zed/discussions/40482) (search snippet).

**Kilo Code** (MIT; the CLI is an opencode fork; opt-in sandbox)
- "The sandbox adds an operating-system boundary around agent tools... The sandbox is **disabled by default**. It does not restrict filesystem reads." It is "not available on Windows. If an enabled macOS or Linux sandbox policy cannot be enforced, Kilo reports the reason and refuses to run the affected tool. It does not silently fall back". — [Kilo docs source: sandboxing.md](https://github.com/Kilo-Org/kilocode/blob/main/packages/kilo-docs/pages/getting-started/settings/sandboxing.md)
- Config lives in `kilo.jsonc`: `sandbox.enabled` (default false), `sandbox.network` (default `"deny"`), `allowed_hosts` (host:port, default port 443, "Only global config may add destinations") and `writable_paths` (global only). "Project config may tighten sandbox policy... It cannot disable a globally enabled sandbox, allow network denied by global config, add destinations, or add writable paths." — [Kilo docs source](https://github.com/Kilo-Org/kilocode/blob/main/packages/kilo-docs/pages/getting-started/settings/sandboxing.md)
- Writable locations are the workspace or worktree, Kilo's data/cache/state directories, `$TMPDIR/kilo` and configured paths. `.git` is always read-only, Kilo's policy files and global config root are read-only (so the agent "cannot widen network or write authority for a later session"), and child processes inherit the restrictions. File-edit tools mutate files through a sandboxed worker. Notebook execution and background processes are disabled while sandboxed. — [Kilo docs source](https://github.com/Kilo-Org/kilocode/blob/main/packages/kilo-docs/pages/getting-started/settings/sandboxing.md)
- Network: with `allowed_hosts` set, direct sockets stay blocked and an authenticated proxy is the only egress. For HTTPS `CONNECT`, the proxy requires the TLS ClientHello SNI to match the allowed host. DNS is resolved outside the sandbox, and non-public results are rejected. "Linux keeps the command in a network namespace and bridges only the proxy socket; macOS Seatbelt permits only the scoped loopback proxy port." MCP tool calls are disabled while the network is restricted. Model inference traffic is not blocked; the docs warn this "is not a provider privacy control". — [Kilo docs source](https://github.com/Kilo-Org/kilocode/blob/main/packages/kilo-docs/pages/getting-started/settings/sandboxing.md)
- Escalation: for writes outside the boundary, e.g. mutating git commands that touch `.git`, "Kilo then shows an escalation prompt and waits for an explicit approval". The docs also state that approving a permission does not make a path writable. — [Kilo docs source](https://github.com/Kilo-Org/kilocode/blob/main/packages/kilo-docs/pages/getting-started/settings/sandboxing.md)
- Implementation: `packages/kilo-sandbox/src/` contains `seatbelt.ts`, `seatbelt-network.ts`, `bubblewrap.ts`, `proxy.ts`, `tls-client-hello.ts` and `kilo-sandbox-network-relay.ts`. `backend.ts` switches on `process.platform` (`darwin`/`linux`/`win32`), and Windows returns `unavailable(reason)`. The repo also carries `patches/@anthropic-ai%2Fsandbox-runtime@0.0.63.patch`. — [GitHub Kilo-Org/kilocode tree](https://github.com/Kilo-Org/kilocode/tree/main/packages/kilo-sandbox/src)
- Dates: the earliest commit to the sandboxing docs page is 2026-06-25 and the latest 2026-09-17 (GitHub API commits). — [GitHub Kilo-Org/kilocode](https://github.com/Kilo-Org/kilocode)
- Contradiction: Kilo's `SECURITY.md` still says "Kilo CLI does **not** sandbox the agent. The permission system exists as a UX feature..." and "If you need true isolation, run Kilo CLI inside a Docker container or VM". That text is likely inherited from opencode and stale relative to the opt-in sandbox. — [Kilo SECURITY.md](https://github.com/Kilo-Org/kilocode/blob/main/SECURITY.md)

**Devin Local / Devin CLI** (Cognition; this harness now powers Devin Desktop, the successor of Windsurf/Cascade)
- The Windsurf terminal docs, now served from Devin Docs, describe Deny/Ask/Allow command rules plus session modes Code/Smart/Bypass Permissions. "Administrators can... enforce sandbox mode". The dedicated agent terminal exists on macOS and Linux (zsh/bash). — [Windsurf docs: Terminal](https://docs.windsurf.com/windsurf/terminal)
- "The Devin Local agent supports OS-level sandboxing": filesystem isolation (writable paths derived from permission scopes; `Read(...)` deny rules hide paths) and network filtering via domain allow/deny lists. Enterprise admins can require it. — [Devin docs: Devin Local](https://docs.devin.ai/desktop/devin-local)
- `--sandbox` / `DEVIN_SANDBOX` is a "[Research Preview] Sandbox exec-tool processes (macOS seatbelt / Linux bwrap+seccomp)". The permission mode `autonomous` requires `--sandbox`. — [Devin CLI: Commands & Flags](https://docs.devin.ai/cli/reference/commands)
- Writable paths are the workspace plus granted `Write(...)` scopes; everything else is read-only. `Read(...)` deny paths are hidden entirely, and mid-session `Read` approvals cannot unhide them. `Write(...)` scopes granted mid-session expand the sandbox. When domain filtering is configured, "a managed network proxy starts on loopback and the sandbox restricts all child traffic to route through it". `network_mode: "limited"` allows only GET/HEAD/OPTIONS. `sandbox.excluded.{allow,ask,deny}` rules (e.g. `Exec(git push *)`) let specific commands run outside the sandbox automatically or after a prompt. The most restrictive verdict wins across user and team settings. — [Devin CLI: Sandbox](https://docs.devin.ai/cli/sandbox.md)
- Fail-closed: "If sandbox resolution fails... the CLI will **refuse to start** rather than running unsandboxed." Windows: "OS-level sandboxing is not currently supported on Windows. Sessions on Windows will hard-fail when `--sandbox` is passed or when sandbox enforcement is **Required**". Linux needs `bwrap` and `socat`. — [Devin CLI: Sandbox](https://docs.devin.ai/cli/sandbox.md). "native Windows cannot run the sandbox. Install WSL 2" — [Devin CLI: Commands](https://docs.devin.ai/cli/reference/commands)

**JetBrains Junie CLI** (EAP; proprietary)
- "Sandbox mode wraps every agent-issued terminal command in an OS-level sandbox (`sandbox-runtime`, `srt`) and restricts native edit tools." It is enabled with `junie --sandbox` or `/sandbox`, is per session, and is "available on macOS and Linux. It is not available on Windows." — [Junie docs: CLI quickstart, Sandbox mode](https://junie.jetbrains.com/docs/junie-cli.html)
- Policy: writes are allowed only to the project, its git directory, temp directories and common tool caches (`~/.gradle`, `~/.m2`, `~/.npm`, ...). Reads are unrestricted except `~/.ssh`, where only `config` and `known_hosts` are readable. Network is unrestricted by default; setting `"unrestricted": false` together with `allowedDomains` enables filtering. — [Junie docs](https://junie.jetbrains.com/docs/junie-cli.html)
- Only `~/.junie/sandbox.json` is honored: "a project-local `.junie/sandbox.json` is ignored (with a warning), so a cloned repository cannot widen its own sandbox". The policy file is on the deny-write list for sandboxed commands. The agent may edit it only through a native edit tool, and only with "fresh *Allow once* approval for every change"; "brave mode and saved approvals cannot bypass this confirmation". — [Junie docs](https://junie.jetbrains.com/docs/junie-cli.html)
- Git worktrees and submodules: Junie asks git for its directories and auto-allows external git metadata after verifying it belongs to the worktree. SSH relies on `SSH_AUTH_SOCK` (ssh-agent) instead of reading private keys. Go tools need `allowSystemCertificateValidation`, which the docs acknowledge is a possible exfiltration channel via the macOS trust daemon. — [Junie docs](https://junie.jetbrains.com/docs/junie-cli.html)
- Verification and failure: before enabling, Junie "starts the real runtime with the generated settings and checks that a controlled forbidden write is blocked" and, if filtering is on, that a direct local connection is blocked. If activation fails, terminal execution stays blocked until the user retries or explicitly chooses "Continue without sandboxing". "Brave mode" (YOLO) does not disable the sandbox. — [Junie docs](https://junie.jetbrains.com/docs/junie-cli.html), [Junie slash-command reference](https://junie.jetbrains.com/docs/slash-commands.html)

### Inferences
- There is now an industry-converged default policy for local sandboxes: write only in the workspace and temp, `.git` read-only, agent-config and policy files write-protected, network denied unless allowlisted through a loopback proxy, Unix sockets and docker.sock blocked, and child processes inherit everything. MossCode can adopt the same policy model even where enforcement differs.
- A "project config can only tighten, never widen" rule, as in Kilo and Junie, is a cheap and important protection against malicious repositories. Cursor unions repo paths, which is weaker.
- Fail-closed is the norm in newer designs: Kilo refuses the tool, Devin refuses to start, and Junie blocks terminal execution until the user explicitly opts out. Zed and Cursor fall back to unsandboxed or approval mode with a warning. MossCode should pick one explicitly and surface it in the UI.
- Junie's startup self-test (try a forbidden write and confirm it is blocked) is a cheap, robust check worth copying. It is especially useful on Windows, where primitives are fragile.
- Kilo is MIT-licensed TypeScript, so it is the most directly reusable reference implementation for its proxy, SNI checks and Seatbelt profile generation. Zed's code should not be copied into an MIT project if the relevant crates are GPL/AGPL (see Gaps).
- Windows remains the hole. Every agent here either uses WSL (Cursor, Zed), which only helps for commands run inside WSL rather than native Windows tools like `python.exe` or PowerShell, or it doesn't support Windows at all (Kilo, Devin, Junie). MossCode's main user is on Windows 11, so a native approach (e.g. AppContainer/restricted tokens/Job Objects as in Codex's Windows sandbox, covered elsewhere) would be a differentiator. Following the WSL route would not sandbox the Windows toolchain the user actually uses.

### Gaps
- Zed's license per crate: the GitHub API returns `NOASSERTION` for zed-industries/zed. My understanding is that the editor crates are GPL-3.0-or-later with some Apache-2.0/AGPL crates, but I did not verify the sandbox crate's license.
- Cline PR #14583 ("opt-in sandboxed execution mode", Sep 27, 2026, search snippet) could not be fetched via the GitHub API, so I could not confirm whether it is open, merged or closed.
- The relationship between Windsurf (the legacy "Cascade" agent) and Devin Local in the current Windsurf product isn't fully clear. The docs show Windsurf docs now served from Devin Docs, and Devin Local mentions an "Enable Cascade" control for the legacy agent.
- I did not check which Kilo surfaces (VS Code extension vs CLI) use which code path for the sandbox, beyond the docs saying the VS Code tab exists on macOS/Linux.

## Q4. Agents without a built-in OS sandbox: Goose, opencode, Cline, Roo Code, Aider, Amp, Warp

### Takeaway
These agents run commands with the user's full rights and rely on approval modes, allowlists or LLM "smart approve". Isolation comes from external containers or VMs, or (for Amp and Warp) from cloud execution environments rather than a local sandbox. Goose shipped and then removed a macOS Seatbelt sandbox, and has an open issue (Oct 2026) to design a cross-platform one.

### Cited Findings
- **Goose**: the v1.25.0 blog post (Feb 23, 2026) now carries this note: "The macOS seatbelt sandbox described in this section was experimental and has been removed. The goose server process (which executes tools) runs with the same permissions as your user account and is not sandboxed at the OS level." Users are pointed to `GOOSE_MODE` (`approve`, `smart_approve`). The removed feature was opt-in via `GOOSE_SANDBOX=true` on macOS Desktop. — [goose blog v1.25.0](https://goose-docs.ai/blog/2026/02/23/goose-v1-25-0/)
- Goose issue #12805, "Define an OS sandbox boundary for shell and tool subprocesses", was opened 2026-10-09 and is still open (GitHub API). According to the search snippet, it proposes Seatbelt, a Linux sandbox and WSL2, with native Windows handled separately. — [aaif-goose/goose#12805](https://github.com/aaif-goose/goose/issues/12805). The repo moved to `aaif-goose/goose`; license Apache-2.0.
- **opencode**: the permissions docs gate tools (`read`, `edit`, `bash`, `external_directory`, ...) with allow/ask/deny patterns, and nothing in them describes OS isolation. — [opencode docs: Permissions](https://opencode.ai/docs/permissions/). Issue #2242 "Is there a way to sandbox the agent ?" has been open since 2025-08-25 (GitHub API). — [anomalyco/opencode#2242](https://github.com/anomalyco/opencode/issues/2242). License MIT. Third-party plugins add sandboxing, e.g. `opencode-local-sandbox`, which provides a `bash_sandboxed` tool using srt. — [ghost91-/opencode-local-sandbox](https://github.com/ghost91-/opencode-local-sandbox) (search snippet)
- **Cline**: the CLI reference offers `--worktree` (a detached git worktree under `~/.cline/worktrees/`) and `--data-dir` ("Use isolated local state and enable sandbox mode"). This is state isolation, not OS confinement. — [Cline CLI reference](https://docs.cline.bot/cli/cli-reference). A third-party analysis (Feb 2026, v3.58.0) says "no built-in sandboxing mechanism". — [agent-safehouse: Cline](https://agent-safehouse.dev/docs/agent-investigations/cline) (third-party, search snippet). License Apache-2.0.
- **Roo Code**: the GitHub repo `RooCodeInc/Roo-Code` is **archived** (GitHub API `archived: true`, last push 2026-05-15) and uses allow/deny command lists in the VS Code terminal. I found no sandbox. — [GitHub RooCodeInc/Roo-Code](https://github.com/RooCodeInc/Roo-Code)
- **Aider**: commands suggested by the model run only after user approval (`/run`, `/test`, auto-test), unsandboxed with `shell=True` — [agent-safehouse: Aider](https://agent-safehouse.dev/docs/agent-investigations/aider) (third-party; not verified against `aider/run_cmd.py`). License Apache-2.0. — [GitHub Aider-AI/aider](https://github.com/Aider-AI/aider)
- **Amp**: the manual describes "Orbs: Machines that Amp creates per thread", a fresh cloud environment, alongside a CLI that "runs Amp on your own machine", "Use Your Mac as a Runner", and a "Handling Secrets" section for orbs. The manual pages I fetched have no local sandbox section. — [Amp manual](https://ampcode.com/manual). In 2025 Amp could edit its own config, adding allowlisted commands or MCP servers, which enabled prompt-injection RCE. It was fixed after disclosure. — [Embrace The Red](https://embracethered.com/blog/posts/2025/amp-agents-that-modify-system-configuration-and-escape/)
- **Warp**: Oz cloud agents run in sandboxed cloud environments ("sandboxed by default, with scoped access to repos, secrets, and compute"). — [Warp docs: Cloud Agent FAQs](https://docs.warp.dev/agent-platform/cloud-agents/faqs/) (search snippet). Built on Namespace with per-team tenants and a temporary user-scoped GitHub token injected. — [Warp blog: secure cloud sandboxes with Namespace](https://www.warp.dev/blog/secure-cloud-sandboxes-for-ai-dev-with-namespace) (search snippet). A third-party review says local agent commands run in the user's terminal with approvals only. — [Guard0 TrustVector: Warp](https://trustvector.guard0.ai/agents/warp) (third-party). The client repo `warpdotdev/warp` is AGPL-3.0 (GitHub API).

### Inferences
- Goose's removal of its Seatbelt sandbox suggests that a sandbox bolted on without agent awareness or escalation UX is hard to maintain. Cursor's emphasis on teaching the agent about the sandbox points the same way. This is inference; Goose gives no reason in the note.
- For agents without a sandbox, the recommended isolation is always "run the whole agent in Docker or a VM" (Kilo's SECURITY.md, OpenHands' warnings, third-party guides). MossCode could document this as the fallback for Windows users until a native sandbox exists.
- The Amp config-self-edit bug shows that protecting the agent's own config, allowlist and MCP settings from agent writes matters even without an OS sandbox. MossCode's application-level checks should already cover this, and an OS sandbox should hard-protect those paths, as Cursor, Kilo and Junie do.

- Warp local agent: I did not open Warp's primary docs for local command execution, so "no local OS sandbox" rests on third-party plus the absence of evidence.
- Amp: the CLI configuration page had no "sandbox", "permission" or "allowlist" matches in the static HTML (the page may be JS-rendered), so Amp's current local permission model is unverified.
- Aider: `aider/run_cmd.py` was not read directly.

## Q5. Cross-cutting design patterns relevant to MossCode (Windows-first, Python)

### Takeaway
Across the agents that sandbox, the common design is a per-command OS confinement wrapper (not a container) with a declarative policy: workspace-write, protected paths, network via a loopback allowlist proxy, read-deny for secrets. It is integrated with the approval system so that sandboxed commands run without prompts and only escalations ask. No agent in this set has a native Windows sandbox; all of them use WSL or don't support Windows.

### Cited Findings
- Escalation instead of prompting per command: Cursor ("Sandboxed agents run freely... and only request approval when they need to step outside it") — [Cursor blog](https://cursor.com/blog/agent-sandboxing); Zed (grants per action, per thread or always, with a mandatory reason) — [Zed docs](https://zed.dev/docs/ai/sandboxing); Devin (`autonomous` mode only with the sandbox; `excluded.ask` rules) — [Devin CLI: Sandbox](https://docs.devin.ai/cli/sandbox.md); Kilo (escalation prompt for writes outside the boundary) — [Kilo docs source](https://github.com/Kilo-Org/kilocode/blob/main/packages/kilo-docs/pages/getting-started/settings/sandboxing.md).
- Protected paths that agents cannot write even inside the workspace: `.git/hooks`, `.git/config` and agent config files (Cursor) — [Cursor sandbox.json reference](https://cursor.com/docs/reference/sandbox); all of `.git` (Zed, Kilo) — [Zed docs](https://zed.dev/docs/ai/sandboxing), [Kilo docs](https://github.com/Kilo-Org/kilocode/blob/main/packages/kilo-docs/pages/getting-started/settings/sandboxing.md); the policy file itself (Junie, Kilo) — [Junie docs](https://junie.jetbrains.com/docs/junie-cli.html).
- Secret protection is mostly read-deny plus not leaking via the model: `~/.ssh` is unreadable except `config`/`known_hosts`, and ssh-agent is used via socket (Junie) — [Junie docs](https://junie.jetbrains.com/docs/junie-cli.html); `Read(...)` deny paths are hidden from sandboxed commands (Devin) — [Devin CLI: Sandbox](https://docs.devin.ai/cli/sandbox.md); `.cursorignore` files are made unreadable via Landlocked overlay copies (Cursor) — [Cursor blog](https://cursor.com/blog/agent-sandboxing); Kilo explicitly says the sandbox "is a write boundary, not a privacy boundary" — [Kilo docs](https://github.com/Kilo-Org/kilocode/blob/main/packages/kilo-docs/pages/getting-started/settings/sandboxing.md); OpenHands masks secret values in command output — [OpenHands SDK secrets](https://docs.openhands.dev/sdk/guides/secrets.md).
- Network: a loopback HTTP(S) proxy with a host allowlist (Zed, Kilo, Devin). Kilo additionally checks TLS SNI, resolves DNS outside the sandbox, and rejects private addresses. Cursor blocks RFC1918 and metadata IPs by default. Non-proxy-aware tools (SSH, raw TCP) break. — [Zed docs](https://zed.dev/docs/ai/sandboxing), [Kilo docs](https://github.com/Kilo-Org/kilocode/blob/main/packages/kilo-docs/pages/getting-started/settings/sandboxing.md), [Devin CLI: Sandbox](https://docs.devin.ai/cli/sandbox.md), [Cursor sandbox.json reference](https://cursor.com/docs/reference/sandbox).
- Windows status: Cursor uses WSL2 — [Cursor blog](https://cursor.com/blog/agent-sandboxing); Zed uses WSL with weaker guarantees on NTFS — [Zed docs](https://zed.dev/docs/ai/sandboxing); Kilo has no backend — [Kilo docs](https://github.com/Kilo-Org/kilocode/blob/main/packages/kilo-docs/pages/getting-started/settings/sandboxing.md); Devin hard-fails — [Devin CLI: Sandbox](https://docs.devin.ai/cli/sandbox.md); Junie is not available — [Junie docs](https://junie.jetbrains.com/docs/junie-cli.html).

### Inferences
- For MossCode, the reusable architecture is: (1) a `SandboxPolicy` object (writable roots, protected subpaths, read-deny paths, network mode and allowed hosts) built from user and global config, where project config can only tighten it; (2) per-OS backends (Seatbelt profile generation on macOS, bwrap or Landlock on Linux, and a native Windows backend designed separately); (3) structured "denied by sandbox" results in tool output, plus an escalation tool or argument with a required reason; (4) a startup self-test with an explicit fail-closed or fallback policy shown in the TUI.
- Because MossCode's main user is on Windows 11 and other agents' WSL approaches don't confine native Windows tools, the Windows backend is the critical-path design problem. The existing agents offer policy and UX patterns for it, but no implementation to borrow.

### Gaps
- No agent in this set documents a native Windows sandbox (AppContainer, restricted token, Windows Sandbox, Job-object-based filesystem/network limits). The Codex CLI Windows sandbox is outside this note's scope.
