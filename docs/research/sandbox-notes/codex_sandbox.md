# OpenAI Codex CLI (codex-rs) sandbox design

Research snapshot: source read from a sparse clone of `openai/codex` at commit `ed8eac40832e6a79f30eaeb3c521912f231d43eb` (committed 2026-11-05; latest tags `rust-v0.168.0-alpha.3`, 2026-11-05). Official docs fetched 2026-11-05 from learn.chatgpt.com (developers.openai.com/codex/* now 308-redirects there). Abbreviations below: `SRC` = `https://github.com/openai/codex/blob/main/` (paths were read at the commit above). Release-version attributions come from the official changelog page https://learn.chatgpt.com/docs/changelog.

## 1. Sandbox modes, writable roots, protected paths, config keys

### Takeaway
Codex has three legacy modes (`read-only`, `workspace-write`, `danger-full-access`) that are now expressed as built-in *permission profiles* (`:read-only`, `:workspace`, `:danger-full-access`) with a richer per-path `read`/`write`/`deny` grammar. In `workspace-write`, reads are broad, writes are limited to cwd + temp dirs + extra roots, network is off by default, and `.git` / `.codex` / `.agents` / `.aws` under each writable root stay read-only.

### Cited Findings
- `sandbox_mode` = `read-only | workspace-write | danger-full-access`; `sandbox_workspace_write.writable_roots` (extra writable roots), `.network_access` (allow outbound network), `.exclude_tmpdir_env_var` (drop `$TMPDIR`), `.exclude_slash_tmp` (drop `/tmp`) — [Config reference](https://learn.chatgpt.com/docs/config-file/config-reference)
- Newer config: `default_permissions` selects a profile; built-ins are `:read-only`, `:workspace`, `:danger-full-access`; it must not be combined with `sandbox_mode` / `[sandbox_workspace_write]` — [Config reference](https://learn.chatgpt.com/docs/config-file/config-reference)
- Custom profiles: `[permissions.<name>]` with `extends`, `filesystem.<path-or-glob> = "read" | "write" | "deny"`, special tokens such as `:minimal` and `:workspace_roots`, `filesystem.":workspace_roots"."**/*.env" = "deny"`, `glob_scan_max_depth`, and `network.*` keys (enabled, domains, unix_sockets, allow_local_binding, mode = limited|full, ...) — [Config reference](https://learn.chatgpt.com/docs/config-file/config-reference)
- Admins can enforce read denials in `requirements.toml` (`permissions.filesystem.deny_read`), which users cannot weaken — [Config reference](https://learn.chatgpt.com/docs/config-file/config-reference)
- Semantics (docs): `read-only` = inspect files, no edits or commands without approval; `workspace-write` = read files, edit within the workspace, run routine local commands; `danger-full-access` = no sandbox — [Sandbox concept page](https://learn.chatgpt.com/docs/sandboxing)
- "The workspace includes the current directory and temporary directories like /tmp"; `/status` shows them — [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)
- Protected paths in writable roots: `<root>/.git` read-only whether dir or file; if `.git` is a `gitdir:` pointer file the resolved git dir is also read-only; `<root>/.agents`, `<root>/.codex`, `<root>/.aws` read-only when they exist as directories; protection is recursive — [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)
- Linux implementation of the same: protected subpaths (`.git`, resolved `gitdir:`, `.codex`) re-applied as `--ro-bind`; symlinks or not-yet-existing protected paths inside writable roots are blocked by mounting `/dev/null` on the symlink or first missing component — [linux-sandbox/README.md](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md)
- Windows implementation: unit tests assert `.git` dir, `.git` file, `.codex`, `.agents`, `.aws` inside a writable root are denied write, and skipped when missing — [windows-sandbox-rs/src/allow.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/allow.rs)
- Windows: missing deny-write carveouts are "materialized" as directories before the command runs so the sandbox cannot create the path later under a writable parent and bypass the carveout — [windows-sandbox-rs/src/setup_provisioning.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/setup_provisioning.rs) (comment near line 1141)
- Default recommendation at launch: version-controlled folders → Auto (workspace-write + on-request); non-version-controlled → read-only; may stay read-only until the directory is trusted — [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)
- Denied-read paths are enforced only inside the sandbox, so when a deny-read policy is active, a `require_escalated` request does *not* drop the sandbox: "bypassing the sandbox would silently grant those reads, so escalation must keep the command sandboxed with the denied reads intact" — [core/src/tools/sandboxing.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/sandboxing.rs) (lines ~288-310)
- `codex sandbox macos|linux|windows [--permissions-profile <name>] [COMMAND]` runs an arbitrary command under the sandbox for testing (aliases `codex debug`, `codex sandbox seatbelt`, `codex sandbox landlock`) — [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)

### Inferences
- The mode → profile shift means the real design primitive is a declarative list of (path, access) entries plus a network block, with each OS backend compiling it (SBPL, bwrap args, Windows ACL + capability SIDs, MXC policy). That compiler design maps well onto a Python implementation.
- Protecting `.git` (incl. hooks) and the agent's own config dir inside the writable workspace is the key detail: otherwise a sandboxed command could plant a git hook or rewrite agent config that runs later *outside* the sandbox.

### Gaps
- I did not find a single doc listing the exact default writable roots per OS for `:workspace` on Windows (code shows TEMP/TMP env-var directories are included unless excluded — tests `includes_tmp_env_vars_when_requested` / `ignores_unix_slash_tmp_for_windows_allow_roots` in [allow.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/allow.rs) — but no prose doc).

## 2. Approval policies and escalation

### Takeaway
Current values are `on-request` (default interactive), `never`, and `granular`; `untrusted` is retired as a user setting (kept internally for untrusted projects) and `on-failure` is now only a serde alias of `on-request`. Escalation is primarily *model-initiated*: the shell tool has a `sandbox_permissions: "require_escalated"` parameter plus a user-facing `justification` and optional reusable `prefix_rule`; automatic "sandbox failed → ask to rerun unsandboxed" exists only for the untrusted policy (and granular with `sandbox_approval = true`).

### Cited Findings
- `AskForApproval` enum: `UnlessTrusted` (serde `untrusted`, "Internal policy for projects marked untrusted. Commands require approval unless an explicit exec policy rule allows them"), `OnRequest` (`#[serde(alias = "on-failure")]`, "The model decides when to ask"), `Granular(GranularApprovalConfig)`, `Never` ("Failures are immediately returned to the model, and never escalated to the user") — [protocol/src/protocol.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/protocol.rs) (~line 1160)
- Docs: "Codex and ChatGPT Work no longer support `approval_policy = "untrusted"`"; replacement is `[projects."/path"] trust_level = "untrusted"`, which makes commands require approval unless an execpolicy rule allows them — [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)
- Granular fields: `sandbox_approval`, `rules`, `mcp_elicitations`, `request_permissions`, `skill_approval`; `false` auto-rejects that category — [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security); [protocol.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/protocol.rs)
- Per-command override enum `SandboxPermissions`: `use_default`, `require_escalated` ("Request to run outside the sandbox"), `with_additional_permissions` ("stay in the sandbox while widening permissions for this command only") — [protocol/src/models.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/models.rs) (~line 61)
- Shell tool JSON schema adds `sandbox_permissions`, `justification` ("User-facing approval question for `require_escalated`"), `prefix_rule` ("Reusable approval prefix ... e.g. [\"git\", \"pull\"]"), and optionally `additional_permissions` (a permission-profile object) — [core/src/tools/handlers/shell_spec.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/handlers/shell_spec.rs) (~line 225)
- Model prompt for on-request: if an important command "fails because of sandboxing or with a likely sandbox-related network error (DNS/host resolution, registry/index access, dependency download failure), rerun the command with `require_escalated`"; escalate for writes outside writable dirs, GUI apps, or unrequested destructive actions (`rm`, `git reset`); don't request broad prefix rules like `["python3"]`; never for `rm` or heredocs. Compound commands are split at `|`, `&&`, `||`, `;`, subshells and each segment checked; commands with redirection, substitution, env assignments or globs are not matched against rules — [prompts/templates/permissions/approval_policy/on_request.md](https://github.com/openai/codex/blob/main/codex-rs/prompts/templates/permissions/approval_policy/on_request.md)
- Orchestrator flow: (1) approval check, (2) first attempt under the selected sandbox, (3) on sandbox denial, if the policy wants a no-sandbox approval, ask the user with a `retry_reason` (either "Network access to "<host>" is blocked by policy." or a reason built from the output) and rerun with `RequireEscalated`; "Under `Never` or `OnRequest`, do not retry without sandbox; surface a concise sandbox denial that preserves the original output" (exception: an on-request network-approval prompt when a network-policy decision is available) — [core/src/tools/orchestrator.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/orchestrator.rs) (~lines 395-560)
- `wants_no_sandbox_approval`: `UnlessTrusted → true`, `Never → false`, `OnRequest → false`, `Granular → sandbox_approval` — [core/src/tools/sandboxing.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/sandboxing.rs) (line 349)
- Default approval requirement: Never = do not ask; OnRequest = "ask unless filesystem access is unrestricted"; UnlessTrusted = always ask; a command allow rule "does not authorize removing filesystem restrictions" — only approval of an explicit escalation may widen the filesystem — [core/src/tools/sandboxing.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/sandboxing.rs) (lines ~195-270)
- Session-scoped approval cache: "If the user approves for session, we store the decision for each key individually" — [core/src/tools/sandboxing.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/sandboxing.rs) (lines ~66-71)
- `approvals_reviewer = "auto_review"` routes approval requests (sandbox escalations, blocked network requests, request_permissions) through a reviewer model; failures fail closed — [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)

### Inferences
- The design separates *what may run* (sandbox) from *when to ask* (approval policy), and escalation is a typed field on the tool call rather than parsing failure text. MossCode's existing approval prompt could be extended with an equivalent `require_escalated` + `justification` argument on its shell tool.
- The orchestrator's "first attempt sandboxed → on denial, offer an unsandboxed retry" loop is only enabled for the strictest policy; for on-request Codex relies on the model to re-issue the call with `require_escalated`.

### Gaps
- How sandbox *denial* is detected for non-network cases (exit-code / stderr heuristics) lives in `build_denial_reason_from_output` and `sandboxing/src/denial.rs`; I did not read them in detail.

## 3. macOS: Seatbelt

### Takeaway
Codex builds an SBPL profile string at runtime (closed-by-default base inspired by Chromium's sandbox, plus generated file-read/write rules with `-D` parameters and optional network rules) and runs `/usr/bin/sandbox-exec -p <policy> -DKEY=path ... -- cmd`.

### Cited Findings
- Only `/usr/bin/sandbox-exec` is used, "to defend against an attacker trying to inject a malicious version on the PATH" — [sandboxing/src/seatbelt.rs](https://github.com/openai/codex/blob/main/codex-rs/sandboxing/src/seatbelt.rs) (line ~57)
- Base policy: `(deny default)`; allow `process-exec`, `process-fork`, `signal (target same-sandbox)`, write to `/dev/null`, a whitelist of `sysctl-read` names, `mach-lookup` of `com.apple.system.opendirectoryd.libinfo` and `com.apple.PowerManagement.control`, `ipc-posix-sem`, KMP shm, `pseudo-tty` and `/dev/ptmx` / `/dev/ttys*` access; comments cite Chromium's `common.sb` / `renderer.sb` — [sandboxing/src/seatbelt_base_policy.sbpl](https://github.com/openai/codex/blob/main/codex-rs/sandboxing/src/seatbelt_base_policy.sbpl)
- Filesystem rules are generated as `(allow file-read* ...)` / `(allow file-write* (subpath (param "WRITABLE_ROOT_n")))` with `(require-not (subpath (param ...)))` carve-outs for protected subpaths, deny regexes for deny-read globs, and `(deny file-write-unlink ...)` on protected directories so renaming an ancestor cannot relocate protected paths; full read access is `(allow file-read*)` — [seatbelt.rs](https://github.com/openai/codex/blob/main/codex-rs/sandboxing/src/seatbelt.rs) (lines ~494-660, 927-1060)
- Also emitted: `(deny mach-lookup (xpc-service-name-prefix ""))` and `(deny system-fcntl (fcntl-command 80 110))` because F_MAKECOMPRESSED / F_TRANSFEREXTENTS "mutate files through read-only descriptors" — [seatbelt.rs](https://github.com/openai/codex/blob/main/codex-rs/sandboxing/src/seatbelt.rs) (lines ~1045-1063)
- Network: nothing is emitted when network is disabled (deny-default blocks it). With network enabled and no proxy: `(allow network-outbound)(allow network-inbound)` plus `seatbelt_network_policy.sbpl` (AF_SYSTEM sockets, mach services for DNS config, trustd/ocspd TLS). With a managed proxy: only `(allow network-outbound (remote ip "localhost:<port>"))` for proxy ports (plus loopback when `allow_local_binding`); if proxy config exists but no endpoint can be inferred, it fails closed — [seatbelt.rs](https://github.com/openai/codex/blob/main/codex-rs/sandboxing/src/seatbelt.rs) (lines ~316-378); [seatbelt_network_policy.sbpl](https://github.com/openai/codex/blob/main/codex-rs/sandboxing/src/seatbelt_network_policy.sbpl)
- With restricted read access, Codex appends a curated macOS platform policy "instead of broadly allowing /System" — [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)

### Inferences
- `sandbox-exec` is deprecated by Apple but still the practical choice; MossCode could reuse the same pattern (static base `.sbpl` + generated parameterized rules) from Python via `subprocess`.

### Gaps
- None material for MossCode's goals.

## 4. Linux: bubblewrap + seccomp (Landlock is legacy)

### Takeaway
Codex has moved from Landlock to **bubblewrap** as the default (and, for filesystem-restricted policies, mandatory) filesystem sandbox; seccomp handles network syscalls. The helper is `codex-linux-sandbox` (also reachable via arg0 dispatch of the main binary). WSL1 lost support in 0.115 because of this move.

### Cited Findings
- "The helper uses bubblewrap for filesystem and namespace isolation, and seccomp for syscall filtering"; Landlock is "legacy" and "rejected for these policies because it cannot isolate app-server Unix sockets" — [linux-sandbox/README.md](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md)
- bwrap discovery: first `bwrap` on `PATH` outside the cwd; fallback to bundled `codex-resources/bwrap`; startup warning if missing or user namespaces fail; old bwrap without `--argv0` gets a compatibility path — [linux-sandbox/README.md](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md); changelog entry #51211 "Reject sandbox-writable bubblewrap executables from PATH" — [Changelog](https://learn.chatgpt.com/docs/changelog)
- Mount layout: `--ro-bind / /` (read-only root), `--bind <root> <root>` for writable roots, `--ro-bind` for protected subpaths; specificity-ordered overlay so `/repo=write, /repo/a=none, /repo/a/b=write` works; deny-read globs expanded before launch with `rg --files --hidden --no-ignore --glob` (fallback internal walker) and masked — [linux-sandbox/README.md](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md)
- Namespaces: `--unshare-user`, `--unshare-pid` by default, fresh `--proc /proc` (falls back to inherited /proc if denied); `--unshare-net` when network is restricted — [linux-sandbox/README.md](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md)
- seccomp (after `PR_SET_NO_NEW_PRIVS`, applied in-process after the filesystem view is established): restricted-network mode denies `connect`, `accept`, `accept4`, `bind`, `listen`, `getpeername`, `getsockname`, `shutdown`, `sendto`, `sendmmsg`, `recvmmsg`, `getsockopt`, `setsockopt`, and limits `socket`/`socketpair` to `AF_UNIX`; all modes deny `io_uring_*`; also denies `ptrace`, `process_vm_readv/writev`; `AF_VSOCK` blocked even when network is allowed — [linux-sandbox/src/seccomp.rs](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/src/seccomp.rs) (lines ~176-250); [README](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md)
- Managed-proxy mode: `--unshare-net` plus an internal TCP→UDS→TCP bridge so tool traffic only reaches configured proxy endpoints; new standalone `AF_UNIX` sockets blocked unless `dangerously_allow_all_unix_sockets` — [linux-sandbox/README.md](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md)
- Legacy Landlock path: read access to the whole filesystem, write only to `/dev/null` and writable roots — [seccomp.rs](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/src/seccomp.rs) (line ~139)
- Docs: "Linux uses bwrap plus seccomp by default"; "WSL1 was supported through Codex 0.114; starting in 0.115, the Linux sandbox moved to bwrap, so WSL1 is no longer supported" — [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)
- Limitations: users must install bubblewrap; bundled helper needs unprivileged user namespaces; Ubuntu 24.04 needs the `bwrap-userns-restrict` AppArmor profile (or `kernel.apparmor_restrict_unprivileged_userns=0`) — [Sandbox concept page](https://learn.chatgpt.com/docs/sandboxing)
- Containers: the sandbox "may not work if the host or container configuration blocks the namespace, setuid bwrap, or seccomp operations"; recommended to let Docker/Dev Containers be the boundary and run `--sandbox danger-full-access` inside — [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)
- Process hardening of Codex itself (pre-main): disable core dumps, disable ptrace attach on Linux/macOS, strip `LD_PRELOAD` / `DYLD_*` — [process-hardening/README.md](https://github.com/openai/codex/blob/main/codex-rs/process-hardening/README.md)

### Inferences
- For a Python agent, invoking a system `bwrap` with generated args is easy; seccomp needs either a helper binary or `pyseccomp`/libseccomp bindings. A plain `--unshare-net` in bwrap already gives "no network" without seccomp.

### Gaps
- I did not pin the exact first release where bwrap became default beyond the doc statement about 0.115.

## 5. Windows (special depth)

### Takeaway
Codex now ships **three** native Windows backends: **`mxc`** (recommended on supported Windows 11 builds; uses Microsoft Execution Containers via `mxc-sdk`, no admin setup), **`elevated`** (preferred legacy fallback: dedicated local sandbox accounts + restricted tokens + capability-SID ACLs + firewall/WFP rules, needs one UAC-approved setup), and **`unelevated`** (restricted token derived from the current user + ACLs; network blocking only via environment variables; no deny-read). WSL2 is a supported alternative (uses the Linux sandbox), but the docs now say to use the native Windows sandbox by default. Code lives in `codex-rs/windows-sandbox-rs` (~27.6k lines), `codex-rs/windows-sandbox-service`, and `codex-rs/mxc-sandbox`.

### Cited Findings

**Backends and selection**
- Docs list the three implementations: `mxc` "recommended ... without administrator-approved setup, additional Windows accounts, or local firewall rules"; `elevated` "preferred legacy fallback ... Requires administrator-approved setup. Commands in the sandbox run without administrator privileges"; `unelevated` "legacy fallback ... weaker network isolation than elevated and doesn't support denied read paths" — [Windows sandbox docs](https://learn.chatgpt.com/docs/windows/windows-sandbox)
- Config: `[windows] sandbox = "mxc" | "elevated" | "unelevated"`; `[features] prefer_mxc = true` (auto-select MXC with legacy fallback); admin `requirements.toml`: `[windows] allow_mxc = false`, `allowed_sandbox_implementations = ["elevated"]` — [Windows sandbox docs](https://learn.chatgpt.com/docs/windows/windows-sandbox); [Config reference](https://learn.chatgpt.com/docs/config-file/config-reference)
- Internal enum `WindowsSandboxLevel { Disabled, RestrictedToken, Elevated }` (restricted token = unelevated) — [protocol/src/config_types.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/config_types.rs) (~line 305)
- Both legacy modes use a private desktop by default ("for stronger UI isolation"; desktop name prefix `CodexSandboxDesktop-<random>`) — [Windows sandbox docs](https://learn.chatgpt.com/docs/windows/windows-sandbox); [windows-sandbox-rs/src/desktop.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/desktop.rs)
- Version support: Windows 11 recommended; recent Windows 10 "best effort" (needs ConPTY, 1809+) — [Windows sandbox docs](https://learn.chatgpt.com/docs/windows/windows-sandbox)
- Timeline (changelog PR titles): "Add a native Windows MXC sandbox adapter" #42841 listed under CLI 0.154.0; "Add an opt-in preference for the local MXC sandbox" #47375 under 0.157.0; "Always use private desktops for legacy Windows sandboxes" #46554 and "Default local binding to true for MXC managed networking" #46523 under 0.156.0; "Add experimental Windows sandbox service provisioning" #42353 under 0.154.0; "Add a CLI command to uninstall the legacy Windows sandbox" #50437 under 0.162.0 — [Changelog](https://learn.chatgpt.com/docs/changelog)

**Core primitive (both legacy modes): write-restricted token + capability SIDs**
- `CreateRestrictedToken(base, DISABLE_MAX_PRIVILEGE | LUA_TOKEN | WRITE_RESTRICTED, ...)` with restricting SIDs in order: capability SIDs…, extra restricting SIDs (the sandbox user's SID in elevated mode), logon SID, Everyone. Then a default DACL limited to the logon SID ("must not grant access to another launch's processes, threads, or IPC") and only `SeChangeNotifyPrivilege` enabled — [windows-sandbox-rs/src/token.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/token.rs) (lines ~370-530)
- Capability SIDs are random SIDs persisted under CODEX_HOME: one per workspace cwd (used "to isolate workspaces from other workspace sandbox writes and to apply per-workspace denies (e.g. protect `CWD/.codex`)") and one per extra writable root, included in a token "only when the root is currently allowed, so stale ACLs from earlier extra roots do not expand later workspace sandboxes" — [windows-sandbox-rs/src/cap.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/cap.rs)
- Writable roots get allow-ACEs for the capability SID; protected children get deny-write ACEs; `workspace_acl.rs` has `protect_workspace_codex_dir` / `protect_workspace_agents_dir` — [windows-sandbox-rs/src/workspace_acl.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/workspace_acl.rs); [spawn_prep.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/spawn_prep.rs)
- Unelevated limitation in code: "WRITE_RESTRICTED tokens consult restricting SIDs only for writes, so this backend cannot make capability-SID deny-read ACLs authoritative"; it bails with "deny-read overrides require the elevated Windows sandbox backend" and "Restricted read-only access requires the elevated Windows sandbox backend" — [windows-sandbox-rs/src/unified_exec/backends/legacy.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/unified_exec/backends/legacy.rs) (lines ~358-365)
- CODEX_HOME, `CODEX_HOME/.sandbox`, `.sandbox-bin`, `.sandbox-secrets` are filtered out of capability write roots ("must remain tamper-resistant") — [windows-sandbox-rs/src/setup.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/setup.rs) (`filter_sensitive_write_roots`, ~line 1454)
- Docs: Codex warns when folders are "writable by Everyone" because the sandbox cannot protect them (the token includes Everyone as a restricting SID) — [Windows sandbox docs](https://learn.chatgpt.com/docs/windows/windows-sandbox); [token.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/token.rs)

**Unelevated network handling**
- Offline is enforced only via environment rewriting: `HTTP(S)_PROXY`/`ALL_PROXY`/`GIT_HTTP(S)_PROXY` = `http://127.0.0.1:9`, `PIP_NO_INDEX=1`, `NPM_CONFIG_OFFLINE=true`, `CARGO_NET_OFFLINE=true`, `GIT_SSH_COMMAND="cmd /c exit 1"`, plus a "denybin" dir of `.bat`/`.cmd` stubs that `exit /b 1` prepended to PATH (with PATHEXT reordered) — [windows-sandbox-rs/src/env.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/env.rs) (lines ~105-160)
- Docs: unelevated "uses environment-level offline controls instead of the dedicated offline-user firewall rule" — [Windows sandbox docs](https://learn.chatgpt.com/docs/windows/windows-sandbox)

**Elevated: setup**

- "Routes a command through the current Codex executable and directly into Microsoft's MXC `BaseContainerRunner` ... never invokes MXC's AppContainer dispatcher, edits host ACLs, creates sandbox users, runs setup, or requests elevation"; depends on `mxc-sdk` 1.0.0 from `github.com/microsoft/mxc` (pinned git rev) — [mxc-sandbox/README.md](https://github.com/openai/codex/blob/main/codex-rs/mxc-sandbox/README.md); Cargo.lock entry `mxc-sdk` (`git+https://github.com/microsoft/mxc?rev=b2112016...`)

### Inferences
- The **unelevated** design is the most portable to MossCode (pure user-mode Win32 via `ctypes`/`pywin32`): `CreateRestrictedToken(WRITE_RESTRICTED|DISABLE_MAX_PRIVILEGE|LUA_TOKEN)` with a random capability SID added to the workspace's DACL, then `CreateProcessAsUserW` with that token in a Job Object. It gives write confinement with no admin rights, but no read confinement and only advisory network blocking (env vars + stub binaries). Two costs: ACEs are added to the user's real workspace dirs (and must be maintained), and anything ACL'd "Everyone: write" leaks.
- The **elevated** design adds the real security properties (separate principal → per-user firewall/WFP scoping and enforceable deny-read) but needs one UAC setup that creates hidden local accounts, stores DPAPI-encrypted passwords, edits firewall/WFP, and grants ACLs across the user profile. That is a large amount of privileged, failure-prone machinery; Codex has spent many releases fixing setup edge cases (error 1385, expired passwords, long paths, enterprise policies — see changelog).
- **MXC** is Microsoft's own container primitive and appears to be where Codex is heading; it requires very recent Windows 11 builds. The user's machine reports `10.0.26300` (Windows 11 Insider-range build), which may or may not have MXC capability enabled — this must be probed, not assumed. `mxc-sdk` is a Rust crate; a Python agent would need either the same native API via FFI or to shell out to a helper.
- Codex did not adopt AppContainer for its own backends (MXC README explicitly says it avoids MXC's AppContainer dispatcher); likely reasons are AppContainer's heavy read restrictions breaking developer tools, but this is not stated in the sources.

### Gaps
- Exact logon type and LSA rights required by the sandbox users (error 1385) are not enumerated in code I read (no `LsaAddAccountRights` in the files grepped).
- No official statement labels elevated/unelevated as "experimental" any more; docs call them "legacy fallback". The original 2025 "experimental Windows sandbox" announcement was not located in the fetched changelog text.
- MXC's public Microsoft documentation (github.com/microsoft/mxc) was not fetched.

## 6. Network policy

### Takeaway
Network is off by default in `workspace-write` (and read-only). Enabling it is a boolean; an optional managed proxy (`codex-network-proxy`, HTTP + SOCKS5 on loopback) enforces allowlist-first domain rules, with OS-level rules forcing traffic through it.

### Cited Findings
- "By default, the agent runs with network access turned off"; enable with `[sandbox_workspace_write] network_access = true` — [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)
- `features.network_proxy` changes enforcement but grants nothing: network off + proxy on = off; on + proxy off = unrestricted direct; on + proxy on = constrained by policy; domain rules allowlist-first (`*.example.com`, `**.example.com`, global `*`), deny wins; `allow_local_binding = false` blocks loopback/link-local/private; hostnames resolving to private IPs are blocked; best-effort DNS-rebinding check — [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)
- Proxy defaults: HTTP `127.0.0.1:3128`, SOCKS5 `127.0.0.1:8081`; `mode = "limited"` is a read-only mode that turns on HTTPS MITM, with CA bundle env vars injected into commands — [network-proxy/README.md](https://github.com/openai/codex/blob/main/codex-rs/network-proxy/README.md)
- The proxy does not filter web search, MCP, connectors, or Codex's own model/auth traffic — [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)
- A full-sandbox escalation approval can bypass the command proxy — [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)
- Per-OS enforcement: macOS SBPL allows only `localhost:<proxyport>` (§3); Linux `--unshare-net` + seccomp + TCP→UDS bridge (§4); Windows elevated firewall rules permitting loopback proxy ports for the offline user (§5); MXC loopback-only (§5); Windows unelevated only env vars (§5).
- Blocked network requests can be turned into approval prompts ("Network access to "<host>" is blocked by policy.") — [core/src/tools/orchestrator.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/orchestrator.rs)

### Inferences
- A loopback proxy + "block everything except loopback:proxy port" at the OS level is a reusable pattern; on Windows it needs a distinct principal (or MXC) to scope firewall rules, which is why unelevated cannot do it.

### Gaps
- None material.

## 7. Secret protection

### Takeaway
Codex's env filtering is weak by default: `shell_environment_policy` inherits **all** variables and `ignore_default_excludes` defaults to **true**, so `*KEY*`/`*SECRET*`/`*TOKEN*` variables are passed unless the user opts in. Only a short hard-coded list of Codex-internal tokens is always stripped. Sandboxed commands generally can read `~/.codex/auth.json`, since default read access is broad on all platforms; no code that denies it was found.

### Cited Findings
- `ShellEnvironmentPolicy` algorithm: inherit (`all` default | `core` | `none`) → default excludes `*KEY*`, `*SECRET*`, `*TOKEN*` *only if* `ignore_default_excludes` is false → `exclude` → `set` → `include_only`; `Default` has `inherit: All, ignore_default_excludes: true` — [protocol/src/config_types.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/config_types.rs) (~lines 205-270)
- Docs confirm: `ignore_default_excludes` "Keep variables containing KEY, SECRET, or TOKEN ... (default: true). Set to false to apply automatic secret-name exclusions"; new `shell_environment_policy.filters` map — [Config reference](https://learn.chatgpt.com/docs/config-file/config-reference)
- Always-stripped `NON_INHERITABLE_ENV_VARS`: `CODEX_EXEC_SERVER_NOISE_AUTH_TOKEN`, `NODE_REPL_AUTH_TOKEN`, `CODEX_GUARDIAN_DECISIONS_API_KEY`, `OPENAI_FEDERATION_RULE_ID`, `OPENAI_IDENTITY_TOKEN_FILE`, `OPENAI_WORKLOAD_IDENTITY_CONTEXT` ("model-reachable child processes must not inherit") — [protocol/src/shell_environment.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/shell_environment.rs)
- No reference to `auth.json` was found in `sandboxing/`, `linux-sandbox/`, `windows-sandbox-rs/`, or `core/src/config` (grep at the snapshot commit) — [repo tree](https://github.com/openai/codex/tree/main/codex-rs)
- Docs warn that in `danger-full-access` inside a devcontainer "a malicious project can exfiltrate anything available inside the devcontainer, including Codex credentials" — [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)
- Windows elevated read grants exclude `.ssh`, `.gnupg`, `.aws`, `.azure`, `.kube`, `.docker`, `.config`, `.npm`, `.pki`, `.terraform.d`, `.tsh`, `.brev` at the top of `%USERPROFILE%`, but not `.codex` — [windows-sandbox-rs/src/setup.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/setup.rs) (lines 59-72)
- Users can deny reads of secrets via profiles (e.g. `"**/*.env" = "none"/"deny"`), and admins via `permissions.filesystem.deny_read` — [linux-sandbox/README.md](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md); [Config reference](https://learn.chatgpt.com/docs/config-file/config-reference)
- Changelog entry "Add opt-in credential masking for proxied sandboxed sessions" (#52302, 0.163.0) — [Changelog](https://learn.chatgpt.com/docs/changelog)

### Inferences
- With default settings a sandboxed command can likely read `~/.codex/auth.json` on macOS (`(allow file-read*)`), Linux (`--ro-bind / /`), Windows unelevated (WRITE_RESTRICTED leaves reads unrestricted), and Windows elevated (`.codex` is not in the exclusion list). This is inferred from the code, not stated in docs. MossCode, which keeps keys in the OS credential manager, is already better placed. Its sandbox should still deny-read `~/.mosscode/` and strip key-like env vars by default.

### Gaps
- Not verified whether OpenAI's keyring-backed credential storage (`codex-rs/keyring-store`) is the default for auth on any platform, which would change the auth.json exposure.
