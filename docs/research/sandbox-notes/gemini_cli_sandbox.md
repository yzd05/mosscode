Snapshot: `google-gemini/gemini-cli` `main` branch read on 2026-11-05 (latest release v0.67.0, published 2026-11-04); `QwenLM/qwen-code` `main` read on 2026-11-05 (latest release v0.26.7, 2026-11-04). Both are Apache-2.0. Source files were read directly from raw.githubusercontent.com. Links below point to `main`, so line content may drift after this date.

Abbreviations: `G/` = `https://github.com/google-gemini/gemini-cli/blob/main/`, `Q/` = `https://github.com/QwenLM/qwen-code/blob/main/`. Every link is written out in full.

## 1. How sandboxing is enabled, and what gets sandboxed (the whole process or each command)

### Takeaway
Gemini CLI now has **two separate sandbox layers**. (a) The older **whole-process sandbox** (`-s/--sandbox`, `GEMINI_SANDBOX`, `tools.sandbox`; the settings schema now calls it "Legacy full-process sandbox") relaunches the entire CLI inside sandbox-exec, Docker, Podman, gVisor or LXC. (b) Since v0.35 (2026-03) there is a **per-tool OS sandbox** (`security.toolSandboxing: true`, off by default). It wraps each shell command and file read/write in bubblewrap+seccomp on Linux, a generated Seatbelt profile on macOS, or a restricted-token, Low-integrity, Job-object helper on Windows. Per-command network and filesystem permissions in (b) follow the approval mode. The design that suits MossCode is (b).

### Cited Findings
- Documented ways to enable it, in order of precedence: `-s`/`--sandbox` flag; `GEMINI_SANDBOX=true|docker|podman|sandbox-exec|runsc|lxc`; `"tools": {"sandbox": true}` in `settings.json` — [G/docs/cli/sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)
- In the code the env var actually wins over the flag and settings ("environment variable takes precedence over argument (from command line or settings)"). The `--sandbox` flag works by setting `process.env.GEMINI_SANDBOX='true'`. Valid commands are `docker, podman, sandbox-exec, runsc, lxc, windows-native`. `runsc` is Linux-only and needs docker; `windows-native` is Windows-only — [G/packages/cli/src/config/sandboxConfig.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/config/sandboxConfig.ts), [G/packages/cli/src/config/config.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/config/config.ts)
- Auto-detection when the value is `true`: on macOS it picks `sandbox-exec` (Seatbelt) whenever it is available. Docker and then Podman are chosen only when the sandbox is explicitly true. runsc and lxc are never auto-detected. If `true` is requested and nothing is found, it raises a `FatalSandboxError` — [sandboxConfig.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/config/sandboxConfig.ts)
- `tools.sandbox` can also be an object `{enabled, command, image, allowedPaths, networkAccess}`. It is complemented by `tools.sandboxAllowedPaths` (default `[]`) and `tools.sandboxNetworkAccess` (default `false`). The schema describes `tools.sandbox` as "Legacy full-process sandbox execution environment" — [G/packages/cli/src/config/settingsSchema.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/config/settingsSchema.ts), [sandboxConfig.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/config/sandboxConfig.ts)
- **Whole-process mechanism:** if `SANDBOX` is unset and sandbox config resolves, `gemini.tsx` reads piped stdin, injects it into `--prompt`, and calls `start_sandbox(...)`, which re-runs the same CLI argv inside the sandbox. The parent waits and exits with the child's code. Inside the sandbox the env var `SANDBOX` is set (`SANDBOX=sandbox-exec` or the container name), which stops it recursing — [G/packages/cli/src/gemini.tsx](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/gemini.tsx), [G/packages/cli/src/utils/sandbox.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox.ts)
- **Tool sandboxing** is documented as "granular isolation for individual tool executions (like `shell_exec` and `write_file`) instead of sandboxing the entire Gemini CLI process … better integration with your local environment for non-tool tasks (like UI rendering and configuration loading)". The setting is `security.toolSandboxing` (default `false`, requires restart) — [docs/cli/sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md), [settingsSchema.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/config/settingsSchema.ts)
- The core `Config` sets `sandbox.enabled = sandbox.enabled || toolSandboxing`. `networkAccess` defaults to `false`, and the global temp dir is always included. `createSandboxManager()` then picks `WindowsSandboxManager` on win32, `LinuxSandboxManager` on linux, `MacOsSandboxManager` on darwin, and `NoopSandboxManager` (environment sanitization only) when disabled. When it is enabled, file tools are routed through `SandboxedFileSystemService`, so reads and writes also run through the sandbox (virtual `__read`/`__write` commands) — [G/packages/core/src/config/config.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/config/config.ts), [G/packages/core/src/services/sandboxManagerFactory.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/services/sandboxManagerFactory.ts), [G/packages/core/src/sandbox/linux/LinuxSandboxManager.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/sandbox/linux/LinuxSandboxManager.ts)
- The `SandboxManager` interface is `prepareCommand(req) -> {program, args, env, cwd, cleanup}`, `isKnownSafeCommand`, `isDangerousCommand`, `parseDenials(result)`, `getWorkspace`, `getOptions`. It rewrites the command into a wrapped invocation and does not run it itself — [G/packages/core/src/services/sandboxManager.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/services/sandboxManager.ts)
- Timeline from the official changelog: v0.34.0 (2026-03-17) added gVisor/runsc and experimental LXC. v0.35.0 (2026-03-24) added `SandboxManager` plus Linux bubblewrap/seccomp tool isolation. v0.36.0 (2026-04-01) added native macOS Seatbelt and Windows sandboxing for tools. v0.37.0 (2026-04-08) added dynamic sandbox expansion and worktree support for Linux/Windows. v0.58.0 (2026-09-01) blocked Docker sockets and binaries in Seatbelt. v0.60.0 (2026-09-15) isolated settings and temp dirs inside the sandbox — [G/docs/changelogs/index.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/changelogs/index.md)

### Inferences
- The two layers can stack. Inside a whole-process container the `SANDBOX` env is set, so `loadSandboxConfig` returns nothing and the inner tool sandbox is active only if `security.toolSandboxing` is true (for example bwrap inside Docker). This is inferred from code paths and not documented.
- For MossCode (Python/Textual, mainly Windows), the per-tool model fits much better than relaunching the TUI in a container. The UI, credentials and model transport stay on the host, and only the command's child process is wrapped.

### Gaps
- No official statement on whether `tools.sandbox` (whole-process) will be removed. It is only labelled "Legacy" in the schema.
- I did not find a Google blog post on the tool-sandbox redesign. The changelog and PRs (#21774, #22231, #22712, #23692) are the first-hand trail.

## 2. macOS Seatbelt: built-in profiles, custom profiles, proxy

### Takeaway
The whole-process Seatbelt mode runs `sandbox-exec -D TARGET_DIR=… -D TMP_DIR=… -D HOME_DIR=… -D CACHE_DIR=… -D INCLUDE_DIR_0..4=… -f <profile>.sb sh -c "SANDBOX=sandbox-exec … gemini <args>"`. All current profiles are `(deny default)`. They differ along two axes: read scope (permissive and restrictive allow reads anywhere, strict allows only an allowlist) and network (open, proxied to localhost:8877, or closed, which is now an alias). Writes are limited to the project, temp, cache, `~/.npm`, `~/.cache` and up to 5 include dirs. Every profile also blocks Docker/OrbStack/Colima sockets and binaries, blocks writes to `~/.gemini`, and blocks reads of Gemini credential files and `.env*`.

### Cited Findings
- `SEATBELT_PROFILE` selects the profile (default `permissive-open`). Documented built-ins: `permissive-open` (write restrictions, network allowed), `permissive-proxied`, `restrictive-open`, `restrictive-proxied`, `strict-open` (read and write restrictions, network allowed), `strict-proxied` — [docs/cli/sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)
- The code also lists `permissive-closed` and `restrictive-closed`, but they are only aliases: "Map standard 'closed' profiles to their strict counterparts for backward compatibility" (`permissive-closed` → `strict-open`, `restrictive-closed` → `strict-proxied`). No `.sb` files exist for them — [G/packages/cli/src/utils/sandboxBuiltinProfiles.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandboxBuiltinProfiles.ts), [G/packages/cli/src/utils/sandboxUtils.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandboxUtils.ts)
- `permissive-open.sb`: `(deny default)`, `(allow file-read*)` anywhere, `process-exec`/`process-fork` ("children inherit this policy, so they stay sandboxed"), sysctl reads (list taken from Chromium's sandbox), `file-write*` only to `TARGET_DIR`, `TMP_DIR`, `CACHE_DIR`, `$HOME/.npm`, `$HOME/.cache`, `INCLUDE_DIR_0..4`, `/dev/stdout|stderr|null|ptmx|ttys*`. Mach lookups for DNS, opendirectoryd and trustd. Inbound and bind on `*:*` (dev servers, OAuth callbacks), and unrestricted `network-outbound`. A comment says "do not switch to (allow default)" — [G/packages/cli/src/utils/sandbox-macos-permissive-open.sb](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox-macos-permissive-open.sb)
- `permissive-proxied.sb` is identical apart from the network rules: inbound only on `localhost:9229` (debugger), and outbound only `(remote tcp "localhost:8877")` — [G/packages/cli/src/utils/sandbox-macos-permissive-proxied.sb](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox-macos-permissive-proxied.sb)
- `restrictive-open.sb`: same write list but without `/dev/ptmx`. Only the `com.apple.sysmond` mach lookup, inbound only on the 9229 debugger port, and full outbound. It explicitly denies read/write on `/var/run/docker.sock`, `~/.docker/run`, `~/.colima`, `~/.orbstack/run`, `~/.rd`, and similar. It denies `process-exec` of docker, dockerd, podman, colima, orb and Docker.app/OrbStack.app/Rancher binaries, denies `com.docker.*` mach and XPC services, and denies `docker` POSIX shared memory. It denies `file-write*` under `$HOME/.gemini` and on `oauth_creds.json`, `gemini-credentials.json`, `mcp-oauth-tokens.json`, `a2a-oauth-tokens.json`, `google_accounts.json`, `trusted_hooks.json`, `trustedFolders.json`, `policy_integrity.json` and `/.env(.*)?`, and denies `file-read*` on the same credential files and `.env*` — [G/packages/cli/src/utils/sandbox-macos-restrictive-open.sb](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox-macos-restrictive-open.sb). `restrictive-proxied` differs only by outbound to `localhost:8877` — [G/packages/cli/src/utils/sandbox-macos-restrictive-proxied.sb](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox-macos-restrictive-proxied.sb)
- `strict-open.sb` replaces read-anywhere with a read allowlist: `/`, `TARGET_DIR`, `TMP_DIR`, `CACHE_DIR`, `~/.npm`, `~/.cache`, `~/.gitconfig`, `~/.nvm`, `~/.fnm`, `~/.node`, `~/.config`, include dirs, plus `/usr /bin /sbin /Library /System /private /dev /etc /opt /Applications`. It also allows `(allow file-read-metadata)` everywhere ("stat/lstat, NOT readdir or file content", needed for Node module resolution) — [G/packages/cli/src/utils/sandbox-macos-strict-open.sb](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox-macos-strict-open.sb), [G/packages/cli/src/utils/sandbox-macos-strict-proxied.sb](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox-macos-strict-proxied.sb)
- The Docker-socket and credential deny rules are also present in `permissive-open.sb` (grep found 7 matching lines) — [sandbox-macos-permissive-open.sb](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox-macos-permissive-open.sb)
- **Custom profiles:** if `SEATBELT_PROFILE` is not a built-in, the CLI loads `sandbox-macos-<name>.sb` from `~/.gemini/` first and then from the project `.gemini/`. `path.basename()` is applied "to prevent path traversal via SEATBELT_PROFILE". Built-ins missing on disk (bundled builds) are written to a 0600 temp file from embedded strings. `BUILD_SANDBOX` is rejected with Seatbelt — [G/packages/cli/src/utils/sandbox.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox.ts)
- Before launching, the CLI resolves cwd with `realpath`. It refuses to run if cwd is a "sensitive host directory": the home directory itself or any ancestor of it, `~/.gemini` or anything inside or above it, or a `.env*` or credential file. It creates a private `mkdtemp` dir `gemini-sandbox-*` (0700) as `TMP_DIR`/`TMPDIR`/`TMP`/`TEMP` and deletes it on exit. It fills exactly 5 `INCLUDE_DIR_i` params (unused ones set to `/dev/null`) from workspace include dirs plus `allowedPaths`, and skips sensitive ones — [sandbox.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox.ts), [sandboxUtils.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandboxUtils.ts)
- **Proxy:** when `GEMINI_SANDBOX_PROXY_COMMAND` is set, the CLI spawns that command (detached, `shell: true`) and sets `HTTPS_PROXY/https_proxy/HTTP_PROXY/http_proxy` to the existing proxy env or `http://localhost:8877`, and passes `NO_PROXY` through. It polls `curl http://localhost:8877` until the proxy is up and kills the sandbox if the proxy exits. The `*-proxied` profiles only allow outbound to `localhost:8877`, and the proxy must listen on `:::8877` (see `docs/examples/proxy-script.md`) — [sandbox.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox.ts), [sandbox-macos-permissive-proxied.sb](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox-macos-permissive-proxied.sb)
- **Per-tool macOS Seatbelt** (tool sandboxing) is a separate generated profile: `(deny default)` + `(import "system.sb")`, with exec, fork and same-sandbox signals allowed. Reads are allowed on the workspace (original and realpath) and on a temp path. Writes are allowed on the workspace only when the mode permits. Governance files (`.gitignore`, `.geminiignore`, `.git`) are denied for writing unless explicitly allowed, and `.git` stays protected even when the workspace is writable. Secret files (`.env`, `.env.*`) get `(deny file-read* file-write* (regex …))`. Forbidden paths are denied, and `NETWORK_SEATBELT_PROFILE` is appended only when network is allowed — [G/packages/core/src/sandbox/macos/baseProfile.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/sandbox/macos/baseProfile.ts), [G/packages/core/src/sandbox/macos/seatbeltArgsBuilder.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/sandbox/macos/seatbeltArgsBuilder.ts)

### Inferences
- The whole-process profiles deny reading `~/.gemini/oauth_creds.json` even though the CLI itself runs inside. That suggests authentication happens on the host before the relaunch (`gemini.tsx` exits with an auth error before entering the sandbox if the initial auth failed). I have not verified how OAuth tokens then reach the sandboxed process.
- The pattern worth borrowing is a parameterised policy template (`-D TARGET_DIR=…`) with a fixed number of include slots, plus a hard deny-list for the agent's own config and credentials and for container-runtime sockets, which is a known escape route.

### Gaps
- `docs/examples/proxy-script.md` (the allowlist proxy example) was not read.

## 3. Docker/Podman (and gVisor, LXC) container sandbox

### Takeaway
The container mode runs `docker|podman run -i --rm --init --entrypoint '' --workdir <same path> -v <cwd>:<same path> …`. Since v0.60 it no longer mounts `~/.gemini`. Instead it mounts a temp dir containing a sanitised copy of the user's `settings.json` (hooks, command hooks and API keys stripped) at `/home/node/.gemini` and forces `HOME=/home/node`. It forwards only a short allowlist of env vars (API keys, Vertex/GCP project vars, model, TERM). On Linux it maps the host UID/GID by starting as root, running `useradd`, then `su`. When `networkAccess` is false or a proxy is used, the network is an `--internal` docker network.

### Cited Findings
- Default image is `ghcr.io/google/gemini-cli:latest`. Image precedence: `GEMINI_SANDBOX_IMAGE` > `GEMINI_SANDBOX_IMAGE_DEFAULT` > settings `image` > `package.json` `config.sandboxImageUri`. The image name must match `^[a-zA-Z0-9_.:/-]+$` — [docs/cli/sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md), [sandboxConfig.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/config/sandboxConfig.ts), [sandbox.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox.ts)
- The image is `node:20-slim` with python3, make, g++, man-db, curl, dnsutils, etc. It runs as `USER node` with `ENTRYPOINT` gemini, which the sandbox clears with `--entrypoint ''` — [G/Dockerfile](https://github.com/google-gemini/gemini-cli/blob/main/Dockerfile), [sandbox.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox.ts)
- **Mounts:** cwd is mounted at the "exact same absolute path" (rw). Then: a sanitised settings temp dir at `/home/node/.gemini` (rw); `~/.config/gcloud` read-only if it exists; the `GOOGLE_APPLICATION_CREDENTIALS` file read-only (with the env var rewritten); `SANDBOX_MOUNTS="from:to:opts,…"` (default `ro`, `from` must be absolute, must exist and must not be sensitive); `allowedPaths` read-only; and `VIRTUAL_ENV` under the workdir shadowed with `.gemini/sandbox.venv` "which is still preferable to having host binaries". The CLI refuses to start if cwd or the target dir is sensitive (home or its ancestors, `~/.gemini`, `.env*`, credential files) — [sandbox.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox.ts), [sandboxUtils.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandboxUtils.ts), [docs/cli/sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)
- A code comment says: "We STRICTLY do NOT mount ~/.gemini root directory or sensitive credential files (oauth_creds.json, .env, etc.). We only mount the sanitized settings file". `sanitizeSettingsForSandbox` deletes `hooks`, `tools.discoveryCommand`, `tools.callCommand`, `apiKey`, `geminiApiKey` and `googleApiKey`. `SENSITIVE_SETTINGS_FILENAMES` covers oauth_creds.json, google_accounts.json, gemini-credentials.json, mcp/a2a-oauth-tokens.json, trusted_hooks.json, trustedFolders.json and policy_integrity.json — [sandbox.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox.ts), [sandboxUtils.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandboxUtils.ts)
- **Env passed in:** `GEMINI_API_KEY`, `GOOGLE_API_KEY`, `GOOGLE_GEMINI_BASE_URL`, `GOOGLE_VERTEX_BASE_URL`, `GOOGLE_GENAI_USE_VERTEXAI`, `GOOGLE_GENAI_USE_GCA`, `GOOGLE_CLOUD_PROJECT`, `GOOGLE_CLOUD_LOCATION`, `GEMINI_MODEL`, `TERM`, `COLORTERM` and `NODE_OPTIONS`, plus arbitrary `SANDBOX_ENV="K=V,…"`, plus `SANDBOX=<containerName>`. PATH and PYTHONPATH entries under the workdir are appended. `.gemini/sandbox.bashrc` is sourced if present. `SANDBOX_PORTS` are published and forwarded with socat. `--add-host host.docker.internal:host-gateway` is set — [sandbox.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox.ts), [sandboxUtils.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandboxUtils.ts)
- **UID/GID:** `SANDBOX_SET_UID_GID=true|false` overrides the default. The default is on for Linux distros whose `/etc/os-release` ID or ID_LIKE matches debian, ubuntu, nixos, arch, fedora or suse. When on, the container starts `--user root`, runs `groupadd -g <gid>` and `useradd -o -u <uid> -g <gid> -d <home>`, then `su -p <user> -c '<cli>'`. If `useradd` is missing it fails explicitly "to avoid insecurely falling back to root execution with host mounts". Under rootless Podman it adds `--userns=keep-id` unless `SANDBOX_FLAGS` already sets `--userns` — [sandbox.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox.ts), [sandboxUtils.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandboxUtils.ts), [docs/cli/sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)
- **Networking:** if `!networkAccess` or a proxy command is set, the CLI creates or reuses a network `gemini-cli-sandbox` with `--internal` and attaches the container to it. With a proxy, a second non-internal network `gemini-cli-sandbox-proxy` is created, the proxy runs in its own container on both networks, and `localhost` in the proxy URL is rewritten to `gemini-cli-sandbox-proxy` ("works even on rootless podman on macos"). Container names get a random 6-byte hex suffix so concurrent starts don't collide — [sandbox.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox.ts), [sandboxUtils.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandboxUtils.ts)
- **Custom Dockerfile:** `.gemini/sandbox.Dockerfile` combined with `BUILD_SANDBOX=1` invokes `scripts/build_sandbox.js -f <Dockerfile> -i <image>`. This only works from a linked source checkout ("Cannot build sandbox using installed gemini binary"); npm installs need a prebuilt image set via `image`/`GEMINI_SANDBOX_IMAGE`. Docs show Artifact Registry images in `{"tools":{"sandbox":{"command":"docker","image":"…"}}}` — [sandbox.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox.ts), [docs/cli/sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)
- `SANDBOX_FLAGS` injects raw docker or podman flags (example: `--security-opt label=disable`) — [docs/cli/sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)
- **IDE integration:** the companion's port and token stay on the host. The host process bridges the MCP connection over `docker exec`/`podman exec`, which also works under gVisor where loopback is private — [docs/cli/sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md), [sandbox.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox.ts)
- **gVisor:** `GEMINI_SANDBOX=runsc` runs `docker run --runtime=runsc` (Linux only). It is described as the "Strongest isolation available". It has a user-space network stack, so host loopback services can't be reached even with `--network host`. **LXC** (experimental, Linux) uses a pre-existing running container (`GEMINI_SANDBOX_IMAGE` is the container name) with the workspace bind-mounted at the same path. It targets snapcraft/rockcraft — [docs/cli/sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)
- **Windows with containers:** host paths are converted for the container by `getContainerPath()` (`C:\foo\bar` → `/c/foo/bar`). PATH and PYTHONPATH are split on `;`. Docs give PowerShell syntax (`$env:GEMINI_SANDBOX="true"`, `$env:SANDBOX_FLAGS=…`). There is also a `windows-native` command value — [sandboxUtils.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandboxUtils.ts), [docs/cli/sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)
- **Running Gemini CLI itself in Docker:** mount `/var/run/docker.sock` so it can spawn sibling sandbox containers, and keep the workspace at an identical absolute path, because the host daemon resolves volume mounts — [docs/cli/sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)

### Inferences
- On Windows the container route needs Docker Desktop (WSL2) and gives a Linux userland, so Windows-native build tools aren't available inside. UID mapping only runs on Linux. The `/c/...` path mapping implies a Linux container with the drive mounted. None of this is spelled out in the docs.
- `SANDBOX_ENV` and `GEMINI_API_KEY` are passed as `--env K=V` on the docker command line, so the values are visible in the host process list (`ps`) for the life of the `docker run` client. That is a mild secret-exposure concern, and MossCode's "keep keys out of commands" rule would flag it.

### Gaps
- The Windows-native section of `docs/cli/sandbox.md` is literally truncated in the source (it reads "... **Troubleshooting and Side Effects:**"), so there is no full user doc for Windows-native. Its behaviour comes from source (section 4).

## 4. Windows native sandbox (per-command)

### Takeaway
On Windows, tool sandboxing compiles a small C# helper (`GeminiSandbox.cs` → `GeminiSandbox.exe`, using `csc.exe` from PATH or the .NET Framework dirs). It runs each command under a `CreateRestrictedToken(DISABLE_MAX_PRIVILEGE)` token lowered to **Low integrity (S-1-16-4096)**, inside a **Job Object** with KILL_ON_JOB_CLOSE. Write access is granted by adding Low-IL "Modify" ACEs and Low mandatory labels (`S:(ML;OICI;NW;;;LW)`) on allowed paths. Secrets and forbidden paths get explicit Deny-FullControl ACEs for the Low SID. "No network" is implemented as a Job net-rate cap of MaxBandwidth = 1, not a firewall block. ACL and integrity changes persist on disk.

### Cited Findings
- The helper usage is `GeminiSandbox.exe <network:0|1> <cwd> [--forbidden-manifest <path>] [--allowed-manifest <path>] <command> [args...]`. It calls `CreateRestrictedToken(hToken, DISABLE_MAX_PRIVILEGE, …)` and sets `TokenIntegrityLevel` to `S-1-16-4096`. It creates a Job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE | JOB_OBJECT_LIMIT_DIE_ON_UNHANDLED_EXCEPTION`. The child is created via `CreateProcessAsUser` with `CREATE_SUSPENDED` and `CREATE_BREAKAWAY_FROM_JOB`, then assigned to the job. Internal `__read`/`__write` run under impersonation of the restricted token — [G/packages/core/src/sandbox/windows/GeminiSandbox.cs](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/sandbox/windows/GeminiSandbox.cs)
- Network off: `JOBOBJECT_NET_RATE_CONTROL_INFORMATION{MaxBandwidth=1, ControlFlags=ENABLE|MAX_BANDWIDTH}`. On failure it only prints "Warning: … Network might not be throttled." — [GeminiSandbox.cs](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/sandbox/windows/GeminiSandbox.cs)
- ACLs: forbidden paths get `FileSystemAccessRule(lowSid, FullControl, Deny)` (inherited on directories). Allowed paths get `Modify` Allow for the Low SID plus a Low mandatory-label SACL (`S:(ML;OICI;NW;;;LW)` for directories, `S:(ML;;NW;;;LW)` for files) — [GeminiSandbox.cs](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/sandbox/windows/GeminiSandbox.cs)
- `WindowsSandboxManager` compiles the helper on first use if the exe is missing, trying `csc.exe` on PATH and then several Framework paths (the repo also ships `packages/core/scripts/compile-windows-sandbox.js`). It scans the workspace and allowed paths for secret files (`.env`, `.env.*`) to depth 3 and adds them to the forbidden manifest. Writable roots never include system directories, forbidden paths or UNC paths ("to prevent credential theft/SSRF"); `\\?\` and `\\.\` are allowed — [G/packages/core/src/sandbox/windows/WindowsSandboxManager.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/sandbox/windows/WindowsSandboxManager.ts)
- Documented side effects: integrity-level changes "are persistent on the filesystem … files created or modified by the sandbox will retain their 'Low' integrity level". Reset with `icacls "C:\path" /setintegritylevel Medium`. System folders like `C:\Windows` are skipped — [docs/cli/sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)
- There is a Windows-specific command safety classifier (`isKnownSafeCommand`/`isDangerousCommand` for cmd and PowerShell) and Windows denial parsing — [G/packages/core/src/sandbox/windows/commandSafety.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/sandbox/windows/commandSafety.ts), [G/packages/core/src/sandbox/windows/windowsSandboxDenialUtils.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/sandbox/windows/windowsSandboxDenialUtils.ts)

### Inferences
- Low integrity mainly blocks **writes** to Medium-labelled objects (No-Write-Up). By default it does not block reading most user files, so read confidentiality depends on the explicit Deny ACEs for forbidden paths and secret files. That inference comes from standard Windows MIC semantics, not a statement in the repo.
- MaxBandwidth = 1 throttles traffic rather than blocking connections, and the call fails open with a warning. It is a weak network control. A stronger Windows design would use an AppContainer without the `internetClient` capability, or WFP filters.
- Writing ACEs and labels onto the user's real project files is invasive: the changes persist, interact with Git and other tools, and need cleanup. MossCode could prefer AppContainer or a per-session restricted SID if it borrows this approach.
- Compiling C# at runtime with `csc.exe` avoids shipping a binary but depends on .NET Framework being present. A Python agent could use `ctypes`/`pywin32` for the same Win32 calls, or ship a small signed helper.

### Gaps
- No official threat-model document for the Windows native sandbox was found. Behaviour comes from source only.

## 5. Linux per-command sandbox (bubblewrap + seccomp)

### Takeaway
`LinuxSandboxManager` wraps each command as `sh -c 'exec bwrap --args 8 … 8<args_file 9<bpf_file'`. bwrap gets `--unshare-all --new-session --die-with-parent`, `--share-net` only if network is allowed, `--ro-bind / /`, a fresh `/dev`, `/proc` and tmpfs `/tmp`, and the workspace bind-mounted rw or ro by mode. Governance files are re-bound read-only. Forbidden paths are masked, and `.env*` files are bind-masked with an empty mode-000 file. A seccomp BPF filter returns EPERM for `ptrace` and kills processes using a foreign arch.

### Cited Findings
- bwrap args: `--unshare-all`, `--new-session`, `--die-with-parent`, optional `--share-net`, `--ro-bind / /`, `--dev /dev`, `--proc /proc`, `--tmpfs /tmp`. The workspace is mounted `--bind-try` if `workspaceWrite`, else `--ro-bind-try`. Global include dirs are mounted ro. Policy paths get read (ro) or write (rw) binds. `.gitignore`/`.geminiignore` are writable when the workspace is, while `.git` stays ro unless explicitly granted (git commands get it automatically when the workspace is writable). Git worktree and main `.git` dirs are mounted ro. Forbidden directories become a read-only tmpfs and forbidden files are bound to `/dev/null`. `.env`/`.env.*` found by `find -maxdepth 3` (skipping .git, node_modules, .venv, `__pycache__`, dist, build) are bound over with a mask file. Mounts are sorted by path length so parents mount before children — [G/packages/core/src/sandbox/linux/bwrapArgsBuilder.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/sandbox/linux/bwrapArgsBuilder.ts)
- The seccomp filter is hand-assembled BPF: kill on arch mismatch, `SECCOMP_RET_ERRNO|EPERM` for `ptrace`, allow everything else. It is passed via `--seccomp 9`. The mask file is created with `chmod 0` — [G/packages/core/src/sandbox/linux/LinuxSandboxManager.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/sandbox/linux/LinuxSandboxManager.ts)
- Write and network decisions: `workspaceWrite = !readonlyMode || isStrictlyApproved(command, approvedTools) || isYolo`. `networkAccess = modeConfig.network || policy.networkAccess || isYolo`, OR'd with persistent per-command permissions and per-request `additionalPermissions` — [LinuxSandboxManager.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/sandbox/linux/LinuxSandboxManager.ts)
- The environment is sanitised for sandboxed commands (`getSecureSanitizationConfig`). Variables whose names match `/TOKEN/i`, `/SECRET/i`, `/PASSWORD/i`, `/KEY/i`, etc. are dropped, and so are values that look like private keys, GitHub, Google, AWS, Stripe or Slack tokens, or JWTs — [G/packages/core/src/services/environmentSanitization.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/services/environmentSanitization.ts), [sandboxManager.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/services/sandboxManager.ts)

### Inferences
- Reads are broad (`--ro-bind / /`), so on Linux secrets outside the workspace (for example `~/.ssh`, `~/.aws`) stay readable unless they are on the forbidden list. Combined with network-on in YOLO mode, exfiltration remains possible. The code makes this trade-off on purpose for usability.

### Gaps
- I did not trace the exact contents of `getSandboxForbiddenPaths()` (the `forbiddenPaths` resolver in `Config`).

## 6. Secret protection and known limitations or escape concerns

### Takeaway
Gemini CLI protects secrets in layers: credential files and `.env*` are denied or masked, the agent's own config dir and settings are made read-only or sanitised, the env is sanitised, sensitive host paths are refused as mount sources or workspace, container-runtime sockets and binaries are blocked (Docker socket = escape), UNC paths are rejected, and a policy rule denies `gha-creds-*.json`. The docs openly say sandboxing "reduces but doesn't eliminate all risks".

### Cited Findings
- "Sandboxing reduces but doesn't eliminate all risks. Use the most restrictive profile that allows your work … GUI applications may not work in sandboxes." — [docs/cli/sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)
- `SECRET_FILES = ['.env', '.env.*']` are hidden (read and write denied) in every per-tool sandbox. `GOVERNANCE_FILES = ['.gitignore', '.geminiignore', '.git']` are "the governance or 'constitution' of the repository and should be write-protected" — [sandboxManager.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/services/sandboxManager.ts)
- `isSensitiveHostPath` blocks the home root or any ancestor of it, `~/.gemini` (inside or above it), `.env*` and credential files, and **fails closed** if path resolution throws. `isCredentialOrSensitivePath` also flags `*credentials*`, `*token(s).json`, `*.key`, `*.pem`, `*.p12`, `*key.json` and `*.env` — [sandboxUtils.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandboxUtils.ts)
- The default sandbox policy contains a rule `"Deny gha-creds"` for `argsPattern = ".*gha-creds-.*\\.json.*"` — [G/packages/core/src/policy/policies/sandbox-default.toml](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/policy/policies/sandbox-default.toml)
- In the changelog, v0.58.0 says Seatbelt now isolates "Docker and container runtime sockets and binaries to restrict container runtime access", and v0.60.0 says settings and temp directories are isolated inside the sandbox (hardening releases in Sep 2026) — [docs/changelogs/index.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/changelogs/index.md)
- gVisor caveat: if runsc is configured with `--network=none`, the whole sandboxed CLI "can't reach the Gemini API", which shows the cost of the whole-process design — [docs/cli/sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)
- Debug: `DEBUG=1` in a project `.env` is ignored by design (use `.gemini/.env`) — [docs/cli/sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)

### Inferences
- Escape concerns I can infer from the code: (1) whole-process Seatbelt and Linux bwrap allow broad reads; (2) Windows network "off" is only a throttle; (3) `SANDBOX_FLAGS` lets the user weaken container isolation; (4) Windows ACL and label changes persist on user files; (5) workspace-write lets the sandbox plant `.git/hooks` or config that later run unsandboxed on the host. Qwen's design doc calls this out explicitly (section 9), while Gemini keeps `.git` read-only by default for exactly this reason.

### Gaps
- I found no public CVE or security advisory specifically about Gemini CLI sandbox escapes in this pass. I did not search GHSA thoroughly.

## 7. Relationship to approval modes (default / auto_edit / yolo / plan)

### Takeaway
The whole-process sandbox is **not** enabled automatically by YOLO. `loadSandboxConfig` considers only flag, env and settings. For the per-tool sandbox, the **approval mode selects the sandbox mode config**: plan = read-only and no network; default = workspace-write, no network, a small approved-tools list; accepting_edits = same with sed/awk/etc.; **yolo = workspace-write + network on + no expansion prompts**. Switching modes rebuilds the sandbox manager. Admins can disable YOLO.

### Cited Findings
- `sandbox-default.toml`: `[modes.plan] network=false, readonly=true`; `[modes.default] network=false, readonly=false, approvedTools=['cat','ls','grep','head','tail','less','Get-Content','dir','type','findstr','Get-ChildItem','echo']`; `[modes.accepting_edits] network=false, readonly=false, approvedTools=['sed','grep','awk','perl','cat','echo','Add-Content','Set-Content']`; all have `allowOverrides=true` — [sandbox-default.toml](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/policy/policies/sandbox-default.toml)
- `getModeConfig('yolo')` returns `{network: true, readonly: false, approvedTools: [], allowOverrides: true, yolo: true}`. A user override file lives at `~/.gemini/policies/sandbox.toml`, and the schema has per-command `allowed_paths` and `allow_network` entries plus in-memory session approvals — [G/packages/core/src/policy/sandboxPolicyManager.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/policy/sandboxPolicyManager.ts)
- `setApprovalMode()` calls `refreshSandboxManager()`, which re-creates the manager with the new mode config — [G/packages/core/src/config/config.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/config/config.ts)
- Approval modes are `default`, `auto_edit`, `yolo` and `plan` (`--approval-mode`, `--yolo/-y`). `security.disableYoloMode` or `admin.secureModeEnabled` overrides YOLO — [G/packages/cli/src/config/config.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/config/config.ts)
- Sandbox config resolution reads only `argv.sandbox ?? settings.tools.sandbox` plus the `GEMINI_SANDBOX` env, and has no YOLO branch — [sandboxConfig.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/config/sandboxConfig.ts)

### Inferences
- In Gemini, YOLO *widens* the OS sandbox (network on, writes allowed), so in YOLO the sandbox is the only remaining barrier and its scope is the workspace. Qwen Code takes the opposite position: "Approval and YOLO do not expand the filesystem or network policy" (section 9). For MossCode, the Qwen position (approval decides *whether* to run, the sandbox decides *what it can touch*, and the two stay independent) is the stronger security property.

### Gaps
- I found no current official doc sentence saying "use sandbox with YOLO". Older Gemini docs may have recommended it, but I did not verify that, so it is not claimed.

## 8. What happens when a command fails because of the sandbox

### Takeaway
Gemini detects sandbox denials heuristically from the failed command's output. It turns a denial into a **"Sandbox Expansion Request"** modal listing the extra read/write paths and network access needed, and on approval re-runs the command with those permissions for that run, or remembers them for the session or persistently. It also proactively requests network for known network-heavy commands such as `npm install`. If the heuristic finds nothing new, the normal error goes back to the model.

### Cited Findings
- Docs: "When a sandboxed command fails due to permission restrictions … or when a command is proactively identified as requiring extra permissions (like `npm install`), Gemini CLI will present you with a 'Sandbox Expansion Request' … If you approve the expansion, the command is executed with the extended permissions for that specific run." — [docs/cli/sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)
- Detection (`parsePosixSandboxDenials`) runs on non-zero exit, error, signal or abort. It matches strings like "operation not permitted", "permission denied", "eperm", "eacces", "read-only file system", "sandbox_apply", "access denied", "permissionerror", and network failures. Extracted paths are sanitised: `..` and stray `~` are rejected. An LRU cache keyed on the first 200 characters avoids re-prompting — [G/packages/core/src/sandbox/utils/sandboxDenialUtils.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/sandbox/utils/sandboxDenialUtils.ts)
- In `shell.ts`, when a denial is found, the shell tool climbs to the nearest existing parent dir and adds it to read/write requests if the path isn't already allowed or the mode is read-only. It merges proactive suggestions and, only if there are *new* permissions, returns an error of type `SANDBOX_EXPANSION_REQUIRED` with `sandbox_expansion` confirmation details. Otherwise: "do not intercept. Just return the normal execution error so the LLM can try providing explicit paths itself." — [G/packages/core/src/tools/shell.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/tools/shell.ts)
- Proactive list: `NETWORK_RELIANT_TOOLS = npm, npx, yarn, pnpm, bun, git, ssh, scp, sftp, curl, wget`. Node tools need network only for subcommands such as `install, i, ci, update, up, publish, add, remove, outdated, audit` — [G/packages/core/src/sandbox/utils/proactivePermissions.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/sandbox/utils/proactivePermissions.ts)
- The repo has an eval for the model recovering from sandbox denials (`evals/sandbox_recovery.eval.ts`) — [G/evals/sandbox_recovery.eval.ts](https://github.com/google-gemini/gemini-cli/blob/main/evals/sandbox_recovery.eval.ts)
- For the whole-process sandbox, troubleshooting is manual: "Operation not permitted" → "Try more permissive profile or add mount points" — [docs/cli/sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)

### Inferences
- The flow detect denial → structured request of paths and network → user approves once, for the session, or persistently → retry maps directly onto MossCode's existing approval UI. It is the most reusable piece of the design. Because detection is heuristic string matching, false positives and negatives are expected, so it should stay advisory.

## 9. Qwen Code differences (fork)

### Takeaway
Qwen Code keeps Gemini's older whole-CLI methods (Seatbelt with 6 `.sb` files including real `*-closed` profiles, and Docker/Podman). It has **no** Windows-native, gVisor or LXC backends. On Linux it built its **own** per-tool "execution sandbox" (`tools.executionSandbox`: bwrap preferred, Landlock fallback). It is more conservative than Gemini: approval and YOLO never widen it, workspace settings can't change it, there is no unconfined fallback, and many host-side features are disabled while it is on. Its container mode mounts `~/.qwen` wholesale, which is less strict than Gemini's sanitised-settings approach.

### Cited Findings
- Qwen's Linux tool-execution sandbox config is `{"tools":{"executionSandbox":{"backend":"auto","filesystem":"workspace-write"|"read-only","network":"closed"|"open"}}}`. It is allowed only in User or System settings, and "Workspace settings cannot enable, disable or modify this policy, even in a trusted project". `auto` tries bwrap (`/usr/bin/bwrap`) and falls back to the bundled Landlock helper (ABI ≥ 3) only when `network: open`. Landlock is reported as `partial` enforcement (no PID or network namespace; chmod, chown, xattrs and timestamps not restricted) — [Q/docs/users/features/sandbox.md](https://github.com/QwenLM/qwen-code/blob/main/docs/users/features/sandbox.md)
- "The CLI, model transport, authentication and session storage remain on the host. Shell, terminal `!`, prompt shell interpolation, Monitor, Read/Write/Edit … use the same runtime policy." "Reads remain broad: this mode does not hide host secrets". "Approval and YOLO do not expand the filesystem or network policy." — [Q/docs/users/features/sandbox.md](https://github.com/QwenLM/qwen-code/blob/main/docs/users/features/sandbox.md)
- While it is on, MCP/LSP, executable hooks and extensions, worktree management, external agents, file checkpoints, IDE connection, etc. are disabled or rejected. `qwen serve`, ACP and web terminals reject the mode. `qwen sandbox`, `qwen sandbox --verify` and `qwen sandbox -- <cmd>` inspect and verify the boundary — [Q/docs/users/features/sandbox.md](https://github.com/QwenLM/qwen-code/blob/main/docs/users/features/sandbox.md)
- Design doc (2026-09-16): "A failed admission or launch never falls back to an unconfined command". The payload env is passed through a mode-0600 control file rather than process args. "Workspace-write intentionally allows repository metadata changes, including `.git` hooks and configuration. A later host process must therefore treat the entire writable workspace as sandbox output and must not execute repository-controlled hooks, filters, or configuration without a separate trust decision." Unconfirmed termination is reported as "may have run and must not be automatically replayed" — [Q/docs/design/2026-09-16-runtime-shell-sandbox.md](https://github.com/QwenLM/qwen-code/blob/main/docs/design/2026-09-16-runtime-shell-sandbox.md)
- Whole-CLI methods: env `QWEN_SANDBOX=true|false|docker|podman|sandbox-exec` overrides the flag (`-s`, `--sandbox[=provider]`) and `tools.sandbox`. The image comes from `--sandbox-image` > `QWEN_SANDBOX_IMAGE` > `tools.sandboxImage` > built-in `ghcr.io/qwenlm/qwen-code:<version>`. Seatbelt profiles: `permissive-open` (default), `permissive-closed`, `permissive-proxied`, `restrictive-open`, `restrictive-closed` ("Maximum restrictions"), `restrictive-proxied`; custom profiles are `.qwen/sandbox-macos-<name>.sb`. The proxy is `QWEN_SANDBOX_PROXY_COMMAND` on `:::8877`. "The container sandbox mounts your workspace and your `~/.qwen` directory into the container so auth and settings persist between runs." On Linux and Windows, "Use Docker or Podman". Whole-CLI bwrap (`--sandbox bwrap`, `QWEN_SANDBOX_NET`) is being migrated to `tools.executionSandbox` — [Q/docs/users/features/sandbox.md](https://github.com/QwenLM/qwen-code/blob/main/docs/users/features/sandbox.md), [Q/packages/cli/src/config/sandboxConfig.ts](https://github.com/QwenLM/qwen-code/blob/main/packages/cli/src/config/sandboxConfig.ts)
- Qwen's code includes `packages/core/src/sandbox/` with `bwrap-execution.ts`, `landlock-execution.ts`, `runtime-shell.ts`, `runtime-file.ts` and `file-worker*.ts`, plus design docs `2026-09-09-linux-kernel-sandbox.md`, `2026-09-16-runtime-file-sandbox.md` and `2026-10-01-settings-sandbox-followups.md` — [Q/packages/core/src/sandbox](https://github.com/QwenLM/qwen-code/tree/main/packages/core/src/sandbox), [Q/docs/design](https://github.com/QwenLM/qwen-code/tree/main/docs/design)
- License: Qwen Code is Apache-2.0 — [Q/LICENSE](https://github.com/QwenLM/qwen-code/blob/main/LICENSE)

### Inferences
- Qwen has no Windows-native sandbox, so it offers nothing new for MossCode's Windows-first case. Its value is in the **policy principles**: operator-only config, no unconfined fallback, approval independent of the sandbox, the hook/config-poisoning warning, and a `sandbox --verify` self-test command.

### Gaps
- I did not read Qwen's 877-line Linux kernel sandbox design doc or its file-worker protocol in detail.

### Inferences
- Design elements most transferable to MossCode (Python, Windows-first):
  1. a `SandboxManager.prepare_command()` abstraction that returns a wrapped argv, env and cleanup, with platform backends;
  2. mode-dependent policy (read-only for plan, workspace-write without network for default, explicit grants);
  3. hard deny-lists for the agent's own config and credentials, `.env*` and `.git` writes;
  4. env sanitisation by name and value patterns;
  5. denial detection → structured expansion request → once/session/persistent approval;
  6. refusing a sensitive cwd such as home or the config dir;
  7. on Windows, a restricted token + Low IL + Job Object helper (or AppContainer), noting Gemini's weak network throttling and persistent ACL side effects.

### Gaps
- No Google blog post or official design doc on the per-tool sandbox was found. The changelog, PR numbers and source are the first-hand record.
