# 操作系统沙箱正在取代逐条审批：Coding Agent 沙箱调研与 MossCode 的 Windows 路线

截至 2026-11-05，成熟的本地 coding agent 已经收敛到同一种做法：不把整个 agent 搬进容器，而是给每条命令套一层操作系统原生沙箱。macOS 用 Seatbelt，Linux 用 bubblewrap + seccomp + 网络命名空间。默认只能写工作区和临时目录；`.git/hooks`、`.git/config` 和 agent 自己的配置即使在工作区内也不可写；网络要么断开，要么只能走宿主机上按域名放行的回环代理。沙箱的价值在于替代逐条审批：Anthropic 称权限提示因此减少 84%，Cursor 称沙箱内的 agent 停下来的次数少 40%。命令被拒后以结构化结果返回模型，由模型说明理由、申请一次性越界，再由用户批准。它和容器的根本区别在于隔离的对象。容器隔离整个 agent，而 agent 自己要联网、要持有 API 密钥，所以挡不住命令联网和读密钥，MossCode 刚写的容器指南也承认这一点。按命令的沙箱把持有密钥、连接模型的宿主进程和执行命令的子进程分开，才能只给子进程断网、清空环境。Windows 是分歧最大的平台。Cursor、Zed、Kilo Code、Devin、Junie 和 Claude Code 本体都没有原生 Windows 沙箱；但 Codex 已有三种原生后端，Gemini CLI、DeepSeek Harness 和 sandbox-runtime（alpha）也各有实现，微软还在 2026-10 正式发布了 MXC。它们共同说明：不需要管理员权限的受限令牌只能限制写入；要真正约束读取和网络，要么用 MXC（需要很新的 Windows 11 版本），要么一次性提权，创建独立账户并配置 WFP 过滤。对 MossCode 的建议是：在唯一的进程启动入口 `tools/process.py` 上加一层“策略 + 平台后端”。Windows 上先实测 MXC 能否在用户的 Windows 11 Home 26300 上运行：能用就以 MXC 为主；不能用就先上 WRITE_RESTRICTED 受限令牌，并如实标为“部分强制”。无论选哪种后端，都要把 `~/.mosscode` 整体设为写保护，避免重蹈 dsh 控制面被沙箱内命令篡改的覆辙。

## 主流做法收敛为“每条命令一层 OS 沙箱”，它和容器隔离的不是同一个东西

阅读说明：带引用的陈述来自 2026-11-05 前后读取的一手文档或源码。标为“推断”的是根据这些材料作出的判断，没有实测。各家产品更新很快，版本号和默认值以引用页面为准。

被调研的 agent 里，凡是有本地沙箱的，基本都在逐命令包装，而不是整体迁移。Claude Code 的沙箱只作用于 Bash、PowerShell、Monitor 工具的命令“及其启动的进程”（[Claude Code 文档](https://code.claude.com/docs/en/sandboxing)）。Gemini CLI 把旧的整进程沙箱标成“Legacy full-process sandbox”，新的 `security.toolSandboxing` 只对单次工具执行做隔离，这样 UI 渲染和配置加载仍留在本机（[Gemini CLI sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)）。Qwen Code 写得更直白：“The CLI, model transport, authentication and session storage remain on the host”（[Qwen Code 文档](https://github.com/QwenLM/qwen-code/blob/main/docs/users/features/sandbox.md)）。Codex、DeepSeek Harness、Cursor、Zed、Kilo Code、Devin CLI、Junie CLI 也是同一结构。默认策略几乎一致：**写入限于工作区 + 临时目录，读取大体放开，`.git` 的钩子和配置及 agent 自身配置为受保护路径，网络默认关闭或只能经回环代理按域名放行，子进程继承全部限制**。

沙箱之所以被普遍采用，是因为它能减少打断。Anthropic 的工程博客说，内部使用中沙箱“safely reduces permission prompts by 84%”（[Anthropic 工程博客](https://www.anthropic.com/engineering/claude-code-sandboxing)）。Cursor 称沙箱内的 agent “stop 40% less often”，在支持的平台上约三分之一的请求在沙箱中执行（[Cursor 博客](https://cursor.com/blog/agent-sandboxing)）。前提是 agent 知道沙箱的存在：Cursor 发现，工具结果不说明是哪条限制导致失败时，模型会反复重试同一条命令。Goose 曾在 macOS 上提供实验性 Seatbelt 沙箱，后来移除，现在 goose 进程以用户全部权限运行（[goose v1.25.0 博客](https://goose-docs.ai/blog/2026/02/23/goose-v1-25-0/)）。推断：缺少“告诉模型、允许越界申请”配套的沙箱难以维持，Goose 自己没有说明移除原因。

容器和这种沙箱解决的是不同的问题。容器靠命名空间、cgroups 和 seccomp，与宿主**共享内核**，Docker 默认 seccomp 配置只禁用“around 44 system calls out of 300+”（[Docker seccomp 文档](https://docs.docker.com/engine/security/seccomp/)）。Docker 自己的对比表把挂载 socket 的容器评为“Partial (namespaces)”，把 microVM 评为“Full (hypervisor)”（[Docker Sandboxes 架构](https://docs.docker.com/ai/sandboxes/architecture/)）。更关键的是结构问题：容器里跑的是**整个 agent**，agent 要连模型、要拿密钥，网络就不能断，密钥也必须进容器。Gemini CLI 文档提到，若 gVisor 配成 `--network=none`，整个沙箱化的 CLI “can't reach the Gemini API”（[Gemini CLI sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)）。MossCode 的 `docs/reference/container.md` 同样写明：容器“不隔离”网络，同一用户的命令仍可能通过 `/proc/<pid>/environ` 读到密钥。按命令的 OS 沙箱把两者拆开：宿主进程持有密钥、直连模型；子进程拿到清理过的环境，网络被截断或只能走代理。容器真正的长处在于文件和进程可见性，它只看得到挂载进去的目录。

两者也可以叠加，但叠加有代价。Codex 建议在 Docker 或 Dev Container 里直接用 `danger-full-access`，把容器当作边界，因为容器配置常常不允许创建命名空间（[Codex 安全文档](https://learn.chatgpt.com/docs/agent-approvals-security)）。Claude Code 在无特权容器里只能打开 `enableWeakerNestedSandbox`，文档说这会“considerably weakens security”（[Claude Code 文档](https://code.claude.com/docs/en/sandboxing)）。第三类边界是 microVM，有独立的客户机内核，见第四节。

| | 整个 agent 进容器 | 每条命令一层 OS 沙箱 | microVM（云端或 Docker Sandboxes） |
|---|---|---|---|
| 代表 | Gemini CLI 旧整进程沙箱、OpenHands、MossCode 容器指南 | Claude Code、Codex、Gemini CLI 工具沙箱、Qwen、dsh、Cursor、Zed、Kilo、Devin、Junie | E2B、Vercel、Cloudflare、Codex/Claude 云会话、Docker Sandboxes |
| 与宿主内核 | 共享 | 共享（同一台机器上的受限进程） | 独立客户机内核 |
| 能否只给命令断网 | 不能，agent 本身要连模型 | 能，模型流量在宿主进程 | 能，出口由 VM 外的代理控制 |
| API 密钥位置 | 必须进容器 | 留在宿主，子进程环境可清空 | 可只放在 VM 外的代理，沙箱内只见占位符 |
| 工具链 | 镜像内（Windows 上是 Linux 容器，推断） | 用户本机的真实工具 | 镜像内，多为 Linux |
| Windows 原生 | 需 Docker Desktop / WSL2 | 取决于后端，见第五节 | 本机需虚拟化，或走云端 |

各家文档对沙箱的定位都很克制：Claude Code 说“Sandboxing reduces risk but is not a complete isolation boundary”，Gemini CLI 说“reduces but doesn't eliminate all risks”，DeepSeek Harness 的 SAFETY.md 说沙箱和审批“do not guarantee isolation”，Kilo Code 说它是“a write boundary, not a privacy boundary”（[Claude Code](https://code.claude.com/docs/en/sandboxing)、[Gemini CLI](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)、[dsh SAFETY.md](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/SAFETY.md)、[Kilo 文档](https://github.com/Kilo-Org/kilocode/blob/main/packages/kilo-docs/pages/getting-started/settings/sandboxing.md)）。

## 三家主力 CLI 各有侧重：Claude Code 重网络代理，Codex 的 Windows 后端最完整，Gemini CLI 新旧两层并存

### Claude Code 与 sandbox-runtime：代理做网络边界，受保护路径防自我提权

**隔离机制。** Claude Code 的沙箱默认关闭，用 `/sandbox` 或 `sandbox.enabled: true` 开启。macOS 上由 sandbox-runtime（srt）为每条命令生成 `(deny default)` 的 Seatbelt profile；Linux 和 WSL2 上用 bubblewrap，参数包括 `--unshare-net`、`--unshare-pid`、`--ro-bind / /`、全新的 `/proc`，再加一个静态 seccomp 辅助程序，拦截 `socket(AF_UNIX)`、`io_uring` 以及 `unshare`/`mount`/`setns` 等可以拆掉只读绑定的系统调用（[srt README](https://github.com/anthropics/sandbox-runtime)、[linux-sandbox-utils.ts](https://github.com/anthropics/sandbox-runtime/blob/main/src/sandbox/linux-sandbox-utils.ts)）。沙箱无法启动时默认**退回无沙箱执行**，设置 `failIfUnavailable: true` 才会退出。原生 Windows 上，“Claude Code runs commands unsandboxed”，文档让用户改用 WSL2；WSL1 会被拒绝（[Claude Code 文档](https://code.claude.com/docs/en/sandboxing)）。

**文件策略。** 可写范围是工作目录、每用户临时目录和 `--add-dir` 加入的目录。读取几乎覆盖整台机器，**包括 `~/.ssh` 和 `~/.aws/credentials`**，文档明说“There is no built-in credential deny list”。一组受保护路径即使落在可写范围内也不可写：`.claude` 设置、skills、agents、commands、hooks、`.mcp.json`，工作目录里的 `.bashrc`、`.gitconfig`、`.vscode`、`.idea`、`.git/hooks`、`.git/config`，以及会把目录变成裸仓库的 `HEAD`/`objects`/`refs`。理由原文是：“A command that could edit those files could grant itself permissions, or add a hook or MCP server that Claude Code runs outside the sandbox”（[Claude Code 文档](https://code.claude.com/docs/en/sandboxing)）。权限规则会并入沙箱配置：Edit 的 allow 规则变成 `allowWrite`，`WebFetch(domain:…)` 规则变成域名名单（[设置参考](https://code.claude.com/docs/en/settings-reference)）。

**网络策略。** Linux 上命令处在一个没有网卡的网络命名空间里，唯一出口是绑定进沙箱的 Unix socket，由 socat 桥接到宿主机上的 HTTP 和 SOCKS5 代理；macOS 上 Seatbelt 只放行代理所在的 localhost 端口。允许名单初始为空，访问未列出的主机时命令“stays in the sandbox and waits for a decision”。Manual 和 acceptEdits 模式下弹窗询问，选“Yes, and don't ask again”会写入一条 `WebFetch(domain:…)` 规则。代理还会检查解析结果：域名只解析到回环、链路本地、云元数据地址（`169.254.169.254` 等）或本机接口地址时一律拒绝，v2.1.284 起启用。不认代理变量的工具（普通 `ssh`、多数数据库驱动、UDP、QUIC、`ping`）连不出去；srt 给 git-over-ssh 和 JVM 做了专门垫片（[Claude Code 文档](https://code.claude.com/docs/en/sandboxing)、[srt README](https://github.com/anthropics/sandbox-runtime)）。

**密钥保护。** 默认情况下，沙箱内命令**继承 Claude Code 的全部环境变量，密钥也在其中**。保护需要主动开启：`sandbox.credentials` 的 `deny` 模式删除变量或禁止读取文件；`mask` 模式让沙箱里只看到哨兵值，由 TLS 终止代理只在发往允许主机的请求里换成真值，这一项只接受用户级或托管配置。全局开关 `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` 按变量名和值的形态清除凭据。hooks、MCP 服务器、`apiKeyHelper` 在沙箱外以完整权限运行（[Claude Code 文档](https://code.claude.com/docs/en/sandboxing)、[环境变量文档](https://code.claude.com/docs/en/env-vars)）。这里有一处需要调和的矛盾：发布博客称沙箱化后“a compromised Claude Code can't steal your SSH keys”，而现行文档写明 `~/.ssh` 默认可读。两者都对，但前提不同：博客依赖的是网络白名单让密钥“读得到、发不出”，不是禁止读取（[Anthropic 工程博客](https://www.anthropic.com/engineering/claude-code-sandboxing)）。

**与审批的关系、被拒后的处理。** `autoAllowBashIfSandboxed` 默认开启：沙箱内的命令不再逐条询问，但 Bash deny 规则、对关键路径的 `rm`、内容型 ask 规则（如 `Bash(git push *)`）仍然生效。`excludedCommands` 可以让命令移出沙箱，文档称之为“a convenience, not a security boundary”，并列出无论怎么配置都留在沙箱内的形态：`sudo`/`eval`/`xargs`、`cd`、命令替换、子 shell、重定向、变量充当命令名。命令被拒时，被拒的主机写进结果，模型可以带 `dangerouslyDisableSandbox: true` 重试；Manual 模式下这会弹出“Bash command (unsandboxed)”确认，严格模式 `allowUnsandboxedCommands: false` 则直接忽略这个参数（[Claude Code 文档](https://code.claude.com/docs/en/sandboxing)）。srt 把违规记录按命令归档，以 `<sandbox_violations>` 块追加到 stderr（[sandbox-manager.ts](https://github.com/anthropics/sandbox-runtime/blob/main/src/sandbox/sandbox-manager.ts)）。变更日志里有两条值得注意的修复：2.1.113 修了 `dangerouslyDisableSandbox` 不经确认就在沙箱外运行的问题；2.1.224 起“Claude now sees which file or network access was denied and why”（[CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)）。凡是会放宽沙箱的配置键（`filesystem.disabled`、`mask`、`tlsTerminate` 等）都不接受仓库内的设置文件。

**sandbox-runtime 本身与它的 Windows 后端。** srt 采用 **Apache-2.0** 许可，用 TypeScript 编写，要求 Node ≥22.12，最新版本 0.0.81（2026-10-20），标注为“Beta Research Preview”，可以作为 CLI、库或纯代理使用（[srt 仓库](https://github.com/anthropics/sandbox-runtime)、[npm](https://www.npmjs.com/package/@anthropic-ai/sandbox-runtime)）。srt 有一个 **alpha 版原生 Windows 后端** `srt-win.exe`（Rust）：一次性提权执行 `windows-install`，创建 `srt-sandbox` 本地用户，口令经 DPAPI 加密保存，并安装全机 WFP 过滤器；执行命令时，代理进程先用 `CreateProcessWithLogonW` 以该用户启动 runner，runner 再用写受限令牌在 Job Object 中启动目标进程，并给它一个独立桌面和全新的环境。WFP 只放行到回环代理端口的连接，其余以该账户身份发起的 connect 一律阻断。README 坦承：Schannel 客户端（System32 的 curl、`Invoke-WebRequest`、.NET `HttpClient`、winget）在受限令牌下无法使用；DNS 经 Dnscache 服务解析，不受拦截；线程先模拟匿名令牌再建 socket，就能绕过 WFP，原话是“Treat the network filter as stopping commands that connect directly, not code written to defeat it”（[srt README](https://github.com/anthropics/sandbox-runtime)）。Claude Code 本体没有用这个后端。微软 MXC 发布博客把“Anthropic Claude Code”列为“releasing support”的厂商之一（[Windows 开发者博客](https://blogs.windows.com/windowsdeveloper/2026/10/07/microsoft-execution-containers-policy-driven-containment-for-ai-agents/)），但截至 2026-11-05，Claude Code 文档仍写着原生 Windows 不进沙箱。合理的解读是支持正在开发、尚未发布。

### OpenAI Codex CLI：策略编译器加三种原生 Windows 后端

**隔离机制与文件策略。** Codex 的三种模式 `read-only`、`workspace-write`、`danger-full-access` 现在用权限配置文件表达（`:read-only`、`:workspace`、`:danger-full-access`），配置文件里可以按路径或 glob 声明 `read`/`write`/`deny`，管理员还能通过 `requirements.toml` 强制禁止读取（[Codex 配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)）。推断：Codex 实际的设计原语是一张“路径→权限”表，由各平台后端分别编译成 SBPL、bwrap 参数或 Windows ACL；Python 实现可以照搬这个结构。可写根目录下的 `.git`（包括 `gitdir:` 指向的真实目录）、`.codex`、`.agents`、`.aws` 一律只读（[Codex 安全文档](https://learn.chatgpt.com/docs/agent-approvals-security)）。macOS 上只调用 `/usr/bin/sandbox-exec`，防止 PATH 被劫持；Linux 已从 Landlock 改为默认使用 bubblewrap，seccomp 在受限网络模式下禁止 `connect`/`bind`/`listen` 等调用，并把 `socket` 限制为 `AF_UNIX`。因为这次迁移，WSL1 从 0.115 起不再受支持；此外，PATH 上可被沙箱写入的 bwrap 会被拒绝使用（[linux-sandbox README](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md)、[seccomp.rs](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/src/seccomp.rs)、[Codex 变更日志](https://learn.chatgpt.com/docs/changelog)）。

**Windows：三种后端。** 这是目前公开资料最完整的原生 Windows 沙箱，代码约 2.76 万行。`mxc` 是推荐选项，调用微软 Execution Containers，“without administrator-approved setup, additional Windows accounts, or local firewall rules”，要求 Windows 11 24H2 build 26100.9278 或 25H2 build 26200.9278。`elevated` 是“preferred legacy fallback”，需要一次 UAC 提权完成安装：创建 `CodexSandboxOffline` 和 `CodexSandboxOnline` 两个隐藏的本地用户，口令用 DPAPI 保存，再配置按用户 SID 生效的防火墙和 WFP 规则，屏蔽 ICMP 和 DNS。`unelevated` 是次级回退，它“doesn't support denied read paths”，网络隔离也更弱（[Codex Windows 文档](https://learn.chatgpt.com/docs/windows/windows-sandbox)、[setup.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/setup.rs)、[firewall.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/setup_provisioning/firewall.rs)、[wfp.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/wfp.rs)）。两种旧后端共用一个核心原语：`CreateRestrictedToken(DISABLE_MAX_PRIVILEGE | LUA_TOKEN | WRITE_RESTRICTED)`，restricting SID 依次是每个工作区一个随机的能力 SID、额外 SID、logon SID 和 Everyone；工作区目录加上授予该能力 SID 的允许 ACE，受保护的子目录加拒绝写入 ACE。尚不存在的受保护路径会预先创建出来，以免沙箱内的命令先建出同名路径、绕开限制（[token.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/token.rs)、[cap.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/cap.rs)、[setup_provisioning.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/setup_provisioning.rs)）。unelevated 模式的“断网”只是改写环境变量：把 `HTTP(S)_PROXY` 指向 `127.0.0.1:9`，设置 `PIP_NO_INDEX`、`CARGO_NET_OFFLINE`，并在 PATH 前插入一个目录，里面是直接返回失败的 `.bat` 桩（[env.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/env.rs)）。OpenAI 的博客解释了为什么不用其他方案：AppContainer 是为“know, up front, exactly what they need to access”的应用设计的，不适合开放式开发工作流；把工作区标成低完整性，会让它变成本机所有低完整性进程都能写入的“sink”；防火墙规则“无法匹配受限令牌的非主体身份”，所以真正的网络隔离必须换成独立账户（[OpenAI 工程博客](https://openai.com/index/building-codex-windows-sandbox/)）。需要说明，Codex 文档已从 developers.openai.com 308 重定向到 learn.chatgpt.com，两组链接指向同一份内容。

**网络与密钥。** `workspace-write` 默认断网。启用网络只是一个布尔开关；可选的托管代理（HTTP `127.0.0.1:3128`，SOCKS5 `:8081`）按允许名单优先的规则过滤，拒绝解析到私有地址的域名，并尽力检查 DNS 重绑定。代理不过滤 Codex 自己的模型流量，经批准的完整越界也会绕过代理（[Codex 安全文档](https://learn.chatgpt.com/docs/agent-approvals-security)、[network-proxy README](https://github.com/openai/codex/blob/main/codex-rs/network-proxy/README.md)）。密钥保护的默认值偏弱：`shell_environment_policy` 默认继承全部变量，`ignore_default_excludes` 默认为 true，也就是说 `*KEY*`/`*SECRET*`/`*TOKEN*` 默认照样传给子进程（[config_types.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/config_types.rs)）。推断：各平台默认的读取范围都很宽，elevated 模式的读取排除名单里也没有 `.codex`，因此沙箱内的命令多半能读到 `~/.codex/auth.json`；源码里没有找到对它的专门保护。

**与审批的关系、被拒后的处理。** 审批策略有 `on-request`（交互默认）、`never` 和 `granular` 三种，`untrusted` 改为项目信任级别。越界主要由模型发起：shell 工具的参数里有 `sandbox_permissions: "require_escalated"`、给用户看的 `justification`，以及可复用的 `prefix_rule`（[shell_spec.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/handlers/shell_spec.rs)）。编排器只在 untrusted 策略（或 granular 打开 `sandbox_approval`）下自动询问“是否不带沙箱重跑”；在 on-request 和 never 下，“do not retry without sandbox; surface a concise sandbox denial”（[orchestrator.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/orchestrator.rs)）。两个细节值得借鉴：命令 allow 规则“does not authorize removing filesystem restrictions”；存在禁止读取策略时，即使批准越界，命令也仍在沙箱内执行，否则等于悄悄放开了那些读取（[sandboxing.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/sandboxing.rs)）。仓库采用 **Apache-2.0** 许可（[LICENSE](https://github.com/openai/codex/blob/main/LICENSE)）。

### Gemini CLI 与 Qwen Code：两层沙箱，Windows 用低完整性令牌

**隔离机制。** Gemini CLI 有两层。旧的整进程沙箱（`-s`、`GEMINI_SANDBOX`）把整个 CLI 放进 sandbox-exec、Docker、Podman、gVisor（`runsc`）或 LXC 里重新启动。v0.35/v0.36（2026-03/04）起新增的按工具沙箱默认关闭，需设置 `security.toolSandboxing: true`；它通过 `SandboxManager.prepareCommand()` 把每条命令改写成包装后的调用，**文件读写工具也走同一沙箱**（[changelog](https://github.com/google-gemini/gemini-cli/blob/main/docs/changelogs/index.md)、[sandboxManager.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/services/sandboxManager.ts)、[config.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/config/config.ts)）。Linux 上用 `bwrap --unshare-all`，seccomp 只拦截 `ptrace`；macOS 上生成 `(deny default)` profile。Windows 上，首次使用时用 `csc.exe` 编译一个 C# 辅助程序 `GeminiSandbox.exe`：以 `CreateRestrictedToken(DISABLE_MAX_PRIVILEGE)` 创建令牌并降到 **Low 完整性**，放进带 KILL_ON_JOB_CLOSE 的 Job Object；可写路径加上 Low SID 的 Modify ACE 和 Low 强制标签，敏感路径加拒绝 ACE（[GeminiSandbox.cs](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/sandbox/windows/GeminiSandbox.cs)、[WindowsSandboxManager.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/sandbox/windows/WindowsSandboxManager.ts)）。它的 Windows“断网”是把 Job 的出站带宽限为 `MaxBandwidth=1`，设置失败时只打印警告；标签修改会持久留在用户文件上，文档教用户用 `icacls … /setintegritylevel Medium` 恢复（[sandbox.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md)）。推断：这是限速而不是阻断，且失败时放行，网络控制很弱。

**文件、网络、密钥。** `.env`、`.env.*` 在每种按工具沙箱里都禁止读写；`.gitignore`、`.geminiignore`、`.git` 被视为仓库的“constitution”，加以写保护。环境变量按名称（`TOKEN`、`SECRET`、`KEY` 等）和值的形态（私钥、GitHub/AWS/Stripe 令牌、JWT）清理（[sandboxManager.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/services/sandboxManager.ts)、[environmentSanitization.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/services/environmentSanitization.ts)）。整进程模式下，Seatbelt profile 禁止读写 `~/.gemini` 中的凭据文件，并阻断 Docker、OrbStack、Colima 的 socket 和可执行文件。容器模式从 v0.60 起不再挂载 `~/.gemini`，只挂载一份去掉 hooks 和 API 密钥的 `settings.json`；工作目录或挂载源是家目录、`~/.gemini` 或凭据文件时直接拒绝启动，路径解析失败也按拒绝处理（[sandbox.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandbox.ts)、[sandboxUtils.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/sandboxUtils.ts)）。

**与审批的关系、被拒后的处理。** 审批模式决定沙箱的配置：plan 为只读、断网；default 和 auto_edit 可写工作区、断网，并带一小份免审批命令；**yolo 打开网络并可写**；切换模式时会重建沙箱管理器（[sandbox-default.toml](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/policy/policies/sandbox-default.toml)、[sandboxPolicyManager.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/policy/sandboxPolicyManager.ts)）。命令失败后，用字符串匹配（“operation not permitted”、“read-only file system”、EACCES 等）识别沙箱拒绝，提取出新的路径或网络需求后弹出“Sandbox Expansion Request”，用户可以批准一次、本会话或永久。对 `npm install` 这类已知需要网络的命令，会提前申请网络。识别不出新需求时，“Just return the normal execution error so the LLM can try providing explicit paths itself”（[shell.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/tools/shell.ts)、[sandboxDenialUtils.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/sandbox/utils/sandboxDenialUtils.ts)、[proactivePermissions.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/sandbox/utils/proactivePermissions.ts)）。

**Qwen Code 的不同取舍。** Qwen Code 是 Gemini CLI 的分支，采用 Apache-2.0 许可。它保留了整进程的 Seatbelt 和 Docker 方式，在 Linux 上另做了按工具沙箱 `tools.executionSandbox`（优先 bwrap，回退到 Landlock），**没有原生 Windows 后端**。它的策略比 Gemini 保守：这项配置只接受用户级或系统级设置，“Workspace settings cannot enable, disable or modify this policy”；“Approval and YOLO do not expand the filesystem or network policy”；启动失败“never falls back to an unconfined command”；开启时 MCP、hooks、IDE 连接等宿主侧功能一并禁用。它的设计文档还警告：workspace-write 允许修改 `.git` 的钩子和配置，所以宿主之后必须把整个可写工作区视为沙箱产物，未经单独的信任判断不得执行其中的钩子（[Qwen 文档](https://github.com/QwenLM/qwen-code/blob/main/docs/users/features/sandbox.md)、[Qwen 设计文档](https://github.com/QwenLM/qwen-code/blob/main/docs/design/2026-09-16-runtime-shell-sandbox.md)）。Gemini CLI 同为 **Apache-2.0**（[LICENSE](https://github.com/google-gemini/gemini-cli/blob/main/LICENSE)）。

### DeepSeek Harness（dsh）：只管写入的沙箱，和一次控制面逃逸

**定位与机制。** `deepseek-ai/deepseek-harness` 是 DeepSeek AI 官方发布的本地 agent 运行时，采用 **MIT** 许可，用 TypeScript 编写，2026-08-13 公开，目前处于 developer preview（[README](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/README.md)、[GitHub API](https://api.github.com/repos/deepseek-ai/deepseek-harness)）。它的三种模式借用了 Codex 的命名，但只约束文件写入，原话是：“Network and process visibility are outside this vocabulary”。各平台的 runner 链为：Linux 依次尝试 bwrap、Landlock；macOS 用 Seatbelt；Windows 用 ACL 受限令牌。全部不可用时失败关闭：“Silent unconfined passthrough is never legal for a confined policy”。每次执行都报告 `full` 或 `partial` 两级强制程度，并按后端区分拒绝时的错误特征：bwrap 是 EROFS，Landlock 是 EACCES，Seatbelt 是 EPERM。它也区分“runner 故障”（命令根本没有运行）和“沙箱拒绝”（[sandbox.md](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/docs/subsystems/sandbox.md)）。

**Windows 后端。** 用 `CreateRestrictedToken(WRITE_RESTRICTED + DISABLE_MAX_PRIVILEGE)` 复制调用者的令牌，restricting SID 里放入工作区和私有临时目录两个能力 SID，再降到 Low 完整性。每次授权写入三项：能力 SID 的允许 ACE；对 Everyone 拒绝父目录的 `FILE_DELETE_CHILD`，否则 `cmd /c del` 能删掉工作区外的文件，因为父目录上的这项权限不需要 restricting SID 共同签署；以及 Low 标签。官方列出的限制有：读取、网络、进程可见性均不受限；NTFS 硬链接有缺口；Low 标签会长期留在工作区上；大目录树首次授权需要数十秒；restricting 列表必须保留 Everyone 和 logon SID，否则 DLL 初始化会崩溃；不支持额外的可写根目录（[sandbox-windows-acl README](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/sandbox/sandbox-windows-acl/README.md)）。决策记录说明了为什么不选 AppContainer 或 MXC：它们默认连读取都拒绝，需要大面积改写 DACL，而且会抬高系统版本要求（[决策记录](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/.agents/notes/implemented/feature/2026-08-08-windows-acl-restricted-token-sandbox.md)）。

**审批、密钥、被拒后。** 审批策略只有 `ask` 和 `never`；审批结果中只有 `allowed-once` 表示放行，审批事件只写日志，不进入模型上下文（[approval.md](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/docs/subsystems/approval.md)）。被拒的命令带回 `sandbox: { mode, denied: true }` 和一条 `[sandbox: file access denied under <mode> mode]` 标记；模型可以带上“够用的最窄模式”和 `justification` 把同一命令重试一次，用户批准前不会执行（[bash-sandbox README](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/shell/bash-sandbox/README.md)）。子进程环境只按变量名清理（`*KEY*`、`*TOKEN*` 等），`*PASSPHRASE*` 这类名字会漏掉；项目的 `.env` 不得设置代理变量（[subprocess-local README](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/subprocess/subprocess-local/README.md)、[network-proxy.md](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/docs/user/guide/network-proxy.md)）。

**CVE-2026-82533 的教训。** 漏洞的过程是：沙箱内的 agent 受提示注入驱使，用一条 shell 命令调用 dsh 自己监听在本机的 Web 接口，把会话改成 `danger-full-access` + `never`，此后的命令都在沙箱外运行，且不经审批。VulnCheck 评分 9.4，2026-09-08 公开，影响 ≤0.1.1-rc.2。根因有四条：沙箱不限制网络，回环地址上的管理接口可达；agent 的 shell 环境里直接给出了接口地址和会话 ID；接口没有认证，判断“是否本地”只看客户端提供的 Host 头；接口还能下载整个会话日志。修复方式是启动时打印一次性 token，用它换取签名 cookie，但沙箱本身没有改（[The Hacker News](https://thehackernews.com/2026/09/deepseek-harness-flaw-let-ai-agents.html)）。各报道给出的首个修复版本不一致：THN 写的是 npm 上的 0.1.2-alpha.2，OX Security 等写的是只在 GitHub 上发布的 0.1.2-alpha.1，两者并不矛盾。这件事的普遍意义在于：**只限制写入的沙箱等于假定沙箱内的代码能访问回环地址上的一切**，宿主的控制面——任何能改变权限模式的通道——必须认证，或者完全不出现在沙箱可达的范围里。

## 其他 Agent 的策略高度一致，“原生 Windows 沙箱”的空缺只存在于其中一半产品

**OpenHands** 走的是整个 agent 进容器的路线：工具运行在 Docker 容器内的 Agent Server 里，宿主通过 HTTP/WebSocket 通信；“process”提供者在本机直接运行，文档称之为“unsafe, but fast”。Agent Server 默认“starts without API authentication”。仓库内容以读写方式挂载，文档也没有说明出口限制。密钥由 Secret Registry 在命令引用时以环境变量注入，并在输出中打码。审批与沙箱分开：模型为每次工具调用填写 `security_risk`，由 `ConfirmationPolicy` 决定是否需要确认。许可证为 MIT（[OpenHands 沙箱概览](https://docs.openhands.dev/usage/runtimes/overview.md)、[Agent Server](https://docs.openhands.dev/sdk/arch/agent-server.md)、[Secret Registry](https://docs.openhands.dev/sdk/guides/secrets.md)、[安全架构](https://docs.openhands.dev/sdk/arch/security.md)）。

**Cursor** 是闭源产品里最成熟的一家。macOS 上用 Seatbelt，profile 根据工作区、管理员设置和 `.cursorignore` 动态生成；Linux 上直接用 Landlock + seccomp，把被忽略的文件替换成 Landlock 保护、不可读写的覆盖副本；Windows 上“we run our Linux sandbox inside WSL2”，理由是“most existing sandboxing primitives are tailored to browsers”，并表示正在与微软合作（[Cursor 博客](https://cursor.com/blog/agent-sandboxing)）。网络默认阻断，默认模式额外放行约 100 个包仓库域名，RFC1918、回环和 `169.254.169.254` 默认拦截以防 SSRF。`.cursor/*.json`、`.claude/*.json`、`.vscode/**`、`.git/hooks/**`、`.git/config` 始终写保护。仓库级的 `sandbox.json` 可以**追加**路径和域名，这一点比 Kilo 和 Junie 宽松（[sandbox.json 参考](https://cursor.com/docs/reference/sandbox)）。在 Auto-review 模式下，沙箱内的命令直接执行；沙箱拒绝后可以在沙箱外重跑，由分类器审查，文档声明“Auto-review is not a security boundary”（[Run Modes](https://cursor.com/docs/agent/security/run-modes)）。这里有一处出入：2026-02 的博客说沙箱已在 Windows 上线（经 WSL2），而 2026-10 的文档只列出 macOS 和 Linux 的要求；论坛上还有用户日志显示“direct egress blocking is best-effort on Windows”（论坛内容只看到搜索摘要）。

**Zed** 从 v1.14（2026-08）起默认对 Agent 的终端和 fetch 工具启用沙箱：工作区可写，`.git` 不可写，网络按主机申请，禁止 Unix socket（会话总线、容器守护进程）。审批粒度是“本次 / 本线程 / 永远”，申请越界时“agents must provide a reason”。Linux 上只用**非 setuid** 的 bwrap，因为 setuid 版本会用部分来自模型的参数执行 root 权限的初始化；bwrap 不可用时“may run the command without the OS sandbox and show a warning”。Windows 上只有在 WSL 内运行的命令才受沙箱保护，`/mnt/c` 上的写入可能逃出授权范围，原生 Windows 进程“do not currently have the same sandbox integration”。它还记录了沙箱外的旁路：rust-analyzer 在沙箱外执行 proc-macro，Makefile 投毒，子模块里的 `core.fsmonitor` 在用户之后运行 git 时被触发（[Zed 文档](https://zed.dev/docs/ai/sandboxing)）。Zed 仓库的许可证在 GitHub API 中显示为 NOASSERTION，沙箱 crate 的许可证未核实，不应复制其代码。

**Kilo Code**（MIT，CLI 由 opencode 分支而来）的沙箱需要手动开启，**不支持 Windows**。项目配置“may tighten sandbox policy… It cannot … add destinations, or add writable paths”；`.git` 和 Kilo 自己的策略文件始终只读。网络只能经认证代理出去，HTTPS CONNECT 时要求 TLS ClientHello 的 SNI 与允许的主机一致，DNS 在沙箱外解析，非公网地址的解析结果一律拒绝。策略无法强制执行时，“refuses to run the affected tool. It does not silently fall back”（[Kilo 文档](https://github.com/Kilo-Org/kilocode/blob/main/packages/kilo-docs/pages/getting-started/settings/sandboxing.md)）。源码里带有对 srt 0.0.63 的补丁（[kilo-sandbox 源码](https://github.com/Kilo-Org/kilocode/tree/main/packages/kilo-sandbox/src)）。它的 `SECURITY.md` 仍写着“does not sandbox the agent”，这是从 opencode 继承下来、没有更新的旧文本（[SECURITY.md](https://github.com/Kilo-Org/kilocode/blob/main/SECURITY.md)）。

**Devin CLI / Devin Local**（Windsurf 的后继，闭源）的 `--sandbox` 仍是“Research Preview”，macOS 用 Seatbelt，Linux 用 bwrap + seccomp；`autonomous` 模式必须开启沙箱。`Read(...)` deny 路径对沙箱完全隐藏，会话中途批准读取也不能解除。沙箱解析失败时“will refuse to start”；Windows 上直接失败，要求改用 WSL2（[Devin CLI 沙箱](https://docs.devin.ai/cli/sandbox.md)、[命令参考](https://docs.devin.ai/cli/reference/commands)）。**JetBrains Junie CLI**（EAP，闭源）直接包装 srt，只支持 macOS 和 Linux。它只读取 `~/.junie/sandbox.json`，项目内的同名文件会被忽略并给出警告；修改策略文件必须每次单独“Allow once”，“brave mode and saved approvals cannot bypass this confirmation”。启用前，它会用生成的配置实际跑一次受控的越界写入，确认被拦截；启用失败时终端执行一直被阻断，直到用户明确选择“Continue without sandboxing”（[Junie 文档](https://junie.jetbrains.com/docs/junie-cli.html)）。

没有内置 OS 沙箱的有：Goose（Apache-2.0，实验性 Seatbelt 已移除）、opencode（MIT，只有 allow/ask/deny 权限）、Cline（Apache-2.0，`--worktree` 只是隔离状态）、Roo Code（仓库已归档）、Aider（Apache-2.0）。Amp 和 Warp 的强隔离在云端（Amp 的 Orbs、Warp 基于 Namespace 的 Oz 沙箱）（[goose 博客](https://goose-docs.ai/blog/2026/02/23/goose-v1-25-0/)、[opencode 权限](https://opencode.ai/docs/permissions/)、[Cline CLI](https://docs.cline.bot/cli/cli-reference)、[Amp 手册](https://ampcode.com/manual)）。Amp 在 2025 年出过一个问题：agent 能改写自己的配置，加入允许的命令或 MCP 服务器，从而经提示注入实现远程代码执行（[Embrace The Red](https://embracethered.com/blog/posts/2025/amp-agents-that-modify-system-configuration-and-escape/)）。这和 dsh 的 CVE 是同一类问题。

## 云端沙箱用 microVM 加出口白名单，密钥只在代理里出现

隔离技术分三档。第一档是容器（命名空间 + cgroups + seccomp），与宿主共享内核。第二档是 gVisor，在工作负载和宿主内核之间插入一个用 Go 写的用户态内核，代价是兼容性下降、单次系统调用开销增大，且“does not provide protection against hardware side channels”（[gVisor 文档](https://gvisor.dev/docs/)、[gVisor 安全模型](https://gvisor.dev/docs/architecture_guide/security/)）。第三档是 microVM：Firecracker（Apache-2.0，Rust）只模拟 5 种设备，启动“<125ms”，每个 VM 的开销“<5 MiB”，另有 jailer 作为第二道防线（[Firecracker](https://firecracker-microvm.github.io/)）；Kata Containers 把 OCI 容器放进轻量 VM，Cloud Hypervisor 是 Rust 写的精简 VMM（[Kata](https://katacontainers.io/)、[Cloud Hypervisor](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/main/README.md)）。推断：被调研的商业 agent 沙箱平台都用第二或第三档运行不可信代码，没有一家只靠普通容器；这三档都不能阻止经由允许的网络路径外泄数据，那需要出口策略。另外，这三项技术都要求 Linux + KVM，Windows 主机只能通过 WSL2/Hyper-V、Docker Desktop 或远程后端使用它们。

| 平台 | 隔离 | 网络 | 密钥 | 接口 | 许可证 / 状态 |
|---|---|---|---|---|---|
| E2B | 每个沙箱一个 Firecracker microVM；从快照恢复 | 每沙箱 nftables + SNI/Host 检查的域名白名单；默认联网 | “Secrets are metadata-only on the control plane”；请求注入 | Python/JS SDK，流式 exec、PTY、文件、暂停/恢复 | runtime 为 Apache-2.0，可自托管 |
| Modal | gVisor 或 VM（`runtime="vm"`） | 默认可访问公网；CIDR、域名白名单（Beta，仅 443） | Secret injection（Beta） | Python/JS/Go SDK | 客户端 Apache-2.0 |
| Daytona | 容器或完整 VM（含 Windows VM） | CIDR/域名白名单、全阻断 | 未核实 | 多语言 SDK | 2026-06 起核心闭源 |
| Cloudflare Containers | Firecracker microVM | `enableInternet: false` 默认 | 由 Worker 持有凭据，出站时添加 | 仅 TypeScript，必须经 Worker | SDK 许可证未核实 |
| Vercel Sandbox | Firecracker microVM | — | OIDC | JS/Python SDK | Apache-2.0 |
| Docker Sandboxes（本地） | 每个沙箱一个 microVM，内含独立 Docker 守护进程 | 出站须通过网络策略 | agent 只见哨兵值，宿主代理替换真值 | `sbx` CLI | CLI 和本地使用免费 |

来源依次为：[E2B runtime](https://github.com/e2b-dev/runtime)、[E2B 网络](https://e2b.dev/docs/sandbox/internet-access.md)、[Modal 沙箱](https://modal.com/docs/guide/sandbox)、[Modal 网络](https://modal.com/docs/guide/sandbox-networking)、[Daytona 隔离](https://www.daytona.io/docs/en/isolation.md)、[Daytona README](https://github.com/daytonaio/daytona/blob/main/README.md)、[Cloudflare 安全](https://developers.cloudflare.com/sandbox/concepts/security/)、[Vercel Sandbox](https://vercel.com/docs/vercel-sandbox)、[Docker Sandboxes 架构](https://docs.docker.com/ai/sandboxes/architecture/)。

托管的 coding agent 采用同一种模式：每个任务一个一次性的 Linux VM 或容器；克隆仓库后，setup 脚本在联网状态下运行，agent 阶段则受出口白名单限制；结果以分支或 PR 交回，从不直接写回用户机器。2026 年的趋势是**密钥完全不进沙箱**：Codex Cloud 的 network secret 让程序只拿到占位符，“the proxy substitutes the real value for allowed destinations”（[Codex 云环境](https://learn.chatgpt.com/docs/environments/cloud-environments.md)）；Claude Code 云会话由“Anthropic's agent proxy adds the key to requests for the hosts you list”，并且承认即使断网也能与 Anthropic API 通信，“which may allow data to exit the VM”（[Claude Code 云环境](https://code.claude.com/docs/en/cloud-environments.md)、[Claude Code on the web](https://code.claude.com/docs/en/claude-code-on-the-web.md)）。GitHub Copilot 的防火墙“only applies to processes started by the agent via its Bash tool”，并承认“Sophisticated attacks may bypass the firewall”（[Copilot 防火墙](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall)）。Copilot 的本地沙箱同样基于 MXC，其文档承认在 Windows 上代理强制“relies on programs honoring the proxy settings”（[Copilot 本地沙箱](https://github.com/github/docs/blob/main/content/copilot/concepts/security-governance-and-network-settings/about-cloud-and-local-sandboxes.md)）。

如果 MossCode 要把命令交给远程执行，有两种成熟模式。一种是会话移交：Claude 的 `--cloud`/`--teleport`、Copilot 的 `--cloud`、Devin 的 `/handoff`，结果经 git 带回（[Devin handoff](https://docs.devin.ai/cli/handoff.md)）。另一种是远程执行后端：agent 循环留在本地，每条命令经 SDK 发到远程沙箱。推断：后者需要持续双向同步工作树，每次调用都多一次广域网往返，交互命令还需要 PTY 通道；而且远程沙箱多为 Linux，与 Windows 用户的 PowerShell 工具链不匹配。厂商发布的产品都采用前者或纯远程工作区，没有找到“本地 agent + 远程执行 + 持续同步”的成熟实现。E2B 的 Python SDK 最完整，runtime 也可自托管，适合作为远程后端的首选。Docker Sandboxes 则是 Windows 用户在本机获得 microVM 隔离的现成方案。

## Windows 原生：受限令牌只能管住写入，读取和网络要靠 MXC 或独立账户

**MXC（Microsoft Execution Containers）** 于 2026-10-07 正式发布，是“policy-driven execution layer for untrusted code”。它有四种后端：进程容器（Windows 上基于 AppContainer）、会话容器（独立的 Windows 账户和会话）、WSL 容器、microVM（实验性）。策略覆盖文件系统（可修改/只读/无访问）、网络（含是否允许经宿主回环访问服务）和 UI，并提供强制、学习、宽松三种运行模式（[Windows 开发者博客](https://blogs.windows.com/windowsdeveloper/2026/10/07/microsoft-execution-containers-policy-driven-containment-for-ai-agents/)）。`microsoft/mxc` 采用 **MIT** 许可，用 Rust 编写，SDK 有 Rust、.NET、Node 三种，**没有 Python SDK**；不用 SDK 时可以把 JSON 请求交给 `wxc-exec.exe` 执行。README 里有一节讲“Required diagnostic data”，说明存在遥测（[mxc README](https://github.com/microsoft/mxc/blob/main/README.md)）。Codex 在 MXC 下的已知限制包括：允许与宿主回环上的服务互相连接，前台命令退出后其余子进程会被终止，禁止读取的 glob 只在进程启动时展开一次（[Codex Windows 文档](https://learn.chatgpt.com/docs/windows/windows-sandbox)）。

这里有两处说法需要调和。第一处是版本要求：Codex 文档写的是 24H2 build 26100.9278 或 25H2 build 26200.9278；dsh 2026-08-08 的决策记录写的是“BaseContainer 层需要 25H2+（26600+），更低版本退回 AppContainer + DACL 增补”。dsh 的记录早于 MXC 正式发布，也早于二手报道所说的 8 月补丁 KB5120998（该补丁编号未经微软来源核实），所以应以较新的 Codex 文档为准。第二处是机制：微软博客说 Windows 进程容器基于 AppContainer，而 Codex 的 mxc 适配器说它“never invokes MXC's AppContainer dispatcher”，直接调用 `BaseContainerRunner`（[mxc-sandbox README](https://github.com/openai/codex/blob/main/codex-rs/mxc-sandbox/README.md)）。推断：MXC 内部有不止一层，Codex 选用了较新的 BaseContainer 路径；BaseContainer 与 AppContainer 的确切关系尚未核实。对 MossCode 来说，两处的结论相同：**用户机器是 Windows 11 Home、build 26300，属于 Insider 编号段，既不等于文档列出的版本号，也没有任何来源说明 Home 版是否可用，只能实测**。

**AppContainer 与 LPAC。** AppContainer 把进程与其他应用的窗口、文件、注册表、网络和凭据隔离开，以 Low 完整性运行；令牌不带网络能力时就无法联网，创建也不需要管理员权限（[Implementing an AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer)、[AppContainer isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation)）。代价是默认拒绝的模型：LPAC 甚至要求“all locations … need to have the right ACLs on them”（[Chromium 沙箱设计](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/design/sandbox.md)）。OpenAI 正是因此认为原生 AppContainer“the wrong shape for the problem”（[OpenAI 工程博客](https://openai.com/index/building-codex-windows-sandbox/)）。推断：用户目录下的 `.gitconfig`、npm 缓存、Python 用户 site、MSYS2 家目录默认都读不到，Git Bash 和 pip 会出问题；但同样的默认拒绝也正好保护了 `~/.ssh` 和 `~/.mosscode`。另外，`subprocess.Popen` 无法传入任意进程属性列表，从 Python 调用需要用 ctypes 自己接管管道。

**受限令牌与低完整性。** `CreateRestrictedToken` 加上 `WRITE_RESTRICTED` 后，restricting SID“considered only when evaluating write access”，系统做两次访问检查，两次都通过才允许（[CreateRestrictedToken](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-createrestrictedtoken)）。再给工作区加一个虚构 SID 的 ACE，就能在不需要管理员的前提下精确限制写入，这正是 Codex unelevated 和 dsh 的做法。但它**管不住读取，也管不住网络**，因为进程仍是同一个用户主体，而“Windows doesn't allow matching a firewall rule to the non-principal identity of a restricted token”（[OpenAI 工程博客](https://openai.com/index/building-codex-windows-sandbox/)）。低完整性（MIC）的默认策略是 NO_WRITE_UP，低完整性进程仍能读取大部分文件、使用 TCP（[Mandatory Integrity Control](https://learn.microsoft.com/en-us/windows/win32/secauthz/mandatory-integrity-control)）。在这一点上设计有分歧：Gemini CLI 和 dsh 都用了 Low IL，dsh 自己也承认 Low 标签会长期留在工作区、其他低完整性进程都能写入；OpenAI 则因为这个“sink”问题明确拒绝。本报告站在 OpenAI 一边。

**独立用户 + ACL + WFP。** 只有换一个独立的主体，才能做按用户的防火墙/WFP 过滤和可强制的禁止读取。代价是需要一次 UAC 提权、创建本地用户（在一些企业设备上被策略禁止）、用 DPAPI 保存口令，还要在真实用户的配置目录上授予读取 ACL。从真实用户调用 `LogonUserW` + `CreateProcessAsUserW` 会撞上“privilege wall”，只能改用 `CreateProcessWithLogonW` 启动一个 runner（[OpenAI 工程博客](https://openai.com/index/building-codex-windows-sandbox/)、[deny_read_acl.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/deny_read_acl.rs)）。srt 的 Windows 后端选了同一条路。推断：本地用户和 WFP 在 Home 版上也存在；换用户后 `%USERPROFILE%`、HKCU、git 全局配置都会变，git 的 `safe.directory` 所有权检查也可能被触发。

**Job Object** 是资源、UI 和生命周期控制，不是访问控制边界。它不能限制文件、注册表或网络访问（只能限速），而且“Child processes created using Win32_Process.Create are not associated with the job”，即可以经由 WMI 逃出 Job（[Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)、[网络限速结构](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_net_rate_control_information)）。在任何方案下它都是必需的底层，但不能单独充当边界。**Windows Sandbox** 隔离最强，但“not supported on Windows Home edition”，同一时间只能运行一个实例，宿主上安装的软件不可用，`wsb exec` 也“no way to retrieve the output”（[Windows Sandbox 概览](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-overview)、[wsb CLI](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-cli)）。**WSL2** 能提供 Linux 级别的 bwrap 沙箱和 Hyper-V 防火墙（[Hyper-V 防火墙](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/hyper-v-firewall)），但命令运行的是 Linux 工具，`/mnt/c` 上的用户文件（包括 `.ssh`）默认可见，Zed 也记录了 NTFS 路径上的写入逃逸。**Windows/Hyper-V 容器**需要容器运行时和 Server Core 镜像（[隔离模式](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-containers/hyperv-container)）；**Win32 App Isolation** 面向 MSIX 打包的单个应用，仍在预览阶段（[Win32 app isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/app-isolation-overview)）；Sandboxie 依赖内核驱动，许可证不适合 MIT 项目（[Sandboxie README](https://github.com/sandboxie-plus/Sandboxie/blob/master/README.md)）。这几项都不适合作为按命令的沙箱。

## MossCode 该借鉴什么：一个策略对象、三个平台后端、Windows 分阶段推进

以下建议基于报告前文的事实和对 MossCode 仓库的阅读。凡是关于 MossCode 现状的判断，都来自阅读 `src/mosscode` 源码，属于推断，没有实测。

### 在 `tools/process.py` 上加一个策略编译层

MossCode 的所有子进程都从 `tools/process.py` 启动，Windows 上已经放进 Job Object，`credentials.child_environment()` 也会去掉 `api_key_env` 指向的变量。这正是 Gemini 的 `SandboxManager.prepareCommand()`、dsh 的 `ctx.sandbox.confine(argv, policy)`、Codex 的权限配置文件编译器所需要的挂载点。建议新增一个与平台无关的 `SandboxPolicy`：可写根目录、受保护子路径、禁止读取的路径、网络模式和允许的域名，后者直接复用现有的 `WebFetch(domain:…)` 规则，Claude Code 就是这样合并的。各平台后端把策略编译成包装后的 argv、环境和清理回调，并返回 `enforcement: full | partial` 以及按后端区分的拒绝特征（dsh 的做法）。策略应随每次调用传入，不固定在后端对象上，这样子 Agent、团队成员和越界重试可以同时使用不同的边界。文件工具（`read_file`、`edit_file`）沿用现有的应用层路径检查，不必像 Gemini 那样也绕进沙箱，但两者应当从同一个策略对象取值，避免出现“文件工具不能写、命令能写”或相反的不一致。

macOS 和 Linux 后端建议用 Python 自己实现，不依赖 srt。原因有三：srt 要求 Node ≥22.12，并且仍是 Beta；Seatbelt profile 和 bwrap 参数都是确定性的文本生成，代码量不大；网络代理可以用 asyncio 实现，Unix socket 到代理的桥接也可以自己写，从而不依赖 socat。参考 srt 和 Codex 的设计不受许可证限制；若直接复制 Apache-2.0 代码，需要保留许可证和 NOTICE。Zed（许可证未核实）和 Cursor、Devin、Junie（闭源）只能借鉴设计。Linux 上先用 `--unshare-net`、`--unshare-pid`、全新 `/proc` 和 `--ro-bind / /`，拦截 Unix socket 的 seccomp 留作第二步。推断：用 bwrap 断网不需要 seccomp，但要防住 docker.sock 这类 Unix socket 逃逸，就离不开 seccomp。

### 默认策略和受保护路径要覆盖 MossCode 自己的控制面

默认策略按行业共识：写入限于项目根目录、`.mosscode/worktrees` 和每会话私有的临时目录（同时改写 `TEMP`/`TMP`/`TMPDIR`）；读取默认放开，但 `~/.ssh`（只保留 `config` 和 `known_hosts`）、`~/.aws`、`~/.azure`、`~/.kube`、`~/.docker`、`~/.config/gh`、`.git-credentials`、`.netrc`、`.pypirc`、浏览器配置和 `~/.mosscode` 列为禁止读取，在后端能够强制的平台上生效。这份清单综合了 srt 和 Codex elevated 的排除列表。

受保护路径（即使位于可写根目录内也不可写）是最关键的一项。MossCode 的 `permissions.py` 已经有一份 `PROTECTED_FILES`（`.mosscode/permissions*.yaml`、`.mosscode/mcp.yaml`、`.mosscode/hooks*.yaml`、`.mcp.json`），但它只约束文件工具。命令走 Git Bash 或 PowerShell 时，目前以用户的完整权限运行，同样能改写这些文件。沙箱的写保护清单应当是它的超集：再加上 `.mosscode/config.yaml`、`.mosscode/plugins.yaml`、`.claude/` 下的 settings、agents、skills、commands、hooks（MossCode 会加载这些目录），`.git/hooks`、`.git/config`、`.gitmodules`，以及整个 `~/.mosscode`。必须包含 `~/.mosscode` 的原因是：团队成员的邮箱文件 `~/.mosscode/projects/<key>/teams/…` 承载 `permission_response` 消息，也就是用户在主窗口里替窗格成员作出的审批答复；`~/.mosscode/permissions.yaml` 则是用户级权限规则。能写这些文件的命令，就能伪造审批或给自己加 allow 规则，这正是 dsh CVE 和 Amp 配置自改问题在文件层面的翻版。Codex 预先创建缺失受保护路径的做法、Claude Code 对符号链接同时拒绝其真实路径的做法，都应一并采用；对应的绕过测试（符号链接、硬链接、重命名父目录、先删后建）按 AGENTS.md 的要求补齐。

### 沙箱和权限档位是两个独立开关

Qwen、Junie、dsh、Codex 一致认为：**审批决定“是否运行”，沙箱决定“能碰到什么”，两者互不放宽**。Gemini 让 yolo 打开网络，是更弱的设计。下表是建议的对应关系。

| MossCode 档位 | 沙箱策略 | 沙箱内的命令 | 越界申请 |
|---|---|---|---|
| plan | 只读，断网 | 维持现有只读白名单；有了只读沙箱后，可考虑放宽计划模式可执行的命令（Gemini 的 plan 即只读加断网） | 不允许 |
| default | 写项目 + 临时目录，断网，域名按需询问 | 后端为 `full` 时免审批，但 deny 规则、灾难级拒绝和高风险级确认照旧（同 Claude Code）；后端为 `partial` 时维持现有审批 | 模型带理由申请，用户可选 once / session / permanent / deny |
| acceptEdits | 同 default | 同 default | 同 default |
| bypassPermissions | 沙箱照常开启（同 Junie 的 brave mode） | 不审批 | 是否自动放行沙箱外执行：待定 |

`partial` 时不免审批，是本报告的关键判断。在 Windows 受限令牌后端下，读取和网络都不受限，免除审批就等于允许命令无声地读取并外发文件；Claude Code 的“免审批”成立，是因为它的网络边界在操作系统层面强制生效。现有的灾难级和高风险级分级继续独立于沙箱生效，对应 Claude Code 在 auto-allow 下仍会询问的关键路径 `rm`。会放宽沙箱的配置键（禁用文件层、额外可写路径、放行域名、允许沙箱外执行）只接受用户级配置；项目配置只能收紧，并且不能通过现有的项目信任提示解锁。这一做法来自 Kilo、Junie、Qwen 和 Claude Code。

### 被拒之后返回结构化结果，越界需要说明理由

Cursor、Claude Code 和 Gemini 的经验一致：模型必须知道自己在沙箱里。建议做三件事。第一，`execute_command` 的工具说明写明当前边界：可写目录、网络状态，以及强制级别是 full 还是 partial。第二，被拒时在结果末尾追加机器可读的违规块，列出被拒的路径或主机和原因（参考 srt 的 `<sandbox_violations>` 和 dsh 的 `sandbox.denied`），并沿用 MossCode 现有的结构化工具结果，而不是只返回 stderr。第三，给工具加两个参数：`sandbox: "require_escalated" | "with_additional_permissions"` 和 `justification`，交给现有的审批面板展示，面板标题明确写“在沙箱外运行”。Gemini 那种从 stderr 推断所需路径的启发式可以作为辅助，用于在审批面板里预填路径，但不能自动放行。Codex 的一条规则值得照搬：存在禁止读取策略时，越界也只放开写入和网络，不放开那些禁止读取的路径。

失败处理需要明确选边并显示在界面上。建议默认**失败关闭**（Kilo、Devin、Qwen、dsh），提供一次性的显式“本会话不使用沙箱”选项（Junie）。启动时做一次自检：用生成的策略实际执行一次受控的越界写入和一次直连，确认都被拦截（Junie）。再增加 `moss sandbox --verify` 或并入现有的 `doctor.py`（Qwen 的 `qwen sandbox --verify`）。

### 网络代理与密钥

网络的目标形态是：命令只能连接 MossCode 自己的回环代理，代理按 `WebFetch(domain:…)` 规则放行域名，不在名单上的域名进入审批，并检查解析结果。MossCode 的 `security.py` 已经为 `web_fetch` 判断地址是否为本机或内网，可以直接复用来拒绝解析到回环、私网和云元数据地址的连接。代理必须认证（srt 和 Kilo 都在代理 URL 中带每命令的随机令牌），否则任何本机进程都能借道出去。HTTPS CONNECT 时校验 SNI 与目标主机一致（Kilo）。在 Linux 和 macOS 上，这种拦截由内核强制；在 Windows 上，只有 MXC（拒绝出口、允许回环）或独立账户 + WFP 能强制。受限令牌后端只能做 Codex unelevated 那种环境变量引导，界面上必须标明“网络未受限，仅为建议”。

密钥方面，MossCode 已经把 API 密钥存进凭据管理器，子进程也不继承 `api_key_env`，起点比 Codex 的默认值好。下一步是把子进程环境从“去掉黑名单”改成“白名单 + 按名称和值的形态清理”：保留 `PATH`、`HOME`、`USERPROFILE`、`SYSTEMROOT`、`TEMP`、语言和终端相关变量，其余的 `*TOKEN*`、`*SECRET*`、`*PASSWORD*`、`*PASSPHRASE*`（dsh 漏掉的那种）以及形如私钥、JWT 的值一律去掉，同 Gemini 的做法。不要把会话 ID、团队目录或任何控制端点放进命令环境。Claude Code 的 `mask` 模式（沙箱内是哨兵值，代理替换真值）需要 TLS 终止和自签 CA，代价较大，建议等网络代理稳定后再评估。

| 1：探测 | 在用户的 Windows 11 Home 26300 上运行 `wxc-exec.exe`，测试最小策略和 Git Bash、PowerShell、ConPTY 下的行为 | 不需要 | — | Codex 的 MXC_OK 探测 |
| 2a：MXC 可用 | 后台调用 `wxc-exec.exe` + JSON 策略：写项目、禁止读取密钥目录、拒绝出口、只放行回环代理；标为 full | 不需要 | 写、读、网络 | Codex `mxc`、Copilot |
| 2b：MXC 不可用 | ctypes 实现 `CreateRestrictedToken(DISABLE_MAX_PRIVILEGE｜LUA_TOKEN｜WRITE_RESTRICTED)`，restricting SID 为 [工作区能力 SID, logon SID, Everyone]；工作区和私有 TEMP 加允许 ACE，受保护子路径加拒绝写入 ACE 并预先创建，对父目录拒绝 `FILE_DELETE_CHILD`；`CreateProcessAsUserW` 放进 Job；不使用 Low IL；对 Everyone 可写的目录发出警告；提供清理 ACE 的命令；标为 partial | 不需要 | 仅写入 | Codex unelevated、dsh |
| 3：可选严格模式 | 独立账户 + WFP（自己实现，或调用 srt 的 `windows-install` 作为外部后端） | 一次性 UAC | 写、读、网络 | Codex elevated、srt |
| 旁路 | Linux 项目用 WSL2 + 同一个 bwrap 后端（隐藏 `/mnt/*`）；最强隔离用 Docker Sandboxes 或 E2B，配合会话移交 | 安装一次 | 视方案而定 | Cursor、Zed、Docker、E2B |

2a 和 2b 的先后由第 1 步的结果决定。MXC 若可用，工作量最小，保护也最完整；但它会在前台命令退出后终止其余子进程，MossCode 的后台 shell 和开发服务器需要作为长期存在的容器单独启动。同时还要先弄清 `wxc-exec.exe` 的分发条款和遥测默认值。2b 在任何 Windows 11 上都能运行，但会在用户真实的仓库上留下持久的 ACE，首次给大目录授权可能需要数十秒（dsh），硬链接也有缺口。另有一个风险两份笔记都没有覆盖：Git Bash（MSYS2）在 WRITE_RESTRICTED 令牌或 AppContainer 下的兼容性，涉及 `/tmp` 映射、`~/.bash_history`、共享内存和 fork 模拟，没有任何来源验证过。Codex 主要以 PowerShell 为默认 shell。srt 的经验还表明，受限令牌下 Schannel 系列工具（`Invoke-WebRequest`、winget、dotnet restore）会失效，必须通过一条经审批的沙箱外路径执行。

### 控制面：dsh 的教训落到 MossCode 上

在 `src/mosscode` 中搜索 `listen`、`create_server`、`HTTPServer`，没有找到本地 HTTP 监听，因此目前不存在 dsh 那种回环管理接口（推断）。但 MossCode 有文件形态的控制面：团队邮箱、权限规则、插件和 hooks 配置、项目信任记录。规则只有一条：**凡是能改变权限、审批结果或宿主之后会执行的内容的通道，都不得出现在沙箱可写或可达的范围内**。具体来说：文件通道由上文的写保护清单覆盖；将来如果加入 IDE 集成、HTTP 形式的 MCP 服务或团队协调服务，必须做认证，并且不把地址和令牌放进命令环境。MXC 和 WFP 方案都会放行回环地址，所以这条规则在 Windows 上同样适用。Qwen 的警告也应写进文档：沙箱内命令写出的一切，包括 Makefile、`package.json` 脚本、`.git` 里允许修改的部分，都要当作不可信的产物；在沙箱外运行的 hooks 和 MCP 不应自动执行这些产物。

## 结论

这次调研最重要的发现是：沙箱的意义不只是安全，更在于把审批从“每条命令问一次”改成“越界才问”。前提是边界由内核强制，并且模型能看到边界在哪里。这个前提在 macOS 和 Linux 上已经有现成工具可以满足；在 Windows 上，它在 2026 年第四季度才刚刚变得可行，而且只在两种条件下成立：MXC 可用，或者用户愿意做一次管理员安装。因此，MossCode 不应该把“有沙箱”当成一个布尔值，而应该把强制级别（full / partial）作为一等状态：它决定是否免除审批，也要明确显示给用户和模型。用 Windows 受限令牌冒充完整沙箱，比不做沙箱更危险。

第二个发现是：几乎所有已知的逃逸都不是攻破内核原语，而是绕到了沙箱旁边。dsh 的回环管理接口、Amp 改写自己的配置、`.git/hooks` 和 `core.fsmonitor` 投毒、docker.sock、可写 PATH 目录上的二进制都属于这一类。对 MossCode 来说，近期收益最高的工作并不是 Windows 令牌编程，而是先把宿主自己的控制面——`~/.mosscode`、团队邮箱、权限和插件配置、项目内的 agent 配置和 git 钩子——从命令可写的范围里移出去，并把子进程环境改成白名单。这一步在任何后端落地之前就能做，也决定了将来任何后端的上限。
