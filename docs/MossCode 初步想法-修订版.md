# MossCode 初步想法：面向 Agent 应用工程的 Coding Agent

## 项目定位

我要用 Python 从零实现一个终端 Coding Agent，名为 MossCode，用于学习和展示 Agent／大模型应用工程能力。

参考 MewCode 的功能拆解与工程学习路径，借鉴 Pi 的小核心、清晰职责边界、可组合扩展与会话上下文设计。Claude Code 是产品体验和交互能力的参考。具体实现及取舍由 MossCode 自己决定，并记录参考来源。

项目的目标是做出能解释、能验证、能演进的 Agent：模型通过工具作用于项目环境，运行时负责调用循环、状态、取消、权限、上下文和验证反馈。核心能力稳定后再增加扩展，不以复刻参考项目的全部功能为目标。

这里的 harness 指围绕模型工作的运行支撑：工具执行、上下文管理、运行状态、会话、事件和权限边界。它是一组系统职责，既不要求特定框架，也不要求先实现多 Agent。

## 总体设计方向

采用以下职责划分，初期可放在少量模块中，不为了分层增加空接口。

| 部分 | 主要职责 |
|------|----------|
| Provider 适配 | 构建特定协议请求、消费流式响应，转换成统一消息与事件；保留协议所需的专属数据 |
| Agent Core | 驱动模型与工具的反馈循环、处理取消和结束条件，输出运行事件，不依赖终端界面 |
| 会话与上下文 | 维护规范的消息状态；后续保存完整会话并选择模型实际看到的上下文 |
| 工具执行边界 | 参数校验、执行、结果处理、权限判定和取消；初期不启用工具 |
| 应用与 TUI | 读取配置、展示事件、接收输入，将取消或确认操作传递给运行时 |
| 扩展 | 后续接入项目指令、Skill、生命周期 Hook 或外部工具，不另建一套 Agent Loop |

数据方向：输入 → 运行时 → Provider → 模型；模型事件 → 运行时 → TUI。启用工具后，由同一运行时调度工具并把结果送入下一轮。

核心边界是：TUI 不组装厂商请求；Provider 不管理会话生命周期；扩展不直接绕开工具执行边界；会话记录与模型上下文不是同一个概念。

## 第一阶段：可演进的流式对话内核

### 阶段目标

用户在终端启动 MossCode，进入交互界面，输入问题后获得实时流式回复。支持多轮对话，并能取消当前请求后继续使用。

本阶段仍然只做对话，是未来 Coding Agent 的基础，还不能据此宣称已经实现自主编程 Agent。

### 功能要求

- 第二章同时支持 Anthropic Messages、OpenAI Responses 和 OpenAI Chat Completions；官方与兼容服务通过协议、端点和模型配置接入，不设置供应商白名单。
- 通过配置选择 Provider 和模型。第一阶段在启动时选择配置，切换配置后开启新会话；会话内跨模型切换在后续验证消息转换规则后加入。
- 消费后端 SSE 流，按收到的文本增量更新界面，不等完整响应返回。增量可能包含多个字符，不人为要求“一字一个事件”。
- 支持多轮对话，模型请求来自同一份规范的会话状态；TUI 不另存一份业务历史作为事实来源。
- 在目标模型支持时启用 Claude thinking。具体模式与参数由 Provider 根据明确的模型能力处理；不支持的组合明确报错。
- 区分正文、可返回的 thinking 内容、用量、结束原因与错误。只展示 API 返回的数据，不假定所有模型都公开完整推理过程。
- 用户取消后关闭当前流、释放资源并返回可输入状态。部分输出可以展示，但标记为取消或失败，不当作成功的完整回复写入下一轮上下文。
- 对认证、网络、限流和配置错误给出可理解的提示；重试次数有限，已输出部分内容的请求避免无提示地重新发送或拼接重复回复。

### 现在需要确定的基础数据

- 规范消息采用结构化内容块，至少支持正文与 Provider 所需的 thinking／签名等数据。后续工具调用、工具结果通过有标识的内容块扩展。
- 统一流事件表达文本增量、thinking 增量、用量、结束和失败；厂商的原始 SSE 类型只在适配层处理。
- Provider 可保留必要的专属元数据，统一接口不等于把所有协议信息压成字符串。跨 Provider 发送历史时按目标协议转换，不盲目回传其他厂商的数据。
- 用同一对话内核支持 TUI 和无界面的调用。先做一个能被脚本调用的入口，不必第一阶段搭建完整服务。
- 暂不实现会话树和持久化事件系统；先让规范消息、当前运行状态与界面显示状态有清楚的归属。

### 配置

仍使用 YAML，但不把“恰好六个字段”当作长期约束。

| 字段 | 用途 |
|------|------|
| name | 配置标识 |
| protocol | 明确的协议，例如 `anthropic-messages` 或 `openai-responses`；第三方兼容协议单独定义 |
| model | 目标服务实际支持的模型 ID |
| base_url | 请求端点 |
| api_key_env | 保存 API key 的环境变量名称；如兼容直接 api_key 配置，不把密钥写入会话和日志 |
| thinking | 可选的思考偏好；由能力配置验证并映射，不仅用布尔值表达所有模型差异 |

超时、输出上限和重试等选项在实现确有需要时增加。先覆盖选定模型与协议，不承诺任意 OpenAI 兼容端点都能无差别运行。

### 不在本阶段实现

工具调用、文件读写、代码修改、Shell 执行、MCP、Skill、Hook、子 Agent、团队调度、长期记忆、自动上下文压缩，以及完整会话树界面。

### 阶段验收

1. 两个真实 Provider 分别可以流式对话；第二轮能使用第一轮的相关信息。
2. UI 和无界面入口共用对话内核，协议分支集中在 Provider 层。
3. 支持 thinking 的选定 Claude 模型可运行对应模式；正文与思考数据不混淆，后续请求保留协议所需内容。
4. 文本分块、错误和取消可用确定性模拟流复现；取消后能够发起下一次请求，未完成输出不伪装成完成消息。
5. 错误密钥或断流不会破坏已完成的对话状态，不出现无限重试或重复回复。

这些是实现后的验收目标，当前文档不代表上述功能已完成。

## 后续里程碑

### 第二阶段：最小 Coding Agent 闭环

加入读取、写入、精确编辑与终端命令四类工具，命令执行适配本机 Shell，不把 Bash 写死为跨平台协议。

同一 Agent Core 完成“模型请求 → 完整工具参数校验 → 权限判断 → 执行 → 返回带调用 ID 的结果 → 下一次模型请求”。第一版工具顺序执行，先验证依赖和失败语义，再考虑并发。

设置可解释的停止条件：正常结束、用户取消、步数或预算限制、不可恢复错误。失败结果能回馈给模型；运行停止原因可被观察。文件修改和命令执行受到明确策略控制，策略判断不等同于操作系统沙箱隔离。

演示目标：读取一个小型示例工程，修复一个有失败测试的 bug，运行测试确认结果。需要真实展示改动和验证证据。

### 第三阶段：可恢复、可检查的运行

追加保存完整的会话条目和关键运行结果，建立唯一的会话事实来源。按需要支持分支和恢复；trace 中可记录细粒度事件，但不要求把每个字符增量都变成持久化会话条目。

将模型上下文作为从会话构建的视图：压缩产生摘要及边界记录，完整会话保留；工具调用与结果的关联不能因压缩或取消失效。会话恢复不自动重复执行已产生副作用的工具，“重放记录”与“重跑任务”分别设计。

评估完成率、工具调用数、Token 用量、耗时、取消行为和失败类型。保存 Provider、模型、任务、配置与结果，使数据可以复核；不同模型能力和 harness 改进分开讨论。

### 第四阶段：一个可证明的扩展点

先选一个有实际用途的 Skill 或生命周期 Hook：例如项目指令按需加载，或工具执行前的策略检查。接入后用相同核心和验收场景证明扩展不破坏行为。

按需求决定是否增加 MCP；多 Agent、Worktree 和自动长期记忆作为后续可选方向，不作为面试项目完整性的前提。

## 面试中的项目主线

重点解释四类取舍：多协议统一时如何保留差异；UI 如何与运行状态分离；工具循环如何处理中断及副作用；完整会话与有限模型上下文如何保持一致。

至少交付一个可以实际运行的 bug 修复案例、一组确定性的异常场景，以及带配置和轨迹的真实模型评估。指标在实验后填写，未实现或未测试的能力清楚标记。
