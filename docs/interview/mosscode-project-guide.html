从流式对话，到受控执行的编程 Agent。

这份讲解围绕一个问题展开：当模型能够读写文件、执行命令并自主循环时，应用怎样决定它是否可以执行，又怎样在被拒绝、取消或发生错误后，维持正确的任务状态？

先记住这句项目介绍

“MossCode 是一个本地终端编程 Agent。我实现了流式对话、工具调用和自主执行循环，并把权限检查放到真实执行入口，让模型负责选择下一步，由运行时决定这一步能不能执行。”

01

项目定位：重点在 Agent 运行时

MossCode 的目标是把大模型接入真实的开发工作流：用户用自然语言描述任务，模型选择工具，程序执行工具并回传结果，模型继续判断，直到结束或遇到停止条件。项目参考 MewCode 的章节路线，学习 Pi 的 Harness 思路，并参照 Claude Code 的终端交互布局。

模型负责

理解任务与选择动作

分析需求、产生正文或工具调用、根据成功和失败结果调整策略。项目没有训练自己的模型，也不把模型输出视为已获授权。

HARNESS / 运行时负责

把一次动作执行正确

组装提示与上下文，适配服务协议，校验工具参数，决定权限，安排并发，处理超时、取消和历史一致性，再把事件交给界面。

这里的 Harness 是对项目职责的归纳。当前实现吸收了 Pi 的工具贡献提示、清晰模块边界等思路；并未实现 Pi 的完整扩展体系，也不声称复制了 Claude Code 的内部实现。

一次真实任务怎样走完

接收任务，组装稳定提示与动态环境

Conversation 提供会话入口，AgentLoop 不依赖 TUI 或具体 SDK。稳定提示和工具描述保持前缀稳定，环境与模式提醒另行注入。

双路收集流式响应

片段实时推送界面，同时积累完整响应。工具参数可能跨多个 JSON 碎片；只有完整响应收集完毕，才允许进入工具执行。

校验、授权，再安排工具任务

相邻只读工具最多四个并发；写入、编辑、Shell 串行，保留操作顺序。执行之前统一经过权限入口。

把每个工具结果配对回写，再继续模型请求

普通失败与权限拒绝都是可观察结果。模型可以换路径、换策略；无工具请求时结束。默认最多 25 次请求，连续三轮全是未知工具时停止，取消或流错误也停止。

三种“历史”要分开讲

模型消息历史在当前进程内存中，用结构化 Message / 内容块组织；终端滚动历史供用户翻看；服务端提示缓存用于复用输入计算。当前没有退出后的会话恢复。终端显示高度与模型的 1M Token 窗口是两回事。

04

这一章：在执行入口建立权限边界

工具出现之前，错误大多表现为回答不准确；工具出现之后，错误可能变成覆盖文件或执行不该执行的命令。这一章把“能调用工具”和“获准执行工具”分开，权限判断由应用代码完成。

控制手段解决的问题可否被授权绕过
危险命令硬拦截已知高危删除、磁盘操作、关机、Git 强制操作、编码/动态执行等特征。不可解除，但正则只覆盖已知模式。
项目路径隔离专用文件工具的解析目标越界；命令 cwd 越界。不可解除，不等于限制子进程全部访问。
分层规则对具体工具、文件范围或命令作明确 allow / deny。按最高匹配层判断；同层 deny 优先。
权限档位决定未命中规则时，哪些操作可自动通过、哪些需要确认。放行档位仍遵守硬限制与最终生效 deny。
人在回路审批对需确认操作取得本次、会话或永久授权。不能解除硬限制、计划限制或生效 deny。

“五层防御”描述五种互补控制，不代表五层操作系统隔离。计划模式是额外的任务能力限制，先于上述授权流程。

实际执行顺序

工具存在吗？计划模式允许吗？参数合法吗？

拒绝未知工具、计划模式副作用工具、非法 JSON 和不符合 Schema 的参数。

硬检查：目标解析、命令黑名单、权限文件保护

由 PermissionPolicy.operation 构造规范化操作；越界或危险操作直接拒绝，不弹出可放开的审批。

查最高匹配规则层，再应用权限档位

规则给出 allow / deny；运行时还可能得出 ask。严格模式下，匹配 allow 也仍然要确认。

需要确认则等待用户；批准后重新核对目标

无界面模式返回 approval_required。交互批准后检查实际目标和 cwd 是否改变，并重新判断拒绝规则。

获准后才创建实际执行任务，启动执行超时

ToolRegistry 的 create_task 位于 authorize 成功之后。等待用户不消耗工具的执行时限；实际文件 IO 前还会复查路径。

05

沙箱详解：先找到实际目标，再判断范围

面试时建议用这个准确名称：应用层项目路径隔离。

它约束专用文件工具通过哪些路径进行访问。执行命令的进程没有被放进容器或系统级文件沙箱；不能把本章称为任意代码的安全执行环境。

核心算法只有几步，关键在顺序

# 讲解用摘录，省略错误消息；对应 security.py / project_path
# root 是启动时 resolve() 后捕获的项目根路径
def project_path(root, value):
    if not str(value) or "\0" in str(value):
        raise SecurityError("invalid_path", ...)
    path = Path(value).expanduser()
    path = (path if path.is_absolute() else root / path).resolve()
    try:
        path.relative_to(root)  # 默认不允许向上走；按路径组成部分比较
    except ValueError:
        raise SecurityError("path_blocked", ...)
    return path

为什么先 resolve？

输入可能含 ..、符号链接或 Windows junction。看似位于项目内的 cache/link/data.txt，实际目标可能在项目外。判断的是解析后的目标，而非用户输入字符串。

为什么不使用 startswith？

F:\work\MossCode-other 也以 F:\work\MossCode 开头，却是同级目录。relative_to(root) 按路径组件检查包含关系，避免这种错误。

Python 官方说明：resolve 会解析符号链接并消除 ..；默认 strict=False，会尽可能解析现有部分，再追加尚不存在的尾部。新建文件因此也要考虑已有父目录的链接目标。参见 Python 3.12 pathlib 文档。

通过路径检查

实际目标在项目内。接下来仍需判断具体工具的规则与权限档位；通过路径检查不等于已获得执行授权。

代码不仅检查入口，也检查真正使用的路径

位置具体措施为什么需要
启动时捕获已解析的固定根路径，后续不重新解析根锚点。根目录之后被换成外部链接时，不能跟着把信任范围搬到外部。
权限判断时将工具 path 或命令 cwd 解析到实际目标，再判断包含关系。拒绝绝对路径、../、同前缀相邻目录和链接越界。
用户批准后重新构造 Operation，比较目标与 cwd，变化返回 target_changed。避免用户批准的是旧目标，实际执行的是另一个目标。
文件 IO 前读写编辑的工作线程内再次从原参数解析路径。缩短检查与 IO 的间隔，降低等待或调度期间的变化风险。
搜索过程中检查搜索入口，并限制遍历/候选文件的实际目标；默认跳过依赖目录。不能只检查搜索根目录，再通过其中的链接递归进入项目外。

最容易被问住的点：命令的 cwd 不是文件沙箱

专用文件工具

路径由应用掌握

Read(../private.txt) 的目标解析后在项目外，直接返回 path_blocked。即使切到放行档位，也不能执行。

执行命令工具

子进程自行访问文件

即使 Python 的 cwd 是项目目录，代码仍可能读取项目外的绝对路径。MossCode 当前检查 cwd、已知危险特征和授权状态；它没有拦截子进程的每次系统调用。

结论：默认命令需要确认，是因为应用层无法完整掌握命令的实际效果。确认表示用户接受这次操作；它不会把子进程的系统权限降低，也不能替代系统级隔离。

现有 Windows Job Object 用于管理命令进程及其子进程的生命周期，取消时清理进程树。项目没有把它当作文件访问隔离；微软文档分别说明了进程分组、终止和可配置限制。参见 Microsoft Job Objects。

重复检查仍然无法证明没有 TOCTOU

T1 · 检查路径解析仍在项目内。
→
T2 · 其他进程改变目录检查后、使用前替换链接。
→
T3 · 实际 IO路径可能已指向另一个目标。

这是检查时与使用时的竞争问题。当前通过批准后重查、IO 前重查降低风险，但没有基于操作系统句柄或不可逃逸执行环境构建完整保证。重复 resolve 不能把检查和 IO 变成原子操作。参见 MITRE CWE-367。

还要准确说明的边界

项目内的敏感文件并不会自动被识别或脱敏；规则按工具生效，Read(secret.txt) 的 deny 不自动等同于所有工具都禁止访问。Shell 也可能修改权限文件，专用写入工具的保护不能约束任意已获准命令。硬链接对象身份隔离、网络访问限制和系统级沙箱不在当前验收保证内。

后续方向：若要支持执行不可信代码，需另行设计操作系统层的执行隔离，统一考虑文件、网络、凭据和资源边界，再进行对抗验证。这是下一阶段的设计任务，当前还未实现。

06

规则：先确定哪层生效，再应用档位

由高到低找到第一层匹配

1 · 会话级内存临时规则 · 退出失效
2 · 本地级<root>/.mosscode/permissions.local.yaml
3 · 项目级<root>/.mosscode/permissions.yaml
4 · 用户级~/.mosscode/permissions.yaml

一旦该层有匹配，就在该层决策；同层同时匹配 allow 和 deny 时，deny 优先。更高层 allow 可以覆盖更低层 deny。

具体规则长什么样

mode: default
allow:
  - Read(src/**)
  - Bash(git status)
deny:
  - Write(.git/**)
  - Edit(.git/**)

Bash 是规则别名，Windows 实际仍运行 PowerShell。文件 * 匹配单段，** 可跨目录。Glob / Grep 规则匹配搜索范围路径。

交互演示 · 权限决策为什么是这个结果

这是按当前策略编写的固定情境模拟，不加载你的规则文件，不执行工具。展示批准之前的决策。

工具操作read_file(src/main.py)
    允许执行

    默认档位下，无规则的只读工具自动通过。

    两个维度不能混在一起

    /plan 决定任务允许使用的能力；/permissions 决定在这些能力内怎样取得授权。计划模式 + 放行档位，依然不能写文件或执行命令。

    为什么 Bash(git *) 不能顺带批准追加命令

    命令规则匹配完整原始命令；通配符 allow 还要经过保守的简单命令检查。串联、管道、重定向、变量或命令替换不能仅凭宽泛 glob 自动获准。git status; python helper.py 因此不会因 Bash(git *) 自动授权；默认档位会转为确认。若用户配置了完整精确命令规则，或者启用放行档位，仍可能获准，硬拦截继续生效。

    黑名单检查完整命令中的已知特征；它不是完整 Shell 解析器，可能误报，也无法识别所有混淆、脚本间接执行和程序实际副作用。

    审批：异步等待，不把 UI 塞进 Agent

    PermissionPolicy创建请求 ID + Future
    →
    审批队列 / 事件流execute_batch 转发请求
    →
    TUI 面板用户选择 + 请求 ID
    →
    respond → 复查完成 Future，再决定执行

    权限模块不导入 TUI。审批请求包含真实工具、目标、cwd、原因和内容预览，通过独立事件传给界面；UI 用请求 ID 返回选择。并发工具通过审批锁排队，避免多个请求争抢输入。审批事件不进入模型历史，模型只接收工具调用与实际工具结果。

    用户选择授权作用域保存位置
    本次允许只执行当前调用。不保存规则。
    本会话允许具体工具 + 具体目标；命令还绑定 cwd。当前进程内存，退出失效。
    永久允许精确匹配，避免自动扩大到通配授权。当前项目 .mosscode/permissions.local.yaml。
    拒绝 / Esc拒绝当前调用；模型可调整策略。返回 permission_denied。
    Ctrl+C取消整个任务，清理等待与执行任务。保留已发生的效果和对应结果。

    永久授权：不能把“这一次”悄悄扩大为“所有操作”

    # 示例：用户永久允许在 src 目录执行这条命令
allow:
  - rule: execute_command(git status)
    exact: true
    cwd: src

    文件授权限定具体工具与文件，文件名里的通配字符不会被扩大解释；命令授权限定完整命令及目录。保存前重读本地规则，保留已有内容，用临时文件加原子替换写入。若保存失败，返回 permission_save_failed 并不执行；不会让 UI 宣称“永久授权成功”而实际没有保存。

    严格档位即便已有会话或永久 allow，仍逐次确认。原子替换防止半份文件写入，不代表跨进程并发编辑具备事务或无丢失更新保证。规则通常在启动时加载，当前没有完整的自动热重载。

    权限拒绝是模型可观察的执行反馈

    {
  "ok": false,
  "output": "用户拒绝了此操作；此调用未执行。",
  "code": "permission_denied",
  "details": { "executed": false }
}

    拒绝不直接结束 Agent Loop。模型收到明确失败，可改为调查、换成允许的目标或向用户解释，仍受轮数上限约束。无界面调用遇到需确认操作返回 approval_required，不永久挂起等待不存在的 UI。

    执行前

    审批期间不能有副作用

    真实工具执行任务在授权成功之后才创建，审批等待不计入执行超时；取消时移除 pending 请求，旧请求 ID 不能再授权。

    执行后

    历史必须承认实际效果

    已经写入的文件不会因取消自动撤销。保存实际结果，为每个完整工具调用补齐结果；未启动的标记未执行，避免模型历史与磁盘状态脱节。

    查看实际审批界面预览

    面试中可以讲出的四个取舍

    统一入口，比在 UI 加确认更可靠

    TUI 和 --prompt 共用执行入口。即使没有界面、模型直接请求工具，也必须经过相同策略；没有 UI 时不会默认替用户批准。

    支持分层和 glob，但自动保存精确授权；复杂 Shell 不凭宽泛 glob 放行，减少授权扩大。代价是一些合法复杂命令也需要确认。

    异步事件解耦与取消一致性

    Agent、权限和 TUI 分离，便于复用和测试；相应需要处理 pending Future、队列、任务取消与结果配对，不能仅写一个同步弹窗。

    阶段性隔离与真实边界

    先实现文件路径隔离和命令审批，控制本章范围；明确子进程与 TOCTOU 的限制，为后续系统级隔离留下独立执行边界。

    可以直接练习的面试讲解稿

    30 秒 / 定位与关键贡献

    我做了一个 Python 终端编程 Agent，叫 MossCode。它支持流式对话和六个本地工具，模型能自主循环处理任务。我的重点是运行时工程：工具执行前统一校验参数和权限，文件工具限制在项目路径内，命令默认由用户确认；拒绝或取消后仍保持工具结果与历史一致。目前做到第六章权限系统，也明确区分了应用层路径隔离和真正的系统级沙箱。

    90 秒 / 架构与设计选择

    MossCode 是一个本地编程 Agent。用户输入任务后，模型选择读文件、编辑、搜索或命令工具，运行时执行并把结果回传，模型再决定下一步。我参考章节项目逐步开发，同时学习 Pi 的 Harness 思路，把模型适配、循环、工具、权限和终端界面分开。

    循环采用双路流式收集：一边更新 UI，一边积累完整响应，所以不会在 JSON 参数没收完时执行工具。相邻只读操作可以并发，写入和命令串行，结果按原始调用顺序写入历史。计划模式除了限制工具定义，还在执行入口再次拦截写入。

    这一章我增加统一权限入口，包含危险命令硬拦截、项目路径隔离、分层规则、三档权限和异步用户审批。永久授权只保存具体工具、目标及命令目录，避免扩大范围。拒绝会作为结构化工具结果进入下一轮，取消不会掩盖已经发生的写入。

    当前沙箱属于应用层路径隔离，子进程仍有当前用户的系统权限。我通过本地测试和 Windows 实际控制台验证这些行为，系统级隔离、会话恢复和上下文压缩留在后续阶段。

    3 分钟 / 权限与沙箱的深入讲解

    MossCode 的核心是“模型提出动作，运行时决定动作是否能执行”。在模型有了工具和自主循环后，提示词里写“不要危险操作”是不够的，所以我把权限策略接到 ToolRegistry 的真实执行入口。校验工具、计划模式和参数后，先做硬检查，再按规则和权限档位决策，获准后才创建执行任务。

    路径沙箱的实现分三步：启动时捕获解析后的项目根路径；把工具输入解析成绝对实际路径，包括 .. 和目录链接；最后通过 relative_to 按路径组件判断包含关系。不能用字符串 startswith，因为 MossCode-other 也具有相同前缀；也不能只看表面路径，项目里的 junction 可能指向外部目录。创建新文件时，现有父目录的链接同样要解析。搜索除了检查入口，还要检查遍历目标。

    根锚点固定后不会跟着目录链接重新解析，防止信任边界被搬走。用户审批可能等很久，所以批准之后还要重查目标和 cwd，变化就拒绝；实际文件 IO 前也再检查。不过这些检查不是与 IO 原子绑定的，仍不能证明没有其他进程并发替换链接的 TOCTOU 风险。

    更重要的是，这一套只约束专用文件工具。命令的 cwd 在项目内，不代表 Python 或 PowerShell 无法读写项目外文件。当前命令默认确认，同时拦截已知危险特征；黑名单不是完整 Shell 解析器，用户确认也不是操作系统隔离。已有 Job Object 用来取消和清理进程树，不提供项目文件沙箱。

    规则按会话、本地、项目、用户从高到低找第一层匹配，同层 deny 优先。更高层可以覆盖更低层；但权限档位不会忽略最终生效的 deny。严格档位逐次确认，默认档位无规则时放行读取，放行档位跳过未匹配操作的确认。计划模式是另一个维度，不能用放行档位解除只读限制。

    审批通过事件队列传给 UI，再用请求 ID 完成等待的 Future。永久放行写入本项目本地 YAML，只精确授权工具和目标，命令再绑定 cwd；保存失败不执行。拒绝回写结构化结果让模型调整，取消则清理 pending 和执行任务，同时保留实际效果与配对历史。

    第六章的本地回归是 242 个通过、一个文件符号链接测试因权限跳过，真实 Windows junction 与控制台烟测通过。这些证明关键实现行为，不能等同于任意代码安全。下一步若要执行不可信代码，需要独立设计系统层文件、网络、凭据和资源隔离。

    面试追问：先回答结论，再给证据

    01 · 这和普通的“调用 LLM + function calling”有什么区别？

    工具调用只是模型返回动作的协议。MossCode 还负责持续循环、工具调度、授权、执行超时、取消和结果一致性，以及流式事件对 UI 的解耦。比如写入已经完成后模型续答断流，运行时必须保留这个结果，不能把整轮丢掉。

    02 · 为什么不用提示词解决权限？

    提示词影响模型选择，不负责实际强制执行。模型参数、文件内容和工具输出都不能直接生成用户授权。真正拒绝在 ToolRegistry 和 PermissionPolicy 内发生，TUI 与无界面入口共用这个边界。

    03 · 沙箱为什么不用路径字符串前缀？

    同前缀相邻目录会误判，符号链接也可能让表面路径与实际目标不同。先 resolve，再按路径组件判断相对关系。项目根目录在启动时固定，不能在每次检查中跟着重新解析改变信任范围。

    04 · 新建文件不存在，resolve 怎么检查？

    默认 strict=False 会解析能解析的现有部分，再追加剩余路径。如果父目录是指向外部的 junction，最终新文件路径也在外部，应被拒绝。当前实现支持正常新文件，但不能承诺消除检查后新建/替换父目录的全部竞争。

    05 · Shell 的工作目录限制是不是沙箱？

    只是 cwd 的路径检查。子进程可以自己使用绝对路径、调用其他程序或发网络请求。当前它仍拥有当前用户的系统权限，命令审批与黑名单不能保证其全部效果；这正是本章未实现系统级沙箱的边界。

    06 · 有了 resolve 和多次检查，还存在什么风险？

    检查与 IO 不是原子的，其他进程可能在两者之间改变链接，这是 TOCTOU。还有硬链接对象身份、项目内敏感内容、Shell 间接执行和外部网络访问等问题。项目没有把路径校验宣称为完整不可信代码隔离。

    07 · deny 是永远优先吗？放行模式能覆盖吗？

    要区分跨层与同层：先找到最高匹配层，同层 deny 优先，所以高层 allow 可以覆盖低层 deny。一旦确定了最终生效的 deny，所有权限档位都尊重它。硬限制和计划模式限制始终不可通过规则或确认解除。

    08 · 为什么严格模式已有 allow 还要确认？

    严格档位表达每次执行都需要人在回路。allow 仍可保存，换到默认或放行档位时使用，但不能免除严格档位的逐次确认。deny 直接拒绝，不通过弹窗绕过。

    09 · 为什么永久放行存在本地项目层，而不是用户全局层？

    用户在当前项目批准一次具体操作，不应自动扩大到所有项目。本地文件对应本机本项目，适合保存私有授权；项目级用于共享规则，用户级提供跨项目默认。自动保存只精确绑定工具、目标及命令 cwd。

    10 · 如果用户等待审批很久，会触发超时吗？

    不会消耗工具执行超时：authorize 完成前没有创建实际执行任务，执行计时在获准后开始。等待期间可以取消；取消清理 Future 与 pending，旧响应 ID 不再生效。当前没有额外审批等待截止时间。

    11 · 无界面模式与多个并发工具怎样处理审批？

    无界面需确认操作立即返回 approval_required，不挂起。交互模式用审批锁串行提出请求，事件流仍能接收其他已完成工具结果。结果回写按原始调用顺序，避免并发完成顺序改变模型上下文语义。

    12 · 权限被拒绝以后，Agent 为什么还继续？

    拒绝是一次工具动作失败，未必意味着整个任务无法完成。把 code、output 和 executed=false 回灌，模型可以读取允许的内容、改变方案或解释阻塞；运行时仍有最大轮数和未知工具停止条件。这里验证了假模型恢复流程，没有保证真实模型总能合理调整。

    13 · Read 的拒绝能阻止 Grep 读同一个文件吗？

    当前规则按工具匹配，不是统一文件对象 ACL。Read 的 deny 不自动变成 Grep 的 deny，搜索规则针对搜索范围路径。因此保护敏感信息需要考虑每个可达工具，以及 Shell 的能力；不能只写一条读取规则就宣称完全保护。

    14 · 取消工具是不是相当于回滚？

    不是。进程可以停止，但已完成的磁盘写入和其他外部效果不能自动撤销。文件操作若已开始，等待实际结果并保存；未开始的调用标记未执行。调用/结果配对是历史一致性要求，不代表事务回滚。

    15 · 缓存与测试成绩，能证明项目效果吗？

    缓存字段证明服务报告的命中情况，不能单独证明真实总成本或任务质量提升。242 个本地通过测试验证实现行为；真实 API 联调、策略效果和对抗安全评估仍是不同验收任务，需要分别给证据。

    16 · 为什么这样拆模块，后续系统级沙箱怎么接？

    权限策略给出能否执行，工具接口负责具体动作，事件流负责反馈。后续可在执行工具的后端引入受限环境，同时继续沿用参数校验、策略、审批与结果协议；但需要重新定义路径映射、凭据/网络/资源边界和取消行为，不能仅替换一个 subprocess 调用就宣称完成。
