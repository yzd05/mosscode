# 规格驱动开发

让需求、设计、实现与验证保持一致。以减少错误假设和返工为目标，文档和审批的投入与任务的复杂度、风险及协作需要相称。

## 选择工作方式

先读取与改动相关的代码、项目约定和已有文档。复用现有规格和计划，避免重复维护相同事实。用户指定的交付物、审批方式和执行范围优先。

| 情况 | 默认方式 |
|------|----------|
| 范围明确、局部且易回退 | 在回复中简述目标、改动与验证后执行；按用户要求留存文档 |
| 存在需求歧义、跨模块依赖或需要协作 | 用一份 `spec.md` 记录需求、必要设计、任务与验收；内容变长或需要分别维护时拆分 |
| 用户要求四文档流程或逐阶段审批 | 使用 `spec.md`、`plan.md`、`task.md`、`checklist.md`；遵守用户指定的审批节点 |

在项目已有文档位置保存产物；没有约定且需要留存时，使用 `docs/specs/<feature>/`。根据新发现调整投入，说明影响；文档数量不是完成标准。

## 1. 明确需求与验收

记录目标、相关现状、行为要求、边界和可观测的验收标准。保留用户明确给出的兼容性、接口、技术栈等约束；需求主要描述行为，实现细节放在设计中。

区分已确认事实、工作假设和未决问题。能从代码、文档或验证获得答案的，先调查；可回退的低影响选择可说明假设后继续。会改变功能含义、公开契约或显著成本的未决选择，需要用户判断时提出简短问题，并推进不依赖该答案的工作。问题可以合并，只保留会改变方案的内容。

需求已有明确答案时，直接采用。存在有意义的取舍时，给出推荐方案和必要的替代方案，说明实际差异。

关键行为应有对应的验收方法。尚不能确定的内容明确标记其影响及解决条件；编码前解决会使实现方向失效的未决问题。

## 2. 形成可执行设计

说明满足需求所需的模块职责、接口、数据流和关键取舍，深度以能开始可靠实现为准。遵循现有项目结构，优先复用；复杂边界可用小型实验验证，再完善设计。

按可独立验证的结果拆分任务，注明必要的依赖、改动位置和验证方法。任务粒度由内聚性与验证成本决定，不按固定分钟数切碎步骤。不确定的文件位置先标明待调查，不编造路径。

验收方法在实现前形成，可以和需求写在一起。验证覆盖关键行为、错误路径和受影响的集成边界；需要验证完整用户流程时安排端到端场景。采用项目已有检查，按改动选择有价值的测试，不为了文档形式新增无意义测试。

需要拆分文档时，读取 [references/templates.md](references/templates.md) 作为起点；合并文档或简单任务无需加载模板。

## 3. 审批与推进

用户已授权实施时，在范围和关键需求清楚后继续工作。需要用户决定的产品取舍、用户明确要求的审批，以及超出当前授权的操作，分别在相关节点确认。

审批提交完整、可评审的内容和关键决策，默认按文档或方案整体评审。仅在用户要求逐段确认或内容确实需要分开讨论时拆分审批。用户只要求规划或评审时，交付对应产物即可。

## 4. 实现并维护一致性

按依赖推进任务，用实际验证判断完成。计划服务于目标；新证据支持更好的实现方式时，可调整授权范围内的细节，并同步受影响的设计和任务。改变需求或验收标准的调整，应取得所需的用户决定。

遇到阻塞，先检查原因与替代路径，继续独立任务；缺少必要信息或权限时说明具体缺口。修复验证失败后重跑受影响的检查，避免没有新证据的重复尝试。

更新发生变化的权威记录，保持需求、设计、任务和验收相互一致。共享定义通过引用复用。提交、发布等操作遵循用户授权和项目约定。

## 5. 用证据交付

将关键验收标准与实际结果对应，记录足以复核的命令、测试或行为观察。编译通过只证明编译结果；行为验收需要对应行为的证据。尚未运行、验证失败与环境阻塞分别标明，无法验证的项目保留为未验证。

交付说明完成的行为、验证结果，以及影响使用的剩余问题。只有授权范围内的实现完成且所需检查通过，才能报告全部完成；用户请求仅规划时，以相应文档完整可评审为完成标准。
