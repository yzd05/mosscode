# 拆分文档的起点

用户要求四份文档，或需求、设计、执行和验收需要分别维护时使用。保留本次任务需要的栏目，调整标题和文件名以符合项目约定。示例中的尖括号内容是生成时要替换的模板参数。

## spec.md：需求和成功标准

```markdown
# <功能名称> Spec

## 背景与目标
<当前行为、要解决的问题和期望结果>

## 行为与约束
- F1：<输入或触发条件，以及预期行为>
- <兼容性、性能等与本次改动相关的明确约束>

## 边界
<本次范围；容易误解但留到后续的内容>

## 验收标准
- AC1（F1）：<操作或输入> → <可观测的结果>

## 假设与未决问题
<仅列实际存在的问题、影响、解决方式和时点；没有则省略>
```

## plan.md：足以开始实现的设计

```markdown
# <功能名称> Plan

需求来源：<spec.md 的相对链接>

## 实现方案
<职责划分、关键接口、数据流以及如何满足关键需求>

## 关键决策
<有实际取舍的选择、理由与后果>

## 集成与兼容性
<受影响的调用方、数据或部署条件；按需补充迁移和回退方式>

## 待验证的技术假设
<假设、最小验证方式和结论；没有则省略>
```

## task.md：结果、依赖和进度

```markdown
# <功能名称> Tasks

设计来源：<plan.md 的相对链接>

## T1：<可独立验证的结果>
- 状态：待执行 / 进行中 / 已完成 / 阻塞
- 改动：<已确认的文件或模块，以及必要改动>
- 依赖：<前置任务或条件；没有则写无>
- 验证：<检查方法与预期结果>
- 实际结果：<执行后记录结果或证据；执行前写未执行>
```

任务步骤仅在具体操作容易出错或需要交接时细化。必要的共同上下文链接到 spec 或 plan。

## checklist.md：验收与证据

```markdown
# <功能名称> Checklist

验收来源：<spec.md 的相对链接>

| 标准 | 验证方法 | 状态 | 实际结果与证据 |
|------|----------|------|----------------|
| AC1 / F1 | <操作或检查> | 未执行 | — |
| <相关集成边界> | <检查方法> | 未执行 | — |
| <项目要求的检查> | <实际检查命令> | 未执行 | — |
```

状态采用未执行、通过、失败或阻塞。需要完整用户流程时加入端到端条目；同一检查可以覆盖多条标准，但其证据应支持各条结论。
